## 2. 要解决的问题与目标

已对齐：先从第一性原则建立从人类意图到可验证交付的责任／判断主轴，再决定专业 Role、Skill、Playbook 和工作流如何附着。
现有优秀工程经验可以保留、评价和重新归位，但不能让现有角色、阶段或来源结构替我们决定新骨架。
“吸收更多 skill”是手段，不是本轮成功目标。

期望得到一套可以按任务调用专业判断的团队设计：

- 人类意图能形成 Owner 可理解、可确认的产品行为约定。
- 各类专业判断有清晰边界，错误可以退回真正拥有该判断的责任方。
- 技术规划与实现拥有合理的自由度，不把责任默默塞给离问题最近的模块。
- 验证使用已接受的行为、领域与系统约束作为依据，不为通过而改写标准。
- 经验按责任和问题挂载，控制注意力负担、传递失真与流程成本。

上述是设计目标，不声明已通过真实业务运行证明。
已对齐：讨论／设计阶段允许充分、多元探索；最终方法须收敛，避免过度流程化、工程化和防御性。
Owner 明确要求先 Divergent 再 Convergent，“中间胖，两头尖”：输入问题与约束清楚，中间展开选择，输出尽可能极简、优雅；探索宽度不转化为交付负担。
责任划分不自动产生固定 Agent、常驻 gate 或额外文档；按任务需要调用，简单任务可直接使用足够的已有结论。

## 3. 已对齐的基本术语

| 术语 | 本轮含义 |
| --- | --- |
| Responsibility / judgment | 对一类问题做什么判断、做什么工作、交出什么供别人继续，以及何时必须回来找它 |
| Decision authority | 在既定委托范围内改变某类结论的权责；产物主笔身份本身不产生这种权责 |
| Change / execution authority | 允许实际改变对象或执行动作的授权；专业上判断正确不自动授予执行许可 |
| Delegation Envelope | 委托的目标、保持的承诺、专业权责、自主调整空间、风险／资源边界和保留决定；不是默认文件白名单 |
| Artifact | 可供后续工作依赖的持久结论与依据；可是一份文件或已有文件中的有界部分 |
| Role / Professional Profile | 可复用的专业配置；本轮首选三层装配方向，具体组合仍未定；名称和默认配置不产生任务决定权 |
| Agent instance | 执行某次任务的具体会话；一个专业配置可以产生多个实例 |
| Instance Charter | 本次实例的责任、范围、输入、交付义务、召回和独立性约定；有效决定权受实际委托与上层政策约束 |
| Skill / playbook | 完成特定问题的方法、指南或内部工作流；挂载方法不自动授予决定权 |
| Driver | 系统内部的责任路由与依赖／交接管理责任；拥有程序性裁量，不自动拥有被路由问题的实质专业裁定权，不作为默认人类接口 |
| Voice | 与人类对齐意图、解释专业取舍、读回理解并记录决定的接口责任；不自动获得所有专业裁定权 |

## 4. 人类接口与责任拓扑

已对齐：接触人类的默认接口不应是 Driver。
当前 Oracle 同时承担 Voice 和高阶裁定，是现有会话的职责组合，不证明未来必须合并这两种责任。
未来 Voice 甚至可以仅承担人类接口与 Intent / Outcome，具体是否一个或多个 Agent 尚未定。

Intent / Outcome 是与人类对齐的语义根。往下的表达逐渐进入产品、领域和技术语言。
更深层判断需要人类决定时，必须翻译成可理解的行为、成本、风险或承诺，不能要求 Owner 对未经解释的实现细节背书。
技术术语本身不是禁止项；接口应适应 Owner 的理解背景。
已对齐：Voice 负责与 Owner 对齐 Delegation Envelope，解释自主空间、保留边界与升格取舍，并维护可引用的接受记录。
它不替专业责任方设计模块拓扑，不凭人类接口身份扩大授权。

暂时保留以下六类判断空间，不把它们当六个 Agent 或固定六阶段：

| 类别 | 核心责任 | 状态 |
| --- | --- | --- |
| A Intent / Outcome | 理解人与使用情境、目标、价值、范围和优先级；审查事实与假设，形成后续可用的问题定义 | 已对齐，不因内部存在目标选择与事实审查而拆成两个责任节点 |
| B Behavioral Contract | 明确外部可观察行为、交互、场景、异常状态与产品接受条件 | 已对齐 |
| C Domain Semantics | 定义概念、关系、不变量、状态、业务规则及上下文边界；不只是词典编写 | 已对齐，横向约束 B 和 D，不是每任务必经阶段 |
| D Technical / System Design | 明确实现行为的系统边界、接口、数据责任、依赖与技术取舍，形成可实施规划 | 已对齐，与 E 区分 |
| E Implementation | 在约定内实现；保有局部算法、函数、类型、重构、测试接缝等判断空间 | 已对齐，不得静默改写上层约定 |
| F Verification | 设计可观察验证、获取真实证据、判断约定是否成立；可作用于实现前的设计与规划 | 方向已对齐，内部如何组合尚待定义 |

A 内部的分析不脱离原始需求，但必须区分用户报告、推断和观察证据。
例如“用户说查找成本高”可引发“经常找不到”的调查，不能仅凭前一句把后一句记成已证实事实。

固定的是责任边界，调用顺序和实例数量按任务决定。Domain 与 Behavior / Design 可以互相反馈；新事实应退回最早受影响的判断。
Spec 是这些专业结论汇合的交付物，不天然由一个 Spec Writer 拥有其中全部决定权。

## 5. 人类冻结、挑战与实施自由度

已对齐：Behavioral Contract 是默认人类冻结面，因为最终交付必须兑现这个约定。
它不是唯一人类决定面。产品行为变化、重大成本、风险、不可逆承诺或既有政策之外的决定，仍可能需要 Owner。
冻结应固定可观察承诺及其适用条件，不把全部函数和算法预先指定，也不只留下模糊方向。

已对齐：D 与 E 需要区分；技术规划加实现链路至少要有两个实际角色承担工作或挑战，避免同一注意力上下文包办整条链。
尚未决定第二方具体是实现者事前挑战、验证方设计评审，还是任务需要时兼有；不预设两道常驻 gate。
本轮 Owner 基本完全认可下述 D→E 分界；示例推演不是业务运行验证。

### 5.1 D→E：跨边界承诺与局部实现

已对齐：Technical Plan 固定 coordination surface；Implementation 拥有 implementation interior。
coordination surface 指其他责任方、模块或调用者必须依赖的承诺；implementation interior 指在这些承诺内的局部实现选择。
判别题：改变这个决定，是否会要求别人改变其依赖的语义、接口、约束或验证依据？
若会，应作为跨边界决定接受或显式委托；若不会，且在已有约束内、局部可恢复，原则上由 E 判断。

已对齐（Owner 本轮明确接受前轮补充）：

- D 汇合并落实跨边界承诺，不因此取得 B/C 的决定权。业务状态含义来自 C，外部行为来自 B；D 不能重新定义它们。
- 私有代码也可能影响性能预算、安全或资源边界；“没有调用者改代码”不足以证明它只是内部细节。
- 不必规定整个系统所有接口；只须把本次任务涉及、会被依赖的承诺明确到足以继续，并引用已接受对象。

Technical Plan 的交接至少显式区分三类内容，可用简短段落，不要求三份文件：

| 部分 | 要表达什么 |
| --- | --- |
| Commitments | 已接受、不得自行改变的责任归属、共享接口、不变量与相关约束；指明所依赖的上游版本和决定责任 |
| Delegated Decisions | E 在什么范围和预算内自主判断；可成类授权，无需枚举每个 helper 或算法 |
| Recall Conditions | 哪些发现超出委托或使承诺不成立，需要返回相应责任方 |

最低充分性测试：未参加讨论、能力足够的实现者，读取接受的上游产物与 Plan 后，能否开始实现而不猜跨边界承诺？
过度规定测试：换一种局部实现，若所有上游约定、共享假设与验证依据都不变，Planner 为何必须固定这一项？
后者允许有明确约束依据，例如已接受的安全、兼容或可维护性要求；不能仅因 Planner 的偏好写死。
这两项是语义检查问题，不声明已可由当前检查器机械判定，也不要求每次任务新增独立 gate。

### 5.2 两端推演夹具（候选示例，不是 UCBIP 已定技术方案）

跨模块 freshness：以下假设 B/C 已接受页面与 turn 的版本语义，真正取舍仍要引用其原始产物。

- **Commitments：**页面数据生命周期负责 page freshness；turn 接入边界按已定语义绑定允许的 snapshot；case_read 消费该 snapshot。实际版本选择、失配行为、数据读取接口及安全边界必须有接受依据，不能以“最新”一词代替。
- **Delegated Decisions：**在上述承诺内选择私有函数组织、校验实现和测试 fixture；不因私有命名或拆分方式召回 D。
- **Recall Conditions：**实现需要自行改读 head、改变 snapshot 绑定、复制 freshness 责任或改变失配行为时，记录受影响承诺，经 Driver 路由。系统边界问题到 D，行为或领域变更分别到 B/C，缺人类授权时经 Voice 返回 Owner。

纯局部任务：假设一个现有私有文本转义函数已明确输入范围、输出行为和测试依据，只替换内部实现。

- **Commitments：**保持已接受的转义语义、签名、错误行为和适用质量约束；引用现有契约与观察，不另写一套预期。
- **Delegated Decisions：**E 自主选择扫描方式、内部数据结构、helper 与局部测试组织；无需 D 预先指定算法。
- **Recall Conditions：**输入语义不清、必须改调用者或共享接口、输出承诺无法保持、质量约束无法满足时返回对应责任方。

局部任务可以引用已有 Plan / 契约，加一段本次差分与委托范围；不因存在 D/E 边界而强制重做规划。
候选：召回只暂停依赖争议结论的工作，保全已做结果；不自动停止整个团队或重开全部设计。

已对齐：下游可挑战上游，但挑战不授予修改上游结论的权力（No Silent Authority Transfer）。
扩大调查视角不同于扩大实际改动范围；可以发现真正责任在相关模块，但不能由此推导任意修改权限。

### 5.3 Delegation Envelope：目标与约束内的团队自治

已对齐：Owner 委托目标、约束与保留决定；专业团队拥有该 envelope 内实现手段的选择权。
技术改动范围通常由调查发现，是专业判断的结果；初始 expected touch set 是工作假设，不默认成为授权边界。
Owner 可以明确限定子系统或对象：例如本轮只优化 classification agent、不改变数据库设计。这种显式边界必须遵守。
“跨模块”本身不构成升格理由；越过明确边界也不能以模块耦合为由自行放行。

Envelope 至少表达以下内容，可引用既有契约，不要求新建独立文件或逐项数字化：

| 内容 | 委托表达 |
| --- | --- |
| Goal | 要兑现的目标、范围与非目标 |
| Frozen commitments | 已接受行为、领域规则、兼容要求等须保持的承诺 |
| Delegated professional authorities | 哪类判断委托给哪种责任；对应裁定范围，以及选择或修订实现手段的空间 |
| Accepted policies / quality constraints | 已接受安全、隐私、质量与运行政策，不由本次方案自行改写 |
| Resource envelope | 成本、周期及相关回归工作在什么范围内可以自主安排 |
| Risk acceptance envelope | 谁可评估、处理风险，谁可接受什么程度的剩余风险；二者不自动相同 |
| Reserved decisions | 哪些决定或动作保留给上级或 Owner，越界时返回谁 |
| Explicit prohibitions | Owner 明确保留的子系统边界与其他禁令，不以隐含的“顺带必要”绕过 |

授权采用原则、保留边界和升格条件，不维护 helper／文件／相邻模块的允许行为清单。
生产发布、破坏性或不可逆数据操作、权限政策变更、未获许可的外部副作用等，不能由技术合理性推导许可；既有明确动作授权可被继承。
实际工具或 sandbox 权限与专业／执行授权分别成立：技术上能写不证明获授权，获授权也不能绕过工具限制。

已对齐：自主技术范围调整须满足：

1. 仍为原委托目标，不引入新目标或顺手优化。
2. 保持 envelope 的冻结承诺与明确范围边界；D 不接管 B/C/政策决定。
3. 不引入超出接受范围的风险类别或实质风险增幅，不触碰保留决定。
4. 成本、周期、回归影响仍在接受的资源范围内。
5. 方案与目标相称，是充分解决问题所需要的范围，有依据而非“既然能改就一起重写”。

专业判断、授权判定、执行分配是三件事，不要求三个新角色或三个 gate。
D 等专业责任方提供方案及影响依据；明确边界下 Driver 可判定是否在 envelope 内并重排工作。
风险、成本或语义边界有实质争议时，Driver 应路由相关判断，不能自填“风险不变”让自己放行。
尚未查明不等于已经保持；但也不因所有细节尚未知就把正常范围内专业判断退给 Owner。
已对齐：Driver 是 procedural authority，不自动拥有 substantive authority；它可判断调用、依赖和交接资格，不能凭流程地位制造架构、安全、成本等专业结论。
已有接受结论与政策足够时直接推进；仅因出现技术范围调整，不再创建一个常驻“审批 Agent”。

已对齐：发现问题、专业判断、接受风险／扩大授权分别成立。
任何责任方可以发现问题；相应专业责任评估、提出处理；有效委托内的决定由被委托责任作出，越界由拥有该边界的 authority 接受或拒绝。
风险识别 → 评估／处理 → 剩余风险接受不是三个固定阶段，而是必须分清的三种判断。
选择 mitigation 的权限不自动包含接受超阈值剩余风险的权限；风险接受也不自动放宽已冻结行为、政策或发布授权。
成本、行为与其他问题遵循同样的路由语法；Security 等名称在此指判断责任，不预设新增常驻 Role。

已对齐：No Silent Authorization Expansion。正确方案需要更多工作，不产生额外执行许可；现有 envelope 已覆盖的调整也不重复索取人类许可。

执行闭环：E 记录跨边界发现 → Driver 召回相关 authority → 修订并接受专业方案 → 对照既有 envelope → 更新 Plan 版本与 Instance Charter → E 继续。
在 envelope 内，D 可修订自己拥有的技术承诺，Driver 可重新绑定实例，不再申请 Owner 对文件清单的批准。
不在 envelope 内，先返回受影响 authority；需要改变人类保留决定时，Voice 解释目标关联、可选方案、代价与风险，交 Owner 决定。
共享边界冲突由指定的专业责任方整合，不以谁先到场为准。任何变更保留接受记录与受影响依赖，不能静默覆盖旧承诺。

两例边界：

- 工具与页面存在真实 freshness 依赖，改变内部联动仍满足上述条件：团队自主调整，不仅因多改模块回问 Owner。
- classification 工具方案要求改变 SQLite schema，而数据库设计被 Owner 明确保留：先解释为何相关、替代手段及影响，经 Voice 请求范围／约束裁决，不把 schema 设计本身交给 Owner 编写。

扩大观察与推理视角仍受访问权限、隐私和任务需要限制；看见依赖不等于获准修改。修改范围可在 envelope 内随专业判断调整。

已对齐（Owner 本轮接受 challenge 并细化）：

- 范围须与根因和责任边界相称、有因果依据，不夹带机会性改造。不能用最少文件或最小 diff 代替判断，应关注不必要的共享承诺、依赖和重复 ownership；不要求证明全局唯一最优。
- Observation / reasoning / mutation 是三类边界，不采用严格的集合包含链。推理可提出未观察假设但须标明，观察有访问限制，修改需授权与足够依据；不能将视角应更广写成无限读取权限。
- 风险类别变化本身先触发判定，不自动等于 Owner 必须裁决。应看是否越过接受的 envelope、政策或保留权责；既有安全等专业责任方有有效委托时，可以处理范围内判断。

### 5.4 四类边界推演（示例假设，不是已运行验证或实际执行许可）

共同前提：存在可引用的目标与 envelope，专业权责已明确。若某项委托未说明，示例不能替项目补授权。

| 情形与前提 | 专业判断与依据 | 委托内可安排的结果 | 升格触发与去向 |
| --- | --- | --- | --- |
| 普通跨模块重构：目标是修复 freshness；内部联动在委托内 | D 确认真实责任归属，给出行为／领域承诺保持、接口和回归影响依据 | 更新 Plan 与受影响 Charter；Driver 安排各部分和验证，不因模块增加问 Owner | 若发现需改变 revision 定义，召回 C；若必须改变冻结行为，召回 B 并按其接受边界到 Voice／Owner |

## 6. 验证责任的依据

已对齐：F 不应只在代码写完以后介入。
行为预期来自 B，领域不变量来自 C，架构约束来自 D，质量要求来自已接受约定与政策。

## 7. Role 与按需装配的首选方向

已对齐：启动 Agent 时，需要适合任务的专业心智模型、逻辑纪律和常见误区，而不是泛化的资历描述。
这类配置不同于所有 Agent 都适用的全局／项目 AGENTS.md。Skill 提供其上的具体方法。

首选候选：稳定责任原语 → 可复用 Professional Profile / Role Preset → 任务绑定的 Instance Charter。
本轮 Owner 明确认可 D/E 分析；三层 Role 方案来自所提供顾问建议，尚不记为 Owner 整体冻结决定。

- 原语定义责任、决定权类别、交接与召回、独立性要求等可组合内容；专业方法与经验可随评价升级，不宣称永远不变。
- Profile 缓存常见责任组合、心智模型、误区与方法入口，不是全部任务的固定职位目录。
- Charter 绑定本次范围、具体委托、不可变约定、输入、产出、召回、独立性与工具许可。

候选原则：Roles are caches, not authorities。Profile 提供默认配置，不授予权限。
Charter 是本次委托的明确记录，不凭写入“允许”就产生权限；它必须继承实际授权、既有政策和硬约束。
已对齐：Driver 可在既有 Delegation Envelope 内重生成或扩展 Charter，不因初始实例范围变化而重新请求 Owner；新的 Charter 仍继承完整约束。
Driver 在接受的原语与预设范围内做 bounded composition，不每次重新发明职业，不通过删除配置绕过独立性或其他硬边界。
高风险或超出预设约束的组合仍需要明确评价，具体资格判据待设计。
即使没有固定 Role 文件，也须在实例启动前明确责任与权限；Skill 列表只表达方法，不能替代任务委托。
