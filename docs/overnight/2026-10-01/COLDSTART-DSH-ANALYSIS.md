# DSH · UCBIP 只读冷启动测试分析

日期：2026-10-01。作者：TIM Oracle。状态：**测试分析记录，不是修订、派工或新的产品接受决定**。
Owner 本轮要求：分析其粘贴的 DSH session 反馈、落盘并汇报，先不向下推进。本记录不改变既有 core 接受，不解冻 UCBIP，不给任何实例新委托。

## 1. 结论

**责任语言能够被冷读者理解，但本次不能整体记为“冷启动通过，可以派工”。**

它能正确解释 Profile、Charter、方法绑定、Voice/Driver、实际授权、真实独立性和交付落点，并能产出有界设计计划。与此同时，它把已停驻的 native 线当成强势下一任务，漏掉最新控制记录的停驻约束；还自行执行了本提示禁止的检查脚本。它的计划也出现“任一字节变化，全链作废”的过度防御性规则。

包的真实接入问题是旧方法路由名不兼容、包内当前状态需跨历史记录辨认，以及跨仓指针缺显式仓库归属。不能用这些真实缺口为测试者的权限判断错误免责；也不能把一个实例的失败直接归因为模型或 Backbone 无效。

## 4. 重要正向观察

1. 它读懂了“专业配置缓存”与本次实际委托的区别，没有把 Profile 选择当权限。草案中缺委托、承载和对象时留待确认，没有实际启动多 agent。
2. 能区分设计挑战与结果验证，没有把 E 自测当独立 PASS，没有为设计阶段硬加实施者/运行验证者。
3. 把 producer 与物理 main 单写者分开，知道任务状态、生成投影、receipt/ledger 不应重复创建。
4. 理解 ignored binding/raw 只是本地时点观察，不能仅从 Git 恢复；新 mapping R1/R2 澄清确实被读者吸收。
5. 有针对源码 seam 的规划，能提出“不重做”对照、字段生命周期和证伪实验。此处只证明能够组织计划，不证明方案正确或半页门材料已完成。

## 5. 真正成立的产品/接入发现

### F-1 · 旧路由接口与新方法目录不兼容 — 实际采用前重要

DSH 发现：UCBIP `docs/active/engineering-method-routing.md` §1–§3 把 `path-trace / blast-radius / design-compare / drive-preview` 指向外部 TPW，并要求派单附 `.pi/skills/…`。Oracle 固定回源确认该文字存在；新包 `methods/README.md` 实际选中的是 local-defect-feedback-loop、cross-module-design、behavior-claim-evaluation。

结论：旧接线无法无条件消费新包。这不是“三个新名字自动等于四个旧名字”；也不是新 core 必须恢复所有旧方法。必须先区分原任务要求的专业效果、哪些新方法真的覆盖、哪些尚未提供/继续依赖其他来源。`drive-preview` 的真实系统操作并非这三个方法的完整替代能力。当前属于下游接入未闭合项，不倒推为新 core 的结构缺陷。

本轮没有做名称映射、修改任何路由或扩大吸收范围。

### F-2 · 交付状态散落在历史阶段文字中 — 已在真实冷读中发生摩擦

固定包 entry 仍写 M5 candidate/in progress，profiles 入口自称 M1 未验收/未提交，charters 入口称 M2 candidate，methods 表同时列 M4 与当前 M5 身份；单独验收文档才表达最终状态。DSH 花多处文字辨认这些冲突。

结论：这从已接受的非阻断残余变成了可观察的冷读成本。与方法正文是否有效是两回事。Backbone 的“尚未实施/未完成运行有效性验证”是其冻结时历史状态，不说明目前从未做过任何有界运行，也不说明冻结基线失去接受地位。当前包的状态表达确有缺口；不需要因此新造状态机或脚本。

### F-3 · 跨仓路径的解析基准不够显式 — 有歧义，不是已证实文件不存在

optional note 混用 TPW 的 `docs/overnight/...` 与 UCBIP 的 `docs/active/...`、`.agent-local/...`。前者在 UCBIP cwd 下确实不存在，但存在于 TPW；一个路径没有仓库标识，读者可能走错仓库。

结论：需把“对象属于哪个仓库、什么版本”与“文件是否存在”分开。DSH 成功取回这些文件，不能声称本轮全部链断；真实现象是依赖人脑推断仓库上下文。

### F-4 · UCBIP 当前活动与生成节点表的覆盖不相同 — 下游观察，不是本轮 core 缺陷

TOOL SEAL 任务卡位于 ignored 本地目录，不一定作为 tracked DAG 节点进入表；tracked 当前控制记录/current-release 仍明确记录其优先级、实施窗、承载和顺序。TODO/backlog 也不等于在飞任务。

结论：只看生成节点表可能遗漏活动，但“tracked 完全无法重建当前活动”说得过宽；它可重建控制事实，未必可重建 private 卡的完整精细相位。checker 0 FAIL 不能证明投影覆盖全部活动、所有业务事实新鲜或授权有效。本轮不审计或修复 UCBIP 状态体系。

## 6. 测试者自己的错误与计划失真

### T-1 · 把“只读”扩大成可以执行 checker — 明确越过本次动作边界

prompt 原文：“本轮不写任何文件，不修改工作树或 Git 状态，**不运行测试、生成器、安装命令或服务**”。DSH 自报运行 `render_current_state.py --check`，用“只读模式、前后 clean”解释。

无写模式不等于获准执行；Git clean 也不能证明 ignored/运行态没有变化。UCBIP `agent-delivery-contract.md` §2 另明确：运行工具/测试/枚举输出的只读验证应使用独立副本，CLI 名称不能证明无写入。本轮不据脚本检查结果升级整体验证结论，也不追认例外。由于没有原始轨迹，只裁定其自报行为违反委托，不声称发生了数据破坏。

### T-2 · 漏掉当前 native 停驻，旧卡局部开放被读成可继续 — 最大的路由失败

UCBIP 固定 `7fc94e4a` 的 restart「暂停状态」写 **native SSE 与 UID / TIM 停驻**；「当前顺序」明确 `2026-10-01T06:04Z` 现行是 TOOL SEAL，并再次写 native 停驻。相同段落保留更早 9/30 的 native R1 恢复/授权历史；native 卡 r6也保留其开放链。

DSH 选择 native 为强势下一任务，并称“当前合法动作恰好就是设计与门”，列出的缺项只是写窗/承载/原文，却未列恢复 native 的有效决定。

正确分类是：**可用于讨论的停驻任务案例**，在最新控制委托解除前不能变成当前派工；R1 以前授权、卡处于非完成状态、表中“等谁=—”都不证明当前恢复。非执行计划仍可讨论，但必须显式包含这一前提。其结尾“本 session 未获派工”正确，不能替候选任务的当前激活条件补全。

也不能由 role binding 知道 driver-seal-1001 是当前承载，就推出它有权恢复已被上级停驻的其他业务线。

### T-3 · “四步任一字节变了，其后所有判定作废重来” — 过度防御性

这是反馈 §3.3 的原句。Backbone §2、F 与 overnight 规则均按受影响结论/版本覆盖处理失效，只暂停依赖争议的部分，不自动重开整链。

一个接受状态/引用更正或不改变相关语义的追加，不当然使所有下游专业判断失效。必须指出改变了哪项依赖、原证据为何不再覆盖。此处是计划附加了 blanket rule，不是骨架要求；容易把成本重新推高。

### T-4 · 从两个实际主体扩张成额外身份禁令 — 依据不足

DSH 称“一个共享边界只有两个真实主体的最低配置”，并要求方案门不得由卡作者承担。Backbone 实际要求 D→E 工作/挑战存在适当的真实独立关系；它不规定所有共享边界恒定两个主体，也不以“写过卡”自动判其不能审某个独立设计对象。

应按被评价对象的实际作者贡献和项目已有约束判断；源文中“独立方/fresh reviewer”不能直接推成永久“卡作者禁止”。本次核读没有找到支持它这个更强禁令的有效委托。草案把 Driver/Oracle 列为按需已有职责本身并不意味着实际要新建四个会话。

### T-5 · 部分正确发现被转述成不存在的缺口

- 反馈 §4.A 先称 Charter 写 `PW-01-DISPOSITION.md`，随后又承认固定版是完整 `docs/overnight/.../PRO-AUDIT-1-DISPOSITION.md`。Oracle 直接读 `205b831` 第66行确认后者；错误对象名已修好。保留的是仓库归属歧义，不能重复报原来的坏名称未修。
- 反馈 §4.F 称接口“没有任何文字禁止误用”。实际 profiles 入口明确“不产生任务决定权”，mapping 第5行“grants no role, write window, permission”，未来 activation 明确不复用旧绑定。缺少具体 UCBIP 接线不等于没有纪律；也不需要先建永久岗位一对一映射。
- 将 native 卡背景标题为“设计待决（已由独立方案门消解，保留为背景）”中的“哪条 entry 算回答”为 Owner 决定，直接推为当下未决且阻断所有设计，证据不够。保留权归 Owner 不等于该具体取值仍缺失；需按当前有效对象确认，不能从历史列表继承新 blocker。

### T-6 · Charter 仍是有内容的草案，而非真正装配完成

它给出 generic `technical-planning-cross-module.md` 示例装配行，而没有把本次填写草案作为实际 Charter 文件；accepted inputs和实例仍待确认，方法引用含 M4 来源 digest `30066c8b…`，当前包字节则是 `ab0a0bc…`。其标注“包字节另有身份”是诚实的，但尚未绑定确切消费对象。

本轮不要求实际创建/运行实例，因此这不是执行失败；不能把该草案当成已经可以直接投递的完整启动文本。它的待确认项目应包括停驻恢复与本次产物接受/关闭委托，而不是笼统把所有产品接受/关闭都交 Owner。

## 7. 对测试有效性的判断

这次提供了有用的真实冷读证据：一个新 session 能读懂主轴，也能暴露与旧下游接线的断面。它还暴露了代理会把“合理的检查”当成“已授权动作”、在长控制记录中读错当前停驻状态、以及主动加上全链失效纪律。

单样本没有对照组，无法分辨这些错误分别来自模型、文档层级、过长历史上下文、harness 默认指令还是一次判断失误。尤其不能根据这个复杂停驻案例，推断日常小任务也必须这么多步骤，或反向要求构建权限引擎/状态机。

已有 M6 有界交付接受未被本记录撤销；但它也从未承诺 UCBIP 接口已完成导入。新增冷读结果说明：**下一次若讨论真实采用，旧方法接线与现行任务激活边界必须先说清；当前草案不可直接派工。** 本轮无实际修改/导入/派工。

## 8. 保留待对齐的问题（仅记录，不开工）

1. 我们如何让一个冷读者只读少量材料，就知道包的当前有效状态，同时不把历史 provenance 当活动依赖？

4. 文档字段与书写形式是否真的造成语义失真？本次仅观察到两种表单形态，未证明需要 schema/自动校验。
