# 集合 A ↔ 集合 B：下游文档映射

本工作流会产出 9 类东西。它们是**产物**，不是文件——每类是一组字段、一个产出方、
一批消费者、一个存活期。具体落在磁盘哪个路径，不在本库决定。

因为下游仓库各有各的文档体系，**本库不定义目录结构**。它定义的是纪律。

---

## 一句话原则

> **纪律继承，位置映射。**

| 层 | 谁说了算 |
|---|---|
| **什么时候写** | 本库 |
| **谁写** | 本库（`registry.yaml` 的 `producer`） |
| **写完谁拿** | 本库（`consumers`） |
| **能不能被改** | 本库（`A9` 只追加） |
| **放在哪个目录** | 下游 |

违反这条原则的典型做法，是把「决策台账」这个纪律降级成「在某个临时目录（例如
`.pi/`）下维护一个 tsv」——
然后下一个人以为那只是个约定，可以删掉、可以改、可以换个地方。
纪律脱离了「必须由谁产出、必须被谁消费」的结构，就会退化成目录名。

---

## 三种情况

装配者进入一个新仓库时，先判它属于哪一种：

### 情况一：文档体系几乎没有

问过 Owner 之后，把集合 A 整搬进去。这是最简单的情况，也是最常见的情况——
大部分代码仓库的文档只到 README 和一个随手写的开发笔记为止。

### 情况二：已经有一套厚实的体系

**逐项映射**，形成该仓库的 *adaptive 版本*。

```
本库          下游
─────────────────────────
A1 诉求    →  3 需求描述
A2 事实    →  7 调研记录
A4 契约    →  1 设计文档
A5 任务图  →  2 任务
...
```

映射时逐项回答三个问题：

1. 下游有没有对应的东西？——有就映射过去。
2. 下游的那个东西，**产出方是不是同一个角色**？——不是就不能映射，
   这是纪律冲突，必须让 Owner 裁决。
3. 下游有没有本库要求、但它没有的东西？——有就补，或者退回。

映射表本身是装配者的决定，要记进 `A9`。

### 情况三：已经有厚体系，但 Owner 仍要本库的

按集合 A 改造下游。这需要 Owner 明确授权，
并且改造要保留下游已有的、有价值的内容——不是清空重填。

---

## 映射时最容易犯的三个错

**1. 只映射名字，不映射责任人。**
下游的「设计文档」是某个特定的人写的；本库的 `A4` 产出方是 `architect`。
如果这两者对不上，映射就是假的：名字对了，但没人负责按新纪律产出它。

**2. 因为下游没有对应物，就把那类产物取消。**
产物被取消意味着它下游的消费者会缺料。
`A2` 事实集如果没有落点，`P4` 的裁决就没有证据可依。
**正确做法是：给这类产物在下游找一个新落点，或者退回告诉 Owner 缺什么。**

**3. 把纪律一起映射掉。**
下游的体系说「设计文档可以改」，本库说 `A4` 冻结。
这不是两个可以调和的说法——它是两种不同的风险取向。
正确做法是：保留本库的冻结纪律，但允许它落在下游那个文件里，
并在下游的文件里写清「本文件在实现开始后不可改」。

---

## 落点找不到怎么办

**退回。** 不许塞进临时目录。

一条 `persistent` 的产物找不到落点，只有两个合法出口：

1. Owner 指定一个位置。
2. 记进 `A9`，标注「本类产物本轮不产出」，并说明因此哪个阶段无法开工。

第二个出口是诚实且可用的。第一个出口是常态。
**没有第三个出口。** 写进临时目录等于这条记录不存在，
而基于它做出的所有下游判断都建立在一个事实上——一份没人能再读到的记录。

---

## 这套映射什么时候做

- 装配者第一次进入某个仓库时，做一次。
- 该仓库的文档体系发生**结构性**变化时，重做一次。
  「加了一篇 README」不是结构性变化；「改用另一套任务管理系统」是。

不做这次映射就开工的代价：`A9` 不知道落在哪，
于是下一次会话找不到它，于是判断依据断链。
这个断链往往在几周后才以「为什么当初要这么做」的形式暴露出来，那时候已经追不回来了。
