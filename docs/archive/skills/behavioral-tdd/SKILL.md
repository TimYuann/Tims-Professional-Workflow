# Behavioral TDD · 行为驱动垂直切片 TDD 技能

## 概述
当开始编写业务代码或修改现有功能时调用本技能。融合了 Matt Pocock 的垂直切片与接缝测试理论，以及 `pstack` 的“测试行为而非实现细节”硬指标，**杜绝写出‘全绿但根本没测到真实逻辑’的同义反复测试（Tautological Tests）**。

## 核心操作规程（Process）

### 步骤 1：垂直切片，一次一个 Red-Green 循环
- **反对水平切片**：严禁一口气写完所有测试，再一口气写所有实现；
- **坚持垂直切片（Vertical Slice）**：
  - 针对当前最小的端到端行为，先写出对应的测试；
  - 运行测试，亲眼看到它发生 **Red（以预期原因失败）**；
  - 编写实现代码使测试转为 **Green（通过）**；
  - 在绿灯保护下执行 **Refactor（重构精简）**。

### 步骤 2：在接缝处测试（Test at the Seam）
- 严禁测试私有实现细节（不要断言某个私有局部变量等于几）；
- 站在调用方的视角，在系统的公开**接缝（Seam）**处进行测试：
  - 传入合法的外部参数；
  - 断言外部可观测的返回值、抛出的领域错误、或持久化的状态变更。

### 步骤 3：反同义反复测试自检（Anti-Tautological Check）
- **致命反例**：测试里的断言算式跟实现函数里写的算式完全一模一样，这种测试测出来的只是“模型会复制粘贴”，零信心；
- **变异自检启发式**：
  - “如果把实现代码中调用的依赖函数返回值改成空或 `undefined`，这个测试会挂吗？”
  - 如果测试依然绿着，说明断言根本没有起到约束作用，立即重写断言或删除该测试！

## 反借口与典型红线（Common Rationalizations & Red Flags）

| 典型借口 / 行为偏差 | 严厉反驳与纠偏纪律 |
| :--- | :--- |
| “我先把代码写完了，再补个测试保平安” | **假 TDD！** 事后补的测试大多沦为对现有代码逻辑的同义反复，无法证明你真正理解了失败边界。 |
| “为了方便测试，我把类的私有变量全改成 public 了” | **破坏封装！** 应该在公开接缝处测行为，而不是刺探私有状态。 |
| “测试跑过了，虽然我直接把期望值硬编码在断言里了” | **自欺欺人！** 断言必须代表客观期望，严禁为了凑绿灯反向修改测试判据。 |

---

## 退出判据（Exit Criteria）
- [ ] 亲眼见证过测试在实现前红过，并在实现后变绿；
- [ ] 测试模拟调用方行为，未侵入私有内部细节；
- [ ] 通过变异自检，确认断言具备确凿的失败抓错能力。
