# System Tracing · 系统真实路径追踪技能

## 概述
当遇到诡异 Bug、性能瓶颈或陌生遗留系统时调用本技能。融合了 `pstack` 的 `how`（真实路径追踪）与 `why`（历史成因考古），以及 Dex Horthy 的“零假设原则”，**还原真实的输入流转，杜绝基于函数名的主观臆测**。

## 核心操作规程（Process）

### 步骤 1：调用路径物理追踪（How: Follow the Data）
- 严禁阅读几个函数名就凭感觉下结论；
- 从外部入口（HTTP 请求、CLI 选项或事件监听器）开始，顺着真实的调用栈和数据流逐行排查；
- 记录关键节点的数据形态（Payload 在哪一步被改动，哪个分支被命中）。

### 步骤 2：历史意图考古（Why: Archeology）
- 遇到反常或看起来“多此一举”的逻辑时，严禁立即删掉或嘲讽；
- 运行 `git log -S <symbol>` 或 `git blame` 查阅历史提交记录与 PR 描述：
  - 了解当初为什么写成这样？是为了绕过底层 Node 的某个 Bug，还是满足某个隐蔽的业务不变量？
  - 将历史约束转化为当下的工程边界。

### 步骤 3：客观事实报告（Zero Speculation Report）
- 遵循 Dex Horthy（HumanLayer）零假设纪律：
  - 报告必须包含：精确文件路径、确切行号、调用拓扑图、实际捕获的运行时变量快照；
  - **严禁在报告结尾夹带未经证实的“我认为这么改就行”的代码补丁**，保持调查结果的客观中立。

## 反借口与典型红线（Common Rationalizations & Red Flags）

| 典型借口 / 行为偏差 | 严厉反驳与纠偏纪律 |
| :--- | :--- |
| “我看这个函数叫 `validateOrder`，那它肯定做了校验” | **不要看名字，看实现！** 很多函数内部是空的或者漏掉了分支，必须读真实代码。 |
| “这行代码看起来很不优雅，我顺手把它删了重构一下” | **严禁鲁莽！** 先查 `git log` 搞清楚当初为什么这么写，否则你是在踩别人趟过的同一个坑。 |
| “我把调查报告写完了，顺便把修复补丁代码贴在最后了” | **违背零假设纪律！** 调查者不要越俎代庖，贴补丁会先入为主误导实现者，请删掉补丁只留事实。 |
