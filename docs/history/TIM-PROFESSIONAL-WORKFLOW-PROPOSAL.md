## 一、执行摘要与问题定义

### 1.1 现状与痛点定位
在大型工程项目（如 UCBIP / ekunAi）中，多 Agent 系统的第一类问题（会话生命周期管理、任务持久化、断点恢复）已通过工作流基础设施得到了较好解决。然而，**第二类核心问题——“工程判断质量”** 日益成为阻碍高阶自治的瓶颈：
- **诊断浮于表面（Symptom Patching）**：模型遇到崩溃只在原地做空指针拦截，掩盖真实根因。
- **缺乏架构反思（Accidental Complexity）**：新功能不断追加胶水层，导致调用者理解负担剧增。
- **验证自欺欺人（Tautological Tests）**：单测逻辑与实现逻辑同义反复，以“全绿”冒充行为成立。
- **审查流于赞美或虚假报警（Sycophancy vs Nitpicking）**：Reviewer 要么顺从作者，要么为证明存在感挑刺无害命名。

### 1.2 核心解法：四层解耦与自主闭环
TIM · Professional Workflow 将软件工程能力拆分为四层正交结构：
1. **工作流层（Workflows）**：波次起止对齐、厚薄任务配方、动态越权隔离预案。
2. **角色层（Roles）**：**九大核心角色**，职责与负面边界严格隔离，杜绝单体 Agent 自审自合。
3. **方法层（Skills）**：经过实战提炼的高浓度操作配方，带确定性反馈回路与反借口表。
4. **项目绑定层（Project Bindings）**：注入具体工程事实（端口、命令、权威入口），实现“**方法全局，配方本地**”。

## 二、工具解耦与 Driver 启动期能力协商协议

### 2.1 工具解耦原则（Harness-Agnostic）
Professional Workflow 是一套纯粹的**工程思想、认知方法与角色纪律资产**，绝对不与任何特定 Harness（开发底座）强绑定。
- 在基础设施层：如 `orchestra-dsh`，仅需提供稳健的基础能力——Session 创建、归档、A2A 消息通信与打断；
- 在方法论层：Professional Workflow 负责角色职责、思考方法与交接逻辑。二者完全解耦，可随时迁移至 Codex、Antigravity、Claude Code、OpenCode 或纯 CLI 环境。

### 2.2 启动期能力协商协议（Pre-flight Capability Negotiation）
每个任务波次启动时，负责统筹的 `Driver` 必须首先探测并与 Owner 对齐当前环境的工具原语：

```
┌────────────────────────────────────────────────────────────────────────┐
│               Driver Pre-flight Capability Negotiation                 │
├────────────────────────────────┬───────────────────────────────────────┤
│ 探测维度                       │ 协商方案与装配拓扑                     │
├────────────────────────────────┼───────────────────────────────────────┤
│ 1. 会话控制能力 (Session Prims)│ • 方案 A (Herdr+Pi/DSH): Driver 调工具动态建/灭会话 │
│                                │ • 方案 B (Subagent Teams): 统一使用平台级 Subagent     │
│                                │ • 方案 C (受限 CLI): 人类协助开启 2-3 个固定终端 Pane │
├────────────────────────────────┼───────────────────────────────────────┤
│ 2. 通信拓扑 (Messaging Mode)  │ • 支持 A2A: 走精准消息派发与 ACK 确认协议             │
│                                │ • 仅单线上下文: 走 Driver 轮流调起角色文件装配模式    │
├────────────────────────────────┼───────────────────────────────────────┤
│ 3. 隔离工作区 (Isolation Mode) │ • 支持 Git Worktree: 启用物理工作区隔离与越权试验分支 │
│                                │ • 不支持: 采用单分支 Patch 快照与暂存回滚守卫         │
├────────────────────────────────┼───────────────────────────────────────┤
│ 4. 模型与算力分配 (Model Spec) │ • Driver 探测当前可用模型列表与思考档位               │
│                                │ • 协商分配: 高智/高思考模型分配给 Oracle/Architect/  │
│                                │   Reviewer; 均衡模型分配给 Implementer/Investigator  │
└────────────────────────────────┴───────────────────────────────────────┘
```

### 2.3 “说人话”铁律（Speak Human Principle）
**所有与人类 Owner 沟通的 Session，必须严格使用纯自然语言大白话，严禁输出任何技术黑话或 AI Agent 术语！**
- 严禁对人类说：“本波次触发 A2A IPC 进行 Context Compaction，并通过 AST Linter 验证 Seam”。
- 必须转换成大白话：“今晚我们会针对‘用户点击导出账单无响应’的问题进行排查。首先会模拟真实点击并检查系统后台报错，确认是数据格式问题还是网络超时，然后编写针对性修复代码并自动测试。如果发现需要修改数据库结构，我们会开一个隔离分支进行试验，不会影响当前主干代码。”
- 采用**多轮自然语言对话（Plan B）**逐步对齐，让非资深开发者也能毫无障碍地把控全局。

## 三、九大核心角色编制与“人类代理人（Oracle）”机制

为了彻底杜绝单一 Agent 既当裁判又当运动员的自欺现象，同时在过夜执行中守护人类的设计品味与业务意图，TIM 确立 **9 个标准核心角色（Separation of Duties）**。

### 3.1 九大核心角色编制表

| 角色 | 核心使命 | 核心交付物 | 绝对不应该做的事（Negative Boundaries） |
| :--- | :--- | :--- | :--- |
| **1. Driver (统筹调度者)** | 任务编排、依赖梳理、派工与人类对话（说人话） | 结构化任务卡、对外自然语言进展报告 | 包揽代码编写；代替人类擅自扩大或缩减产品核心承诺 |
| **2. Oracle (人类代理人/先知)** | 在人类离线时代表人类视角，裁决业务意图与隐式偏好 | 业务意图仲裁卡、产品取舍决策意见 | 陷入代码实现细节；推翻人类在波次启动时已明确冻结的契约 |
| **3. Investigator (调查归因者)** | 还原系统真实行为，区分事实与假说，定位根因 | 证据完备的因果诊断报告、执行路径追踪 | 顺手改代码；把“附近的报错”当根因；夹带未经证实的补丁 |
| **4. Architect (方案设计者)** | 决定接口形态、状态归属与模块边界，比较方案 | 接口与类型草案、2-3 种方案取舍对比 | 把个人偏好当契约；自动进入编码实施；制造不必要的中间抽象 |
| **5. Planner (方案切片者)** | 将设计转化为按依赖排序、可独立验证的切片 | Tracer-bullet 改动清单、验收命令矩阵 | 借拆解任务之名偷偷重新设计系统或扩大改动范围 |
| **6. Implementer (实现者)** | 在严格限定的文件与语义范围内完成变更与自验 | 代码变更（Diff）、开发自验通过的客观证据 | 超出授权范围改动无关文件；自行宣布最终业务验收通过 |
| **7. Reviewer (独立审查者)** | 独立对抗性审查，挖掘结构坏味道与安全前提 | 结构化 Findings（按机器修复与人类考量分栏） | 为了证明存在感挑刺无害代码；替作者重构整套实现 |
| **8. Verifier (独立验证者)** | 独立构造反例与真实端到端路径，证伪核心主张 | 真实环境执行日志、反例构造结果、覆盖率声明 | 绕过真实入口只测 Mock；把“测试全绿”等同于“交付正确” |
| **9. Integrator (集成者)** | 将已验证结果合入目标分支，消除意图冲突 | 集成后版本、冲突消解说明、全量回归证据 | 借合并之机插入未经审查的新改动；擅自突破发布权限 |

### 3.2 关键补充：Oracle 角色在过夜执行中的定位
在人类入睡（如 00:00–08:00）的自主运行阶段，常常会出现技术方案满足要求但“产品交互别扭”、“语义虽然跑得通但不符合用户直觉”的灰色地带。
- **Oracle 的职责**：阅读项目的长期意图文档（`CONTEXT.md`、产品定位、用户偏好），在架构师设计分歧或 Reviewer 发现体验问题时，以**“如果人类 Owner 醒着，他会怎么选”**的角度进行裁决。
- **权限边界**：Oracle 只能在启动时预先授权的业务偏好范围内裁决；如果遇到涉及商业模式变更、不可逆数据丢失或外部依赖替换，Oracle 同样必须行使挂起权，留待晨会升级。

## 四、波次起止介入、动态越权 Worktree 隔离与异常预案

### 4.1 波次起止模型（Wave Execution Model）
人类 Owner 的介入严格限制在**波次的开始与结束**两个点上：
1. **波次启动会（Wave Kickoff）**：
   - Driver 用大白话与 Owner 对齐：本波次目标、允许改动范围、预算限制、环境模型分配。
   - 确定**动态越权预案**（默认采用“隔离试验分支，不阻塞主线”）。
2. **波次运行中（In-Flight Autonomous Execution）**：
   - 团队在授权范围内**100% 自主交接与闭环推进**，绝不因为 Implementer 交付给 Reviewer 这种日常交接打扰人类。
3. **波次晨会（Wave Review & Handover）**：
   - Driver 用大白话交付成果报告：已完成并合入本地集成分支的任务、自动化测试证据、以及夜间隔离试验完成的创新方案。

### 4.2 动态越权难题的终极解法：Git Worktree 隔离试验机制
在无人值守的过夜开发中，难免会出现“原本以为是小修小补，调查后发现必须做深层架构重构”的动态越权场景。如果停下来等人类，整夜算力浪费；如果直接在主分支硬改，存在严重破坏基线的风险。
- **TIM 标准越权处理规程**：
  1. Driver 检测到当前重构方案超出了昨夜授权范围；
  2. Driver 立即命令系统开辟一条独立的 **Git Worktree（如 `worktree-isolate/<task-slug>`）**；
  3. 团队在该隔离分支上，完整完成深度架构设计、代码实现、独立审查与验证；
  4. **主干工作区不受任何污染**，继续推进本波次中其他未越权的独立任务；
  5. 晨会时，Driver 向 Owner 汇报：“昨夜发现 X 模块存在深层隐患，我们在隔离分支上完整实现了更干净的重构方案并通过了所有验证。请您审查，若符合预期我们今天一键合并回主线。”

### 4.3 零进展熔断条件（Stop-The-Line Criteria）
- 严禁同一个 Bug 在没有新证据、没有新假设的情况下无限重复打补丁。
- **熔断判据**：若针对同一故障连续两次修复均未能通过 Verifier 的反例验证，且调查没有产生新的竞争性解释，**立即停止盲目修补**。
- 将故障现场、已排除的假设、运行日志打包为挂起任务卡，释放算力推进下一任务。

                   ┌─────────────────────┴─────────────────────┐
                   ▼                                           ▼

       (例如 UCBIP 平台已有完整文档)                  (例如初创项目或小代码库)
                   │                                           │

    • TIM 任务卡 ──▶ 项目 Task Card              "发现当前项目缺少统一的决策记录和
    • TIM 决策卡 ──▶ CONTEXT.md / ADR            验证账本规范。是否允许我们为您引入
    • TIM 证据流 ──▶ evidence-ledger.md          一套轻量规范，方便后续追溯？"

## 八、对象绑定证据、三态判定与按因归属返工

### 8.1 证据严格绑定对象（Object-Bound Evidence）
任何审查与验证的 PASS 结论，必须同时锁定三个要素：
1. **被测目标的精确 Commit SHA 或 Patch Hash**；
2. **执行验证的具体运行环境配置（端口、环境变量、分支状态）**；
3. **已覆盖的范围与明确声明未检查的盲区**。
- **自动失效规则**：一旦 Implementer 随后改动了代码，或者目标基线发生移动，前序 PASS 凭据立即自动作废，不得作为合入依据。

### 8.2 三态判定机制（Tri-State Verdicts）
彻底废除简单的二元 PASS/FAIL，引入符合生产实际的三态机制：
- **`PASS`（有效通过）**：在正确环境对目标对象完成指定检查，证据确凿支持结论。
- **`FAIL`（有效失败）**：检查有效执行，且确凿证明目标未满足预期约束（明确为产品代码有缺陷）。
- **`UNVERIFIED / INCONCLUSIVE`（未完成有效验证）**：因环境故障、网络超时、缺少凭据、测试脚本自身缺陷等导致验证中断。**严禁冒充 PASS，也严禁直接断定为产品代码 Bug！** 必须先修复验证条件。

### 8.3 按因归属返工路由（Cause-Directed Rerouting）
打破“测试失败一律打回 Implementer”的错误做法，建立智能分流：
- **代码实现偏差**（未忠实兑现接口契约）→ 打回 **Implementer** 修复；
- **架构设计内在矛盾**（实现发现该接口在逻辑上不可行）→ 升级由 **Architect** 重新设计；
- **任务切片或依赖缺失**（前置前提未就绪）→ 打回 **Planner** 调整顺序；
- **验证夹具或环境损坏** → 打回 **Investigator / Verifier** 修复探针；
- **核心业务需求冲突** → 由 **Oracle** 仲裁或在晨会升级 **Owner**。
