## 二、WAVE Protocol：应该删除的是“个人运行策略的全局化”，不是自治

你对这份文件的不满有依据。

当前 `wave-protocol.md` 不只是一个过夜示例，而是自称“核心标准化运行协议”，写入了具体时间、晨会、固定交接，以及超授权任务自动进入 Worktree 完成整套设计—实现—审查—验证的流程。相同思想还被复制进 README、AGENTS、Driver 和入口 Skill。  

所以，**只删除 `workflows/wave-protocol.md` 不够**。其他入口仍会让 Driver 按同一套方式执行。

### 应留在核心库里的内容

授权范围内自行推进；交接不要求人类逐次确认；依据证据返工；无进展时停止重复尝试；超出权限时不能自行扩权；完成后准确报告已验证与未完成部分。

这些都是可迁移的工程协作原则。

### 应移出核心库的内容

几点启动、执行几小时、什么时候晨会、Owner 只能在哪两个时间点出现，以及所有范围外问题都默认完整做成一个实验分支。

这些应由本次任务的 Driver、项目运行约定或用户授权决定，而不是能力库决定。

### “越权就开 Worktree”尤其需要改写

我不反对预先授权隔离实验。问题是：

> **隔离实验本身也需要范围、预算和环境约束；创建工作树不等于获得新的授权。**

例如，代码虽然写在另一个工作树里，启动脚本仍可能连接相同数据库、使用相同凭据、占用相同端口，或者触发外部请求。Pi 官方也明确说明：工具和扩展使用 Pi 进程本身的权限，项目信任不构成工具调用沙箱。

建议统一改成：

> 超出当前交付范围时，先判断是否属于已经明确授权的实验范围。属于，则在指定隔离环境和预算内探索，结果不自动取得合入资格；不属于，则保留问题并继续无依赖的已授权任务。

**这里应该使用“预授权实验”，而不是“动态越权”。**

另外，“对人类绝对禁止技术术语”也应改成“以用户能判断的结果和后果为主，必要时保留准确技术名词”。你会直接讨论 Driver、Session、Skill 和事务边界，禁止这些词并不能帮助你决策。

## 三、Oracle：我支持保留独立判断职责，但反对当前的人类替身设定

当前 `roles/oracle.md` 的核心要求是：在人类离线时代表人类视角，根据“如果 Owner 醒着，他会怎么选”作出权威的品味与业务语义裁决。触发条件甚至包括对模糊需求产生两种业务解释。

架构提案中确实补了一条限制：只能在预先授权的业务偏好范围内裁决。这条值得保留；但角色自己的操作规程没有要求每次裁决都找到对应授权，仍然把“推测偏好”作为主要方法。

### 当前定义为什么危险？

因为它容易把三个不同的东西混起来：

**已记录的 Owner 决定、团队对既定目标的工程解释、模型猜测 Owner 可能喜欢什么。**

前两者可以支持执行；第三者最多是建议，不能自动成为批准依据。

而且，当前 Oracle 还被禁止进入底层实现细节。如果一个争议实际取决于状态所有权、事务边界或测试是否触及真实路径，禁止它读必要代码，反而会让它靠抽象语言裁决。

### 建议的定位

> **Oracle：按需调用的独立决策复核者。对竞争性技术判断、证据冲突和重要取舍提供第二意见；在明确授权的裁量范围内作出有依据的选择，不模拟 Owner 授予新权限。**

它与 Architect 的区别应该是：

**Architect 负责形成方案；Oracle 负责在值得独立复核时，检查方案、前提或争议是否站得住。**

不是所有设计都过 Oracle，也不是所有 Reviewer finding 都向它升级。

一张 Oracle 结果卡只需回答：

```text
待裁问题：
已冻结的要求与明确授权：
支持各选项的证据：
建议／授权范围内的裁决：
仍未消除的不确定性：
需要哪项最小验证：
是否涉及新增 Owner 决策：
```

它可以阅读必要代码，可以要求一个能够区分方案的实验；不能自行修改产品实现、豁免验证失败、降低验收标准或扩大权限。

**我不反对第九个角色文件，反对第九个角色被赋予“猜测人类意愿即可批准”的权力。**

### Reviewer 的分类也必须一起修

当前 P0 表示阻断缺陷，P1 表示建议，P2 表示人类／Oracle 决策；最终规则是“存在 P0 则 REJECT，否则 PASS”。 

这把**严重性、是否阻断、由谁处理**混成了一个轴。

例如，一个尚未决定的业务语义可能没有代码 Bug，却足以阻断交付；不能因为它被放到 P2，就沿着“无 P0 即 PASS”继续。

建议用三个独立判断：

**问题影响是什么；是否阻断本次交付；由谁处理。**

Oracle 的进入条件应来自“需要独立判断”，不是来自某个优先级数字。

我不建议用“八个还是十二个”直接衡量质量。真正的问题是：**每个方法是否给 Agent 增加了判别能力，是否保留了原方法的适用条件和例外。**

| `system-tracing` | **保留并扩展适用范围** | 不只服务故障；也应支持理解陌生模块。历史实现理由不是自动生效的当前硬约束。 |

| `adversarial-review` | **保留并重写结果规则** | 分离问题类型、阻断性与处理者；补未完成审查状态；坏味道不是强制产生 finding 的理由。 |
| `blast-radius-proof` | **保留并调整证明口径** | 一两个关键前提是聚焦策略，不是所有问题的上限；一次运行不能证明对所有调用者普遍安全。 |

对应内容均可在当前文件中定位。       

其中三类问题值得单独说明。

### 1. 设计方法正在奖励“表面简洁”，而不是正确封装

当前设计 Skill 要求先写两三行最理想调用，固定生成三种方案，并将某些调用顺序问题直接判为必须重新封装。

我的建议是：

**先明确调用者真实需要表达的行为和约束，再优化接口；不要把“两三行”当成设计指标。**

有些顺序本来就是领域含义的一部分。需要判断的是：这个顺序是否必要、是否明确、是否受到正确约束，而不是一律把它隐藏。

方案比较也应按不确定性触发。跨边界且存在真实选型空间时，比较结构不同的方案；局部修改已经足够时，不必为了满足模板，虚构一个“全面重构方案”。

### 2. 诊断方法丢掉了最能提高质量的几个环节

现在有工具清单、竞争性假设和重复失败后的前提检查，但缺少足够明确的：

**复现是否对应原问题；如何缩小复现；实验怎样区分解释；修复后如何回到原始场景；无法稳定复现时怎样继续。**

这些在 Matt 的原方法中都有更具体的处理，而当前版本把较多篇幅用在“禁止猜”“必须五次为什么”上。 

还有一个职责冲突：Investigator 的工作是诊断、不修改产品代码，但它挂载的方法写着“把根因修在源头”。建议方法输出**被证据支持的因果解释与下一步验证问题**；是否修改，由任务授权和实现职责决定。

**调查可以在明确说明剩余不确定性的情况下结束，不应被迫把尚未证明的解释写成“唯一真因”。**

### 3. 测试方法不能靠一个万能变异判定好坏

一个拒绝操作的负例测试，可能正是要求“不产生副作用”。把操作变成空操作，该负例仍然通过，不代表它没有价值；需要配套正例，或者注入能破坏拒绝条件的变异。

因此，建议改成：

> 针对被验证的具体要求，构造代表性的错误实现，证明测试能区分它与正确实现。

同时，测试中写明确的字面期望值并不是问题。当前反借口表把“期望值硬编码”放在被批评的示例里，容易让 Agent 避免本来很好的具体断言。应批评的是**为了追随当前实现而改期望值**，而不是字面期望值本身。

这类内容尤其值得修，因为你建立这个库，就是为了让 Agent 获得更好的判断，而不是记住更严厉的口号。

## 五、我建议新增四个方法，而不是把七个缺失引用全部补成独立 Skill

**推荐首版：一个入口＋十一个工程方法，总共十二个 Skill 文件。**

新增的四个都有明确消费者和独立产物：

| 新增方法 | 主要使用者 | 应解决什么 |
|---|---|---|
| **`planning-and-task-breakdown`** | Planner、Driver | 把目标和已确定设计变成依赖清楚、写入面明确、能够验证的任务；定义哪些工作适合垂直切片，哪些是必要的基础准备。 |
| **`real-path-verification`** | Verifier | 从应用真实入口驱动行为，核对运行身份、可见结果及副作用，处理隔离、清理、证据保留和验证未完成。 |
| **`safe-integration`** | Integrator | 核对候选与证据、区分机械冲突与语义冲突、判断哪些检查需重做，以及什么时候停止集成并退回独立审查。 |
| **`performance-diagnosis`** | Investigator、Verifier | 建立可比较基线、区分测量噪声与收益、定位关键路径、控制实验变量，并确认优化没有破坏正确性。 |

其中前三项是现有角色已经承诺、却没有落到方法文件的能力。性能方法则是现有描述明确想覆盖、但目前只被泛化诊断清单带过的能力。   

其余缺失引用这样处理即可：

**`domain-modeling`** 先作为接口与边界设计的按需参考，讲清术语、事实归属与不变量，不必立即独立成 Skill。

**`constraint-driven-development`** 归入规划方法。指标应来自用户要求、既有契约或测量，而不是 Planner 为显得专业自行发明“CPU 不得增加 5%”之类的约束。

**`incremental-implementation`** 归入行为测试和实施参考，避免两个方法重复规定同一开发循环。

**两个 Git 方法** 合成 `safe-integration`。你需要的是正确的集成交接方法，不是另建一套 Git 管理体系。

安全审查、数据迁移、并发正确性、浏览器交互验证，可以先放到相应方法的 `references/`，按触发条件加载。**不要因此再增加四个常驻专家角色。**

### Integrator 需要立即删除一条规则

当前要求“严禁使用 `--abort` 逃避冲突，必须按意图消解”。

这条与“不能在合并时搞新设计”直接冲突。

假设两侧更改反映不同的业务语义，Integrator 无法同时满足，正确动作可能就是停止当前合并操作，保留证据并回到设计／实现／审查，而不是被迫“融合”。

建议替代为：

> 能机械且无歧义地保持双方既定意图时，完成冲突处理；需要新增语义判断或改变已审实现时，形成新候选并返回相应审查。允许安全退出当前集成操作，不得以强行合并作为完成标准。

## 六、大小项目能不能交付好：关键是两条轴，而不是薄／厚两个固定队列

我认为可以共用这一套角色和方法，但需要同时识别：

**项目上下文成熟度**：有没有现成架构、测试和运行配方。

**本次变更风险**：行为是否明确、原因是否确定、是否跨边界、是否改变持久化和外部契约。

项目大，不代表每次修改都需要厚流程；项目小，也不代表状态与权限变更可以轻率处理。

| 场景 | 建议方式 |
|---|---|
| 大项目中的文案或局部展示修改 | 保留独立审查和针对性验证，不要求全仓考古、三套架构方案或全量回归。 |
| 小项目中的共享状态、认证或持久化变更 | 按高风险变更处理，必要时调查与设计，不因文件少而走捷径。 |
| 新建小项目／新功能 | 从行为目标和最小运行路径开始，不强迫 Investigator 先提交“故障根因”和历史演进报告。 |
| 大项目中的跨层迁移或性能改造 | 先建立当前路径与关键约束，尽早设计验证，再实施，并检查集成后的组合效果。 |

当前薄流程仍固定走 Driver→Implementer→Reviewer→Verifier→Integrator；厚流程则每个切片都重复完整审查、验证和集成。它们作为示例可以，但不应被当成唯一拓扑。 

**我不建议为了省成本，把你明确想分开的实现、审查、验证重新合成一个会话。** 应该省掉的是不相关的阅读、重复的全量检查、虚构的设计选项和不必要的交接材料。

还有三个具体改动：

**验证不要永远排到代码完成之后才第一次出现。** 高风险任务可以让 Verifier 提前指出怎样区分正确实现和错误实现，实施完成后再独立执行；不需要因此增加角色。

**保留固定职责，不保留无限累积的固定上下文。** 可见 pane 可以复用，但新任务、重要返工或独立审查应使用适当的新 Session，不能让一个 Reviewer 因为长期读过所有作者解释，就失去独立性。

**不要让每次基线移动都作废所有历史证据。** 当前提案写的是基线一动，前序 PASS 立即全部作废；这对串行集成会产生大量重复工作。应区分“旧对象的检查结果仍是真实记录”与“它是否足以支持新组合的合入资格”，由受影响范围决定补验。

上述能力都可以写成薄规则并接入现有 Workflow，不需要新增全局状态服务。

## 七、Driver 接入：现在欠的不是“万能自适应”，而是一条明确可跑的路径

### 1. 当前入口还不能算交接说明

`professional-workflow` 已经承担入口角色，这是合理的；但它主要要求 Driver 自行探测环境、自行适配文档、自行装配角色，没有讲清：

角色文件如何进入新 Session；路径以哪个根目录解析；必需 Skill 何时实际读取；会话身份如何确认；任务通过哪个已有通道发送；接收与交付如何对应。README 的快速导航也没有把这个入口放到最前面。 

**“Harness 解耦”不意味着“每次让 Driver 重新猜一次 Harness 怎么用”。**

我建议只补一条首版接入路径：

```text
README
  → START.md
      → 项目已有权威入口／薄绑定
      → adapters/herdr-pi.md
      → 本次选择的角色与方法
      → 项目现有任务与证据交接方式
```

`START.md` 是给冷启动 Driver 的操作入口；架构提案是设计背景，不应该成为每次启动的主执行文档。

### 2. HERDR／Pi 本身具备所需原语

HERDR 官方提供实际终端 pane、Agent 创建、读取、等待和状态识别，并支持 Pi；它还建议优先读取本机 `herdr --skill`，以获得与已安装版本一致的操作说明。:chatgpt-content-reference{index="40"}

Pi 官方支持：

**通过 `--append-system-prompt` 加入角色正文；通过 `--skill` 提供方法目录；通过命名和独立 Session 保存上下文。** 但 `--skill` 通常只是把名称、描述和路径放进可用目录，**不代表完整方法已经进入上下文**，关键方法仍需实际读取或显式调用。 

因此，装配应区分：

> **角色正文已注入；方法文件已注册；本任务要求的方法已读取。**

这三件事不能用“Agent 说自己知道了”混为一谈。

### 3. 接入命令可以很薄

下面只是根据当前官方接口整理的装配形状，**不是我已在你的机器上跑通的命令**。应先按本机帮助确认参数，并使用 HERDR 返回的真实 pane ID：

```bash
herdr agent start reviewer-a --kind pi --pane "$PANE_ID" -- \
  --name reviewer-a \
  --append-system-prompt "$KIT_ROOT/roles/reviewer.md" \
  --skill "$KIT_ROOT/skills/adversarial-review" \
  --skill "$KIT_ROOT/skills/blast-radius-proof"
```

HERDR 要求先有可用 shell pane，`agent start` 自己不创建布局；原生 Agent 参数放在 `--` 后。

真正要补充的只是：

**在目标项目／工作树启动；预检角色与方法文件可读；确认实际会话身份；通过现有通信通道下发任务；得到对应任务的接收回执；最后从产物而非 pane 的 idle 状态判断是否完成。**

如果沿用你已有的 Pi Intercom，就继续用它，不为这个库另造 A2A 通道。

同时，既然你要求可见独立 Session，入口就不能静默降级成“同一上下文轮流扮演角色”。当前入口允许这种降级，与 Reviewer 要求独立新鲜上下文的定义不相容。 

**首版把 HERDR／Pi 接通即可。没有必要同时做好所有 Harness。**

## 八、脚本和“六仓吸收”的证据：不能把声明当成交付

### 1. 版本守卫存在已复现的问题

我从连接器取回 `check-team-version.sh`，比对其 Git blob 为：

`608f50f8738975625eac63c4f2ae783cd69a7202`

然后在合成的隔离目录运行。结果如下：

| 输入／变化 | 实际结果 |
|---|---|
| 正确的顶层版本字符串 | 返回 `0`，显示成功 |
| 嵌套在 `professional_workflow` 下的版本 | 解析失败，但返回 `0` |
| 版本相同，另填错误 commit | 返回 `0`，commit 没被检查 |
| 不含版本的无关绑定文件 | 返回 `0` |
| 修改合成角色文件，版本不变 | 修改前后均返回 `0` |
| 版本字符串不同 | 返回 `2` |

它实际是一个**本地版本字符串比较器**，不能承担提案承诺的固定内容快照校验。解析不到版本返回成功，也不适合作为必需的 preflight 资格判断。

版本不同返回 `2` 是否会阻断当前工作，还取决于调用方；但直接接入 `set -e` 的前置脚本时，它会把“有不同版本”变成失败，和“固定旧版本可继续使用”的设计相冲突。

:chatgpt-content-reference{index="52"}[版本守卫隔离测试记录](sandbox:/mnt/data/tim-workflow-review/version-guard-probes.txt)

最小修正不是开发发布平台，而是分开两种检查：

**当前加载的内容不符合本轮锁定快照：失败。**

**存在更新版本，但当前快照仍符合绑定：提示即可。**

### 2. 当前远端不能证明“六仓已经深度合并”

我能核实的是：提案列了三个固定上游 SHA，以及四个外部经验源的说明；同步脚本只处理三个仓库。八个 Skill 没有逐项记录实际采用的源文件版本、保留与删除了什么，以及验证记录。  

这不说明 AG 没有调研另外的仓库；`upstreams/` 本来就被忽略，不在远端证据中。

但需要区分：

**参考过六个仓库，不等于六个仓库的重要方法已经被正确吸收。**

我建议只加一份简短 `SOURCES.md` 或映射表，每个方法记录：

```text
来源仓库、固定版本、具体文件；
保留的机制；
主动改写或删除的机制及理由；
本地对应方法；
证明改写没有破坏原意的代表性案例。
```

不需要把所有上游装进运行上下文。

这次最值得纠正的吸收方式，是把原方法压缩为“必须／严禁”之后，丢掉适用条件、实验构造和合理停止方式。**来源数量不应成为质量指标，判断能力的增量才是。**

## 九、下一轮怎么改，才能真正收口

我建议把下一轮限定为五组修改，不继续开新的大架构讨论。

### 第一组：清理范围与权威

移除当前 Wave Protocol 及各入口中的过夜强绑定；重写 Oracle；把运行规则、设计背景和历史 review 分清。Owner 已明确冻结的内容由项目权威提供，TIM 不建立第二份产品决定。

### 第二组：闭合角色与方法

修订现有七个方法和入口，新增规划、真实路径验证、安全集成、性能归因四个方法。把七个失效挂载逐项改成真实存在的目标，不用为保持旧名字而创建重复文件。

### 第三组：做通一个冷启动入口

README 明确指向 `START.md`；提供 HERDR／Pi 的薄适配说明和一份项目绑定样例。Driver 能从全新上下文完成一次装配，而不是依赖你在旁边解释“这些文件应该怎么读”。

### 第四组：修复机器能检查的问题

检查角色引用、必需文件、根目录解析和快照一致性。修正版本守卫。现有执行工具已经负责的权限、证据和集成事务，继续复用，不重新实现。

### 第五组：用少量真实任务证明行为

没有必要先建设完整 Benchmark 平台，但定稿前至少应看到以下结果：

| 验证场景 | 应当看到什么 |
|---|---|
| 冷启动接入 | Driver 从单一入口创建可见独立 Session，角色正文与必需方法确实加载，任务与回执能对应。 |
| 小范围修改 | 保留独立审查和验证，但不触发无意义的架构三案、全仓历史调查或新文档体系。 |
| 跨边界问题 | 团队识别真实的不变量／状态归属问题，并用针对性反例抓到错误实现。 |
| 原实现正确 | Reviewer 能给 PASS，不为证明存在感制造坏味道改造。 |
| 验证环境损坏 | 产生 `UNVERIFIED`，不假绿，不无依据要求实现者改产品代码。 |
| 授权或规则异常 | Oracle 不补造 Owner 决定；缺失 Skill、快照不符时不静默继续；无依赖任务仍可推进。 |

至少在两种上下文不同的项目上运行，其中一个可以是 UCBIP，另一个可以是小型 CLI 或库。比较当前做法和加入 TIM 后的结果时，尽量保持模型、工具、输入与预算一致。

这只能证明首版在代表性任务上可用，不能证明方法已经最优；但足以支持一个诚实的 V1 定稿，而不需要无限追加审查。

## 最终建议

**保留九种可选职责，不扩大角色阵容；保留七个工程方法的主体，但修正其中的绝对化规则；补齐四个确有独立用途的方法；移出 Wave 运行策略；把 HERDR／Pi 的单一接入路径真正跑通。**

当前仓库最需要的，不是更多“专业感”，而是让三个问题都有明确答案：

**角色遇到具体问题时，到底多掌握了什么判断方法？**

**冷启动 Driver 到底按哪条已验证路径把这些方法交给独立会话？**

**团队说完成时，到底有什么证据说明它解决了目标，而不是完整执行了一遍纪律？**

**这三件事闭合后，这个库就可以定稿为可用的工程能力套件；继续堆角色、来源名单和强制流程，反而会离你的目标更远。**
