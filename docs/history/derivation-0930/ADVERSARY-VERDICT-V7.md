## 2. 点 2 · 宽口径自查的豁免范围是否合适 → **不合适，且该豁免的陈述与事实不符**

driver 的说法是：「剩余命中**全部只在版本表的「原值→新值」声明行（24/25 行）**，技术正文已清。」

**我按同口径复扫，结论是这句不成立。** `grep -n -- ':368'` 命中 **2** 处：

```
25:  | **V7 = 本版** … V6-C2 第 228 行 `:368`→`:370` …      ← 版本表，属豁免

     （`:368` 是一句「未定义阶段」的报错消息，不是跳过集）。   ← ★ 技术正文，不在豁免范围
```

**第 229 行是改 2 的 S4 论证段，属技术正文，不在「24/25 行」这个豁免范围里。**

**但要说清两件事，二者不可混为一谈：**
1. **第 229 行的内容是正确的** —— 它不是在「使用」`:368` 这个错锚点，
   而是在**说明 `:368` 不是跳过集**。**没有错误的锚点被当作有效引用。**
2. **driver 那句「全部只在 24/25 行、技术正文已清」是不准确的**，
   属于**又一处范围声明与实际不符**。

### 豁免范围该怎么定 —— 我的判断

**当前豁免按「位置」划（24/25 行），这是错的划法**，理由有两条：

- **按位置划的豁免会随文件增长失效。** 今天残留恰好在 229 行所以被看见；
  下一次真正的残留若落在第 400 行，豁免不会覆盖它，而复核者若照抄
  「24/25 行除外」这个范围，就会**再次漏检**。
- **这恰恰是 driver 自己刚总结出的那个病的同型复发**：
  「**验证比被验证的窄**」。上一轮的窄是 grep 带了文件名前缀；
  这一轮的窄是**豁免范围比实际残留窄**。两次都是**用比内容窄的规则去判定内容**。

**我的候选（未经独立复核）**：豁免应按**语义**而非位置定义 ——
「**凡出现在『原值 → 新值』对账句或更正括注中的旧值，不计为残留**」，
而不是「除第 24/25 行外」。
这样规则与内容的形状绑定，文件怎么增长都不会漏。
配套的验证口径应是：**先逐处人工判语义，再统计**，而不是**先按行号区间豁免**。
