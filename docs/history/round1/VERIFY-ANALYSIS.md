## A. 6/6 是真通过还是假绿？

**结论：目标功能的核心行为与红→绿读数是真实的；“E1–E6 全通过/该角色无条件通过单注入”是假绿。** 最早的失败甚至不在六项评分表里：`roles/implementer.md:16-25` 把 `slice-plan` 列为**主收据**，`slices` 缺失则“不开工”；本轮只有 Driver `TASK.md`，没有 Planner 的 `slice-plan`（会话 JSONL 第 7 行 Driver 还特别说“没有其他角色材料，也不需要去找它们”）。实现者第 8 行直接读 `TASK.md` 并开工，没有索要 `slice-plan`，也没有生成明确的替代物；`roles/implementer.md:29-30` 将 `task-card` 列为**副收据**，不能仅靠内容相似就悄悄升级为主收据。这违反 §2 开工门，且 Driver 的第 3/4 层不得改变角色第 1/2 层边界。`closure.md:26` 的跳过切片条件是“单文件单函数，且验收判据显然”；本次改了**两个**文件（实现 + 测试），即使按这条也未证明具备跳过资格；更何况其移交只要求事后补验证判据，不负责合成完整 `slice-plan`。因此该冷启动证明“模型能做出正确的小功能”，**未证明**“只注入本角色就会服从自己的输入契约并闭环”。

**本次新增的根因候选**：正控制的 `make check` 确实能失败、实现代码当前满足小卡；假绿发生在**文本自评（E3 的边界反事实）与对象身份判定标准（E6 只比较局部两文件）比可观察证据宽**，而不是 pytest 缓存伪造读数。工具结果与我对重建基线的独立重跑一致。

## B. “身份字段无统一形态”是否真缺陷？还有哪些同类？

**基本方向对，但“从原理上无法执行”说得过满。** `roles/implementer.md:44-45,144` 只说“基线身份 / 提交对象或等价树”；`roles/reviewer.md:20-21,39`、`roles/verifier.md:20-21,34` 用 `object=(base+tree)`；`roles/integrator.md:53,109` 要核对三份身份；全库没有规定“等价树”包含哪些文件、相对路径基准、排序、字节编码、忽略目录以及相等判定。**实测例子**：同样两文件和同样 SHA，执行者的 `shasum` 文本行再 hash 得 `8fa1e21a…`，而合法的“路径 NUL + 原始 hash bytes”排序后再 hash 得 `ac2b8377…`，两者不等。这会让不同会话对同一对象给不同身份，也可让漏掉受影响文件的身份假匹配；是实际的**跨角色契约缺陷**。但一个具体会话若明确约定算法并交出所有文件 hash，Integrator 在那一次仍可按字节核对，并非逻辑上绝对不可能。

与此**同一类别**（字段名相同，内容形态或从一个步骤传到下一环所需的承重值没有契约）；下列按风险排序，避免对所有描述字段搞无意义的大 schema：

1. **切片被跳过时没有主收据**：本次已观察到 `TASK.md` 只是一张 Driver 任务卡，`roles/implementer.md:16-25` 的 `slice-plan.slices` 仍缺；`closure.md:26` 的跳过切片条件对本次两文件改动也未得到满足，而且只要求 Implementer 在 `self_verification` 里补验收判据，没规定谁把任务卡变为完整 `slice-plan`，也没让 Implementer 的 §2 接受一个明确的单片替代收据。字段既未给出实际值，也未定义降级时由谁负责合成。
2. **调查最小复现载体缺位**：`roles/investigator.md:28-38` 的 `investigation-report` 有 `coverage`、`hypotheses`，却**没有必需的复现命令、固定输入/夹具、期待错误输出或脚本路径字段**；`roles/investigator.md:154-159` 声称交“最小复现场景与回路命令”，`roles/implementer.md:121-130` 则要求直接拿它先跑红。仅凭 report 的字段存在，并不能保证实现方找得到、复现得了；`coverage` 中一句“跑过”也不是可重跑载体。应把可复制命令/输入/预期红点与其来源明确作为调查收据一部分，或指定它们属于 `coverage` 的强制结构。
3. **方案选择/批准的身份缺位**：`roles/architect.md:32-42` 的 `alternatives` 是两个形状 + 一个不改对照，§4.4 会“明确推荐”；`roles/planner.md:12,16-24` 却要求收到**已批准的设计**才能切片，`alternatives` 只写“候选与对照”，未携带选定方案 ID、由谁批准、绑定哪个冻结契约/版本。一个交来三案但无选择/授权的 `design-proposal` 在字段上完整，Planner 实际不能开工。
4. **审查/验证放行状态缺位**：`roles/reviewer.md:35-42` 交 `blocking/coverage/residuals`，但 `roles/verifier.md:25-26`、`roles/integrator.md:30-31` 只要求 `object/blocking` 等，未要求“审查已经完成且该对象明确获准晋升”的**终态**；`blocking=[]` 与“审查尚未完成/coverage 有洞、没有填 blocker”可以长得一样。`roles/verifier.md:30-39` 的 `result` 虽规定“逐主张三态”，`roles/integrator.md:16-25` 只写“三态结论”，没有主张 ID、全局 FAIL/UNVERIFIED 对晋升的聚合规则。需把未审完与无阻断明确区分，避免空列表被当 PASS。
5. **前置边的释放凭据不成形**：`roles/driver.md:45` / `roles/planner.md:36` 要求四类依赖类型，`pipeline.md:57-64` 给了各类语义，但 `dependencies` 未要求每条边的生产者/消费者 ID、所等的接口或资源 ID、解除该边的证据指针和谁接受解除。两张同为“接口冻结”的边实际可能等不同接口，字段不空也不能让 Driver 安全放行。
6. **复核实验在回程丢字段**：`roles/oracle.md:33-41` 的裁决固定有 `distinguishing_experiment`，`roles/driver.md:29-30` 副收据却只要求 `ruling/basis/undecided`，`closure.md:31,36` 的 Driver 路由同样不承接实验。表能显示 `oracle-ruling` 存在，却没保证接手人收到/兑现那条可区分选项的实验。这是本轮闭环矩阵“字段包含不等于价值传递”的具体反例。
7. **授权记录与任务卡引用关系不闭合**：`pipeline.md:128` 明订授权记录要有谁授权、对象、条件、期限、接收确认；`roles/driver.md:22,44` 的 `authorization` 只有“动作集合”，没有要求有效授权记录的标识和内容/快照。一个任务卡写了允许动作，但授权早已失效，字段仍齐备；检查器不能因此证明“每步推进前授权仍有效”。这个缺口与身份相同，必须把判定用到的对象与来源绑定起来。

### 对提出的 (a)(b)(c) 方案的判定

- **(a) 一处权威身份规范 + 无 git 降级**：**必要方向，尚不足以完整解决**。至少要明示候选文件清单/纳入依据、相对路径基准、排序与序列化、hash 算法、对缓存与测试依赖文件的处理、`base`/`tree` 的范围、`object=(base,tree)` 如何比较及读数归属哪个环境。注意**不是**要求 base 与 tree 相同：它们本来就是变更前/后的不同值。无 git 的基线还须**事前固定**，事后重建需验此前记录的 hash 并标可信等级。
- **(b) 六角色“引用那一处规范”**：若只是写“见 `identity.md`/`pipeline.md`”，则**破坏本轮“角色文件是唯一注入单元、单独注入能开工”**：除 Driver 外的角色并不保证读到外部文件，而 `pipeline.md` 明定 Driver 唯一读。可保留一份面向维护者的单一规范，但给每个接收身份的角色**内联足以独自计算/比较的短规则**，并用生成/一致性检查保证不漂移；或在四层交接中给一个已算好且带规范版本的不可变对象和核对方法，同时说明这不需要角色借第 3/4 层补自己方法的缺失。两条路线需明确选一条；不能把文件路径本身当成可执行方法。
- **(c) checker 两项**：第一项“存在唯一块 + 每个角色引用”是**结构哨兵**，抓不住错误序列化或漏扫文件；必须用无 git 夹具让“文件改一字、路径乱序、漏掉测试/运行配置、两种算法声称同一身份”等反例**实际变红**。第二项“缺了怎么办列非空”有价值但**不是这次身份错误的根因**：它只能检查表格单元格非空，抓不到一个填了“自行猜测/按最新工作区”的错误处置，也覆盖不到副收据 `字段：…` 散文格式；不能把它作为身份一致性已解决的证明。建议最小先加身份的**一个真实校验脚本与正负夹具**，再决定是否把所有输入缺失语义整理成结构化字段。

**返工定位**：候选行为问题如后续证实交 Implementer；身份/字段跨角色契约缺口先交 Architect/Driver 定规则与所有权，再由 Implementer 在授权文件内实现规范和可失败脚本、Reviewer/Verifier 独立检查。E3 的错误反事实先在探针记录更正；这不是需要修改 `pricing.py` 产品行为的证据。
