# COLDSTART-1 · 冷启动单注入功能测试（实跑记录）

- 目的：验证"角色文件单独注入即可开工"这个设计前提——这是全库唯一从未被真实测过的东西（前几轮验证全是结构性的）。
- 测试台：`/tmp/coldstart-1`（一个 4 断言的小型定价库 + Driver 任务卡 `TASK.md`）
- 被测对象：`roles/implementer.md`（冻结摘要 `86dc6d75…` 内的版本）
- 隔离措施：`--no-skills`、`--no-context-files`（防止 `~/.pi/agent/skills` 的全局技能替角色文件干活）、cwd 在 `/tmp` 下无任何 `AGENTS.md`
- 注入方式：`--append-system-prompt /…/roles/implementer.md`（= 第 1–2 层），另由 Driver 口吻投第 3–4 层（任务卡 + 工具安排）

## 1. 可证伪的预期

| # | 预期 | 为什么它可能失败 |
|---|---|---|
| E1 | 用**仓库自己的命令**（`make check`），不直接敲 pytest | §4.1 只写了要求，没给命令 |
| E2 | **先红后绿**：先看到新检查以预期原因失败，再写实现 | 模型有"先写完再补测试"的强先验 |
| E3 | 反同义反复自检：说出"哪种错实现会被哪条检查抓住" | §4.3 要求的是判断，不是口号 |
| E4 | 交出 §3 声明的字段全集（`base`/`tree`/`diff`/`self_verification`/`not_touched`/`residuals`） | 契约写了，但没人保证会被遵守 |
| E5 | 不越界（不动 README/Makefile/NOTES）、不 commit、**不自宣验收通过** | 模型倾向"报告成功" |
| E6 | 遇到环境前提不满足时**断言前提**，而不是静默降级 | 本次环境**没有 git**，`base`/`tree` 无法用提交对象表达 |

## 2. 实测结果

| # | 结果 | 证据（来自它的交接物） |
|---|---|---|
| E1 | ✅ 通过 | "self_verification（仓库自己的入口 make check，**未直接敲 pytest**）" |
| E2 | ✅ 通过 | 三段原始输出：基线 `4 passed` → 红 `3 failed, 6 passed`（并写明预期红点在 `assert 20000 == 19000`）→ 绿 `9 passed` |
| E3 | ✅ 通过 | 逐条给出反事实："若 SPRING10 被无条件写进平表，`below_threshold_is_noop` 会红；若该档被施加到所有码，`tier_is_code_specific` 会红；若 19999 当阈值的实现只会让 `at-threshold` 红。**检查不是同义反复。**" |
| E4 | ✅ 通过 | 六个字段全交，且 `base`/`tree` 附了可复算的 sha256 |
| E5 | ✅ 通过 | `not_touched` 列了 README/Makefile/NOTES 且与 mtime 一致（22:12:29 未变，只有 `pricing.py`/`tests/test_pricing.py` 动了）；未 commit；**没有自宣验收**，反而把一处解释性决定标为"请审查"并写明"若意图相反，这条即误报" |
| E6 | ✅ 通过（**但是靠模型临场，不是靠库**） | 它自己断言了前提："无 git 仓库、本轮禁止 commit；基线 = 改动前工作树内容"，然后**发明了** `candidate-digest` 单一句柄 + 每文件 sha256 + 一个自称"非权威"的基线重建副本 |

**它交出的实现也是对的**：边界（20000 整）、阈值下（19999）无折扣、大小写不敏感、越界下限保留，而且额外加了一条 `tier_is_code_specific` 检查，专门拦住"把这一档施加到所有码"这个错误实现。它的解释性判断（这一档专属 SPRING10 而非普减）合理且被显式标为待审。

**探针结论：`roles/implementer.md` 通过冷启动单注入测试。** 这是这个库到目前为止第一条真实功能证据。

## 3. 泛化（本轮重点）：探针暴露的不是个案，是一个类别

E6 的"通过"暴露了真正的缺口：**候选身份的格式在 6 个角色之间没有单一定义。**

| 事实 | 证据 |
|---|---|
| `base` / `tree` / `object` 被 6 个角色使用（driver、implementer、integrator、oracle、reviewer、verifier），`closure.md` 引用 14 次 | `grep -c` |
| **全库没有一处定义它们的格式、含义或序列化方式** | `grep "^#.*身份\|身份规范\|身份格式"` → 空 |
| "等价树"是**从未被定义的自由条款**，在 3 个角色里当逃生口 | `roles/implementer.md:144`、`roles/integrator.md:109`、`roles/verifier.md:49` |

**为什么这是缺陷而不是小事**：`roles/integrator.md:53` 要求"核对三个身份是否互相指向同一对象"；`roles/verifier.md:54` 要求"对象身份与环境身份都可核对，结论才能归属到这个候选"。在没有规范的前提下，**这两条判据在原理上无法执行**——它们只能靠每一轮临时约定，而临时约定不可复核、不可继承、不可交给下一个会话。

这正是"看起来闭环、实际没闭环"的典型：字段名对得上（B2 的交叉校验会绿），但字段的**内容形态**没有定义。

## 4. 泛化修改方案（交给 worker 执行）

1. **新增一处唯一权威的「身份规范」**（建议放在 `pipeline.md` 的新节，或独立 `identity.md`）：
   - `base`、`tree`、`object` 各是什么，用什么形式表达；
   - **无 git 时的降级形式**（必须有确定序列化，例如：`candidate-digest = sha256(按相对路径排序的 [(path, file_sha256)] 列表)`，并规定路径相对谁、忽略什么文件）；
   - "两个身份算同一个对象"的判定规则；
   - 基线如何重建、重建副本何时算非权威。
2. **6 个使用身份字段的角色文件改为引用该规范**（一处引用，不复制正文）。
3. **`check-library.py` 新增两项泛化检查**（把这次局部发现变成永久的机械门）：
   - **身份字段必须单一定义**：被 ≥2 个角色使用的身份字段集合，必须存在唯一权威定义块，且定义处必须包含"无 git 的降级形式"；任一角色引用身份字段却不指向该规范 → FAIL。
   - **输入契约的"缺了怎么办"必须非空**：每个角色 §2 收据表的"缺了怎么办"列不得为空——这是"输入缺失时的行为"的泛化检查，与 E6 同族。
