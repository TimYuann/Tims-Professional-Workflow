## 2. 逐条计划

### 2.1 C6 · 先立原则（根因，必须最先落地）

**处置**：不新增机制，只立一条可执行的库级原则，并明确它的机械可查边界。

**落点**

- `AGENTS.md`「核心原则」新增第 8 条（现在有 7 条）。
- `pipeline.md §3 不可合并的边界（硬规则）` 新增第 8 条（现在有 7 条）。
- `SOURCES.md`：登记本条为**本库自定**（依据：matt `writing-for-agents:78` 的 single source of truth + pstack `orchestrate:23/32` 的一写者与派生视图 + `principle-encode-lessons-in-structure:3` 的"第二次重复就编码进结构"）。

**措辞草案**

> **AGENTS.md 原则 8**
> **同一条规范只由一处拥有**。一条规范或一个默认值只有**一个权威位置**；其他位置只允许**引用**或**派生**，不得复写含义。为"单独注入即可开工"而必须内联的副本，必须在 `SOURCES.md` 登记它的**事实源**并与事实源保持一致；由脚本从事实源生成的派生视图不得手写。数字默认值同此规则：要么本库自定（附理由），要么显式标注为下游覆盖值。

> **pipeline.md §3 硬规则 8**
> 8. **一条规范一个 owner。** ① 事实源唯一；② 为自包含而内联的副本，登记在 `SOURCES.md` 并保持一致（结构性一致必须可机械核对，如 `identity.md` + 6 份内联规则由 G1 守）；③ **禁止同一规范在多处各自定义**——默认值可以各自漂移的那一类就是它；④ 派生视图由脚本从事实源重建，不手写。
> 边界（写进原则同段）：**语义重复不可机械检查**；机械可查的只有"结构性一致"（登记项齐全 / 副本与事实源结构相同 / 派生视图可重建）。这一层交独立审查与人审。

**影响面与新无主环节**：这是一条"约束其它规则"的元规则，不产生新的交接物、不产生新的等待。风险是它会被用来要求"删掉所有重复"，从而破坏"角色文件单独注入即可开工"（`identity.md` 的 6 份内联就是有意的）——所以措辞里必须**显式保留"登记的内联副本"这一档**，这一点已写进草案。

**生效判据**：`grep -c "只由一处拥有\|一条规范一个 owner" AGENTS.md pipeline.md` ≥2；且 `identity.md` 的 6 份内联仍被 G1 检查覆盖（回归不破）。

**反例推演**

- 场景：C4 改完后，有人觉得"审查轮次"也该写进 reviewer 自己的文件里（它确实在那里）。→ 规则判：审查轮次的**默认值**属事实源（`pipeline §7`），reviewer 文件里只能是"阈值来自本轮装配说明"这一句**动作**，不得出现数字。若有人把数字写回去，两次改动就会各自漂移——这正是 C4 的原始病因。
- 场景：有人以"自包含"为名把证据复用四条件在 `verifier §4.7`、`integrator §4.5`、`pipeline §8` 三处各自改写措辞。→ 规则判：三处中只有一处是事实源（建议 `pipeline §8`，Driver 读的那份），另两处必须**逐字一致**并把事实源登记进 `SOURCES.md`；任一处措辞漂移即违规。
- 场景：有人用这条原则要求把 6 份身份内联删掉。→ 规则明确**禁止这样做**：内联副本是"自包含"的必要代价，受登记 + 一致性检查约束，不属"竞争性定义"。

### 2.3 C5 · 数字分三类

**处置**：在 `planner §4.5` 定义三分类；改 `§5` 的禁止措辞；`architect §4.6` 与 `planner §2` 标注 `change_cost` 的性质。

**落点**：`roles/planner.md §4.5`（标题与内容）、`§5`、`§2`（`change_cost` 行）；`roles/architect.md §4.6`（判断依据）；`SOURCES.md`（登记三分类为本库自定 + 依据 addy planning 的 sizing heuristic 与 `definition-of-done:63` 的门禁形态）。

**措辞草案**

> **planner §4.5 数字分三类**（标题从"数字门禁：只从真实来源取"改为"数字分三类：门禁 / 估算输入 / 测量值"）
> - **门禁数字**（能判否、能拦交付）：只允许三个授权来源（**用户要求 / 既有契约 / CI 配置**），并且必须配一条判定命令；没有授权就只报测量值与不确定性，阈值写「待确认」。
> - **估算与判断输入**（`change_cost`、体量、波及面、候选比较）：用于**比较**与**决定切片边界**，**不构成门禁**；必须写"用途 + 依据"，允许区间与相对量；**不得转写成门禁**（例如"超过 5 个文件就不许合"）。
> - **测量值**（一次或几次读数）：只作报告，**不自动升级为门禁**；统计量先量噪声带（见 `verifier` 的噪声门）。
> 判据：一条数字要当门禁，必须能回答"**由什么命令判否、谁授权了这个阈值**"；答不出，它就是估算或测量值。

> **planner §5 改措辞**
> 「我不可以：**把没有授权来源的数字写成门禁**（估算、测量值、我的估计都不行）；发明没有来源的量化门禁指标；……」

> **planner §2 `change_cost` 行**：含义列改为「下次改动成本**估算**（判断输入，非门禁）」。

> **architect §4.6 判断依据追加一句**
> 「`change_cost` 是**判断输入**：它用于在候选之间比较、决定"下次改动要动几处"；**它不是门禁**，本库不允许把它写成"超过 N 就否决"。」

**影响面与新无主环节**：不改任何交接字段，只改语义标注。**新的无主风险**：谁审"这条数字是不是门禁冒充"？→ `reviewer §4.6` 的"阈值未定"那一类已覆盖一半，**追加一个子类**："阈值来源未授权"（判据：这条阈值有没有 Owner/契约/CI 的出处与一条命令）。这条追加落在 reviewer，不落在 planner。

**生效判据**：`grep -n "估算" roles/architect.md roles/planner.md` 能命中"非门禁"字样；`planner §5` 的禁止句从"发明量化指标"变成"把无授权数字写成门禁"；反例表里至少一条"把估算当门禁"的反例。

**反例推演**

- 场景：Architect 给 `change_cost = "5–8 个文件、2 个调用方"`，Planner 用它决定"这片太大，继续切"——合法（估算输入）。
- 场景：Planner 把它写成"本片范围 5 个文件以内，超出即失败"——**违规**（转写门禁）；正确做法是要一个 Owner 授权（"这次只许动 2 个文件"）+ 一条判定命令（`git diff --name-only` 计数）。
- 场景：CI 里已有 bundle ≤ 200KB 的门禁，Planner 在卡里重写一遍"bundle 不得超 200KB"。→ 违反 C6（同一条规范两处拥有）：卡里应写"沿用 CI 的 bundle 门禁（来源：CI 配置）"并给命令，不复制数值。**C5 与 C6 在这里相交，两条都要写进反例**。
- 场景：性能回归门（C3 §4.5 第 9 步）是门禁数字 → 必须走 `planner §4.5` 的三来源；若只是"上下浮动不超过噪声带"这种**由测量导出的规则**，它的来源是"本库自定（噪声带判据）"，必须如此标注，不得伪装成 CI 阈值。

| 字段 | 含义 |
|---|---|
| `target` | 要驱动的对象与版本（app / CLI / 服务 + 候选或环境标识） |
| `state` | `ready` / `blocked` / `not-attempted` |
| `launch` | 启动命令 + **就绪判定**（日志行 / 端口应答 / 提示符），含 teardown |
| `doctor` | **一条只读命令**回答"这个实例值不值得驱动"（进程在 / 版本对 / 端口归我们 / 凭据有效）+ 期望输出 |
| `drive` | 从真实入口驱动的方式；选择器用本仓自己的稳定标记，**不从别的仓库抄** |
| `evidence` | 证据落点与格式（截图 / 转录 / 响应体 / 读数）；**cleanup 不得吃掉证据** |
| `cleanup` | 清理命令（杀自己起的，不按进程名杀） |
| `blocked_by` | 仅 `state=blocked`：缺哪一项能力 / 试过什么 / 需要谁在什么授权下提供 |
| `scope` | 本次驱动不到的范围与原因 |

**方法草案（`verifier §4.9`）**

> **触发条件**：需要从真实入口驱动行为，而当前环境驱动不了时（启动失败 / 无凭据 / 无实例 / 无清理方式）。
> **步骤**
> 1. **先复用**：找本仓已有的 harness 或驱动入口（仓库文档的命令优先）；**不从别的仓库抄选择器、端口、脚本路径**。
> 2. **建五段**：`launch / doctor / drive / evidence / cleanup`。`doctor` 必须是一条只读命令。
> 3. **证明它会红**：让 `doctor` 在一个已知坏条件下报红；**没被证明会红的 doctor 不算就绪**（与 §4.6 反实现挑战同源）。
> 4. **端到端跑一次**：launch → doctor → 驱动**一个**真实入口 → 采证据 → cleanup；**cleanup 之后证据仍在**。
> 5. **落收据**：`state=ready` 必须附 (3)(4) 的证据指针；同一目标同一时间只有一份收据，建好交对方复用，**不得两人同时驱动同一实例**（`pipeline §5` D 类共享资源）。
> 6. **建不动**：`state=blocked`，`blocked_by` 写三件事（缺哪一项能力 / 试过什么 / 谁能提供），交 `roles/driver.md`。**不得**用截图、单测、状态注入、源码阅读冒充真实驱动。
> **判断依据**：结论的强度不超过它经过的真实路径；环境身份先于对象结论。
> **反例 / 何时不适用**：doctor 只检查"进程在"（进程活着但版本是上一轮的 → 不值得驱动）；用桩掉布局的检查判"打开即最新"。不适用：纯静态检查不需要运行环境，但仍需断言对象身份。

**三类阻塞分流（`driver` 侧）**

> 收到 `harness-receipt.state=blocked` 时按 `blocked_by` 分流：
> (a) 缺的是**本仓的一个改动**（依赖、启动脚本、种子数据、端口配置）→ 发一张卡（`goal`=可驱动面就绪；`verification`=`doctor` 命令变绿），给 `implementer`；跨边界设计先给 `architect`；
> (b) 缺的是**能力**（无浏览器 / 无凭据 / 无网络 / 无第二台机器）→ 报 Owner（附试过什么与最小代价选项）；
> (c) 缺的是**授权或对象**（写权不在授权范围、验证对象变了）→ 按 §4.4 写窗与 `pipeline §10` 授权处理。
> **环境修复若触及候选写入范围 → 候选作废，走新候选（`pipeline §6.3`），旧结论不自动延续。**

**为什么补进角色而不是新增角色**：三仓都没有环境检修角色（EVIDENCE §1.3）；环境是**状态**不是**纪律**；新增角色会造一个常驻会话 + 一套新交接，违反本库"不为没有消费者角色的需求新增抽象"（`SOURCES.md §4.9` 同理由）。**代价**：验证角色要负担建设成本；缓解手段是"先复用仓库已有 harness"（`control-ui:8`）与"只驱动一个真实入口"（`create-verification-skill:38`）。

**影响面与新无主环节**：新增 1 个交接物 + 1 条按需边，**不新增角色**。
- 新风险 1：Verifier 借"建 harness"越权改产品。→ 边界写死：**临时 harness 在临时空间（§5 现有权限内）；要落进仓库的 harness 一律走卡**；"这个改动会不会改变被验证对象的行为/交付内容？会 → 它是实现，走卡"。
- 新风险 2：两个角色都产同一份收据 → 谁是真源？→ 规则：**同一目标同一时间只有一份；先建者持写权，另一方复用**。
- 新风险 3：Investigator 等 Verifier、Verifier 等 Investigator 的死锁。→ 规则：收据只有三态；要求方**不得因等待而阻塞其他部分**（`pipeline §5` 只暂停受影响部分）；`blocked` 一律交 Driver，Driver 是唯一分流点。

**生效判据（怎么知道它生效了）**：`harness-receipt` 在全仓被 ≥2 个角色声明；字段集在 closure 的按需行与两个产出方 §3 逐字一致；checker 全绿；`grep "向 roles/driver.md 要资源" roles/` 只剩在"三类分流"的语境里（不再是唯一的下一步）。

**反例推演**

- 场景：Verifier 收到候选，app 起不来（缺种子数据）。→ 跑 `doctor` 红 → `blocked_by` 分类为"(a) 本仓改动" → 交 Driver → Driver 发卡（goal=装载种子数据；verification=`doctor` 变绿）→ Implementer 落盘 → Verifier 重跑 doctor → ready → 继续验证。**检查**：如果 Implementer 的修复改动落在候选写入范围内 → 候选身份变了 → `pipeline §6.3` 走新候选，旧审查/验证结论作废。这条必须在计划里写死，否则会出现"候选悄悄变了、结论还在用"的导管。
- 场景：Verifier 需要真实浏览器，环境没装。→ 分类 "(b) 能力" → 报 Owner，附"试过 control-ui 的复用优先与临时组装、都缺浏览器"与最小代价选项（装一个 / 换一台机器 / 改验收范围）。**不得**把它写成 `UNVERIFIED` 就结束——那正是现在"只报不办"的病。
- 场景：harness 装好后 doctor 一直绿，但验证结论一直错。→ `doctor` 的"会红"证明（步骤 3）与 Verifier §4.6 的变异（把正确实现改坏，看检查是否红）是两道不同的闸；两道都要留。
- 场景：Investigator 造不出回路，问 Verifier 要 harness，Verifier 本轮还没被装配（solo 档）。→ Investigator 自己建（它有 §5 临时空间权限）；建不动就 `blocked` 交 Driver。**不会死锁**，因为收据不是"只能由 Verifier 产"。

### 2.6 C3 · 性能诊断

**处置**：定位法补进 `investigator`；测量清单补进 `verifier`；**工具专有表一律不搬**（与已登记的删减标准一致）。

**落点**

- `roles/investigator.md §4` 新增小节（建议追加为 `§4.8 性能类症状：先建可比基线，再定位`，**不重编号**以免打乱既有落点）
- `roles/verifier.md §4.5` 追加步骤 6–10
- `SOURCES.md`：把 `performance-optimization` 那一行的"不采纳（未落地）"改为"**部分落地**：方法骨架落地在 `investigator §4.8` + `verifier §4.5`；工具专有表（Lighthouse/web-vitals/EXPLAIN/框架示例）仍不吸收"，并登记 pstack `perf-issue` 的八个策略族（可选，见下）

**措辞草案（`investigator §4.8`）**

> **触发条件**：症状是"慢/卡/占用高"，不是"报错/结果错"。
> **步骤**
> 1. **先建可比基线**：在**改动前**、用**一条命令**采一个可重复读数，同一命令同条件至少两次，记下两次之差（噪声带）。
> 2. **按症状选测量对象**（通用映射，不绑定工具）：首屏/启动慢 → 先量"阻塞在什么上"（资源体积 / 服务端等待 / 渲染阻塞）；交互卡 → 量主线程长任务或重渲染；导航后慢 → 量数据加载 vs 渲染；后端整体慢 → 量连接/池/内存/CPU；**间歇性慢** → 量锁竞争/GC/外部依赖。
> 3. **定位手段**：二分（在两个已知状态之间缩小）或差分（新旧同输入比输出）；**不用日志探针**（它改变时序且给不出分布）。
> 4. 得到机制解释后，回到**未经最小化**的原始场景重跑一次。
> 5. 交付：`repro_command` 是那条测量命令；`coverage` 写噪声带与样本数；`not_proven` 写"未测出"的部分。
> **判断依据**：没有可比基线的性能结论只是印象。
> **反例**：拿一次前后测量声称省了 13%（噪声门会拦）；在未受控环境上比冷/热缓存。
> **不适用**：症状是"结果错"而不是"慢"时走 4.1。

**措辞草案（`verifier §4.5` 追加）**

> 6. **同法复测**：处理组的测量必须与基线同一命令、同一条件（含缓存、预热、样本数）。
> 7. **中性 = 回退**：落在噪声带内不算收益；不保留"没坏处"的改动。
> 8. **一次一个**：多条优化一起落地只能得到一个数字，归因不了。
> 9. **守用户可感的那一个指标**：只给它设回归门；门禁数字的来源与命令要求见 `planner` 的数字三分类（回归门是门禁数字）。
> 10. 尝试台账（含被回退的尝试）：见 §4.8。

**不搬清单（写进 SOURCES 的"未吸收"栏，带理由）**：Lighthouse / web-vitals 调用、`EXPLAIN ANALYZE` 与索引细节、`React.memo`/`useMemo`、连接池数值、具体框架示例 —— 理由：具体语言与协议形态，违反本库"不绑定语言与协议栈"（已有同标准先例）。

**可选（默认不采纳，留给 Oracle 与 Owner 判断）**：pstack `perf-issue:8-16` 的**八个策略族**（elimination / divide and conquer / caching / indirection / batching / redundancy / lazy evaluation / scheduling）作为**假设生成器**（明确"trace 显示对应信号才启用，不当清单"）。价值：它把"猜优化手段"变成"从信号选族"；代价：正文增长、且部分族（redundancy/hedged requests）偏分布式系统。**建议：先不搬，等有真实消费者（有性能任务的批次）再评估**。

**影响面与新无主环节**：只加方法，不加交接物。**新风险**：性能任务的基线必须在**改动前**采（`figure-it-out:29`），谁负责要求？→ 现状 `planner §4.2` 步骤 5 已有"先基线后改动"，`verifier §4.1` 的环境断言已要求对象与环境可核对；C1 的 `harness-receipt.evidence` 应包含基线证据（草案里已含"证据落点与格式"），把两件事挂上即可。

**生效判据**：`investigator §4.8` 含"可比基线 / 症状映射 / 二分或差分 / 不用日志探针"；`verifier §4.5` 含"同法复测 / 中性=回退 / 一次一个"；SOURCES 那一行从"不采纳"改为"部分落地 + 未吸收清单"。

**反例推演**

- 场景：Verifier 收到"这次 CPU 降了 30%"的主张。→ 先看基线（同命令同条件、≥2 次、噪声带）→ 落在带内 → 报"未测出"，不记收益也不记损失；若实现改了 → 回退（中性=回退）。**检查**：回退会动候选吗？不会——回退由 Implementer 在新候选里做（Verifier 不改实现，`§5` 边界）。
- 场景：性能问题只在生产偶发，本地复现不出。→ 按 `matt diagnosing-bugs:53` 的路径：停手、列出试过的方式、点名要"能复现的环境 / 脱敏的现场材料（profile、trace、"（可选）临时插桩许可）"；这不是 `UNVERIFIED` 一句话，而是一份具名请求（可与 C1 的 `harness-receipt.blocked_by` 合并表达）。
- 场景：一次改动里既修了 bug 又做了优化，测量变好。→ "一次一个"判：不能归因；要么拆成两次，要么只声称"合在一起更好"，并写明未分离。

> ### 4.9 推进前：用纯自然语言讲清楚（硬规则）
>
> **触发条件**：在向下推进任何工作之前——发第一张卡、开写窗、并行派工、进入长跑、换批次。
>
> **步骤**
> 1. 向 Owner 讲清六件事：① **做什么**（结果的形状，一两句，不用术语）② **为什么现在做**（与 Owner 目标的关系）③ **动什么**（文件/目录/系统，以及明确不动的）④ **代价与风险**（时间、轮次、可能的返工、不可逆点）⑤ **不做什么**（明确排除项）⑥ **怎么算成功**（Owner 自己能观察到的表现）。
> 2. 按规模给三档重量：机械低风险项一句话；常规任务半页；跨边界、长跑、高代价给完整六要素。
> 3. 自查一句：Owner 能不能用**他自己的话**把这六件事复述出来？做不到 = 没讲清（不是他没听懂）。
> 4. 讲完即推进。**这是陈述，不是审批门**；只在三种情况停下来等：授权缺失或授权变更、不可逆动作、Owner 明确要求确认。
> 5. Driver 由 Owner 亲自承担（`solo(1)`）时，"讲给他听"退化为"写下来"——仍是必做动作。
>
> **判断依据**：没有讲清的推进，是让 Owner 在下游用返工来发现上游的假设。
>
> **反例 / 何时不适用**
> - 反例：用"重构一下""优化一下""补一补"当解释——它们没说动什么、代价是什么。
> - 反例：把解释写成审批请示，每次动手前等回复——这会把 Owner 变成瓶颈（与"可逆工作不阻塞"冲突）。
> - 不适用：无。机械项可一句话，但不省略。

**与 §4.1 的分工（交叉引用措辞）**：`§4.1` 步骤 5 末尾加——「（**要问的**决定见本节；**动手前要讲的**事见 §4.9。两者不重复。）」

**记录形式**：六要素摘要用 `scripts/log-decision.sh` 写一行（阶段=`推进`，决定=摘要，为什么=`推进前解释`，证据=消息指针/时间），使"讲没讲"可回溯。**备选（更重）**：新增 `advance-brief` artifact → Owner（六字段 + `state`）。代价综述：新 artifact 要接 closure/拓扑/checker（约 4 处改动），收益是"每份推进都有独立收据"。**建议先用 ledger 行；如果 Oracle 或 Owner 要求可机械追溯，再升级为 artifact。**

**影响面与新无主环节**：不改交接字段、不动档位表。**风险 1**：与 `§4.1` 的"Owner 确认之前不动手"看起来重复 → 已用交叉引用与分工句隔开。**风险 2**：与 `never-block` 冲突 → 已在步骤 4 写死"陈述非门 + 三种情况才停"。**风险 3**：变成仪式（每次写六段废话）→ 三档重量 + 反例里点名"把解释写成审批请示"。

**生效判据**：`grep -n "4.9 推进前" roles/driver.md` 命中；六要素齐；`§4.1` 有交叉引用；反例表里有一条"用'重构一下'当解释"。

**反例推演**

- 场景：Driver 要发第一张卡（小改动，单文件）。→ 一句话："把 X 文件的 Y 改成 Z，动 1 个文件、无风险、不动别处，成功 = 你能看到 Q"。讲完即发卡，**不等回复**。
- 场景：Driver 要开一个跨边界长跑（改权限模型）。→ 完整六要素（含不可逆点与轮次预算）；由于"改变权限语义"命中高风险，**同时**触发独立复核（`pipeline §2`）——两条规则叠加，不冲突。
- 场景：Owner 看完解释说"不对，我要的不是这个"。→ 停止推进、改卡；这是 §4.1 的 frontier 变更，走重新对齐。**不改变"讲完即推进"的默认**（否则每次都要等回复）。
- 场景：Driver 用术语写了一堆（"对 identity 做一次 rebase 后的 tree 对齐"）。→ 违反"不用术语替代事实"（`AGENTS.md` 原则 6，引用不重述）；Reviewer/Owner 都可据此打回。
- 场景：某轮任务很急，Driver 想跳过。→ 步骤 5 与"不适用：无"使它无法跳过；但机械项只要一句话，所以代价趋近于零。

## 5. 明确不做 / 代价与残留

1. **不新增角色**（C1/C2 都不）。代价：真相是"可驱动面"的建设成本落在验证侧；若某类项目几乎每次都要重造 harness，本方案会暴露这个成本，而"新增常驻环境角色"会把它藏起来。这是有意的选择。

3. **不设"最多几轮"的通用上限**（C4）。代价：不同活动的停止语义要靠"三个量"的命名来区分，读者要多读一张表；收益是默认值只有一个 owner。
4. **C2 的写权默认给 Architect**。代价：无 Architect 的装配里多一次指定动作；备选（谁解析谁写 + 写窗）会把共享状态暴露给多写者，不推荐。
5. **C7 不新增 artifact（第一版）**。代价："讲清楚了"的第一版证据是一条 ledger 行 + Owner 收到的消息，不是独立收据；若需要可机械追溯，按 §2.7 的备选升级。
6. **`check-library.py` 不重写**。代价：它仍是 879 行、26 项检查的体量；本轮只改"它的位置"（从门降为维护者工具）与"它的预算规则"，不改实现。若 Owner 认为体量本身就是问题，需要在下一轮做一次"删检查"的清单（每条附"它拦下过什么"的证据，没有证据的删）。
7. **残留风险（如实标）**：
   - "为过检查而改措辞"这类自欺，机械层拦不住，只能靠报告必须附证据指针 + 独立复核。
   - C4 的装配参数若长期不写，角色会一直走"本库默认"，实际值可能长期与项目现实不符——这需要 Driver 的装配说明被纳入收口检查（本轮只写规则，不加机械门）。
   - C1 的收据在真实底座上是否可行（临时空间、浏览器能力）未验证。
   - `SOURCES.md` 新增"事实源 ↔ 内联副本"登记会让 145KB 的台账再长一点；本轮只登记新引入的两处（`harness-receipt` 的双产出方、C4 的两个量），不追溯登记全部既有重复（作为已知欠账）。
