## 2. 实际发生了什么（按时间）

1. **`f-driver` 自发发来《推进前说明》**（未被我提示）——六要素齐：做什么 / 为什么现在做 / 动哪里不动哪里 / 代价与风险 / 怎么算成功 / 怎么组织；并写明"**授权已获且可逆，说明已送达，我据此开工；这不改变「授权仍是你的」**"。它主动标出一处不确定处（金额单位是分还是元）让我确认，按证据判定 500 元 = 50000 分——**正确**。
2. **Driver 自己补了缺件**：在 scratch 里产出 `slice-plan.md`（含 slices/dependencies/verification/scope/stop_condition 全字段）、`contract.md`（冻结契约 C1–C10）、`task-card-f-impl.md`（含 auth_record）、决策台账、base/tree manifest。**三份收据一起交给作者侧。**
3. **`f-impl` 回接收确认**："三份收据读全、auth_record 有效、未发现停止项"→ 写窗移交 → 开工。**它的 §4.0「开工前收据核对」执行了。**
4. **红→绿在 mtime 上可见**：`tests/test_pricing.py` 16:18:06 先改，`pricing.py` 16:18:23 后改。
5. **第 1 轮独立审查**：`state=complete`、无阻断、C1–C9 全 PASS；审查方**独立复现了"改动前预期会红"**，并自造 **5 个变异体全部杀掉**（比例折扣 / 写错等号 / 漏大小写 / 平铺进字典 / 去掉非负钳制）。
6. **审查方发现 Owner 的验收口令不合格**：一个**写错的「按 3% 减」实现能让 `make check` 全绿**。→ Driver 让作者侧补一条把额度钉死的测试（51000→49500、50850→49350），**只动测试文件、实现一字未动**。
7. **对照实验（本轮最硬的证据）**：

8. **Driver 主动披露一次范围放宽**：它把 `.pi/**` 从"不得改动"名单移出，改称"运行时状态、不纳入源码身份"。**是 f-review 先抓到的。** 现场核过：`.pi/loops/loops-*.json(.prev)` 6 个文件会变，写它们的是**编排机制自己**；逐条比对全项目清单后**除两个白名单文件外其余源码逐字节未变**。
9. **第 2 轮重新冻结**：`tree=ws:v1:1a3756d9…1e35`；`pricing.py` 逐字节未动。Driver 要求 **f-review 独立复现，不采信 f-impl 的转述**。
10. **旅程级验收**：在冻结版本上跑 9 条真实下单路径（不到 500 / 刚好 500 / 509 / 600 / 三种大小写 / 两个老码 / 乱码）→ 9/9 通过。

## 5. 库级发现（4 条，交 Oracle 复核）

### 发现 1 · 没人复核"验收口令"本身够不够
**现象**：Owner 给的验收口令 `make check` **分不出"定额减 15 元"和"按比例减 3%"**——一个合理但错误的实现能让它全绿。
**谁发现的**：审查方的变异实验，**顺手**发现的。
**为什么算缺口**：库里那条「判据必须能失败」**只长在 Reviewer / Verifier 身上**。但任务卡 `verification` 字段里的验收口令是 **Owner 或 Driver 给的**，它没有过门。**这次被验的不是实现，是 Owner 给的标准。**
**待判**：这道门该长在谁身上？

### 发现 2 · 没有 Planner 的批次里，切片缺口由谁补（文档自相矛盾）
**现象**：`closure.md` 的跳过行说 **`roles/implementer.md` 在候选里补写验收判据与验证命令**；**实际行为是 Driver 补成一份正式 `slice-plan.md` 当主收据**。
**我的判断**：**实际行为更好**（closure 的写法等于让作者侧自己给自己写验收标准，气味很近"实现者给自己发验收单"），**应改 closure.md**。
**待判**：我这个判断对不对？

### 发现 3 · `identity.md` 的排除清单漏了"编排运行时会写的路径"
**现象**：任何真实会话都会往被测目录写运行时状态（`.pi/loops/**` 等），而 `identity.md` §2 的排除清单只有 `.git/**`、缓存、构建产物、`__pycache__`、`.pytest_cache`。后果：算身份时漂移 → 要么误判"对象变了"，要么逼执行方临时放宽范围。
**性质**：**真实使用中必然遇到**，不是测试台偶发（我把会话 cwd 设在被测目录放大了它）。
**待判**：补进排除清单时，怎么定"该排除哪些、不许泛指"的规则？

### 发现 4 · 没有证据保管规则
**现象**：判断侧冻结的判据 **C9 按路径引用了 `/tmp/f-review-probes/`**（对照副本、变异读数、688 点扫描）。删掉它，C9 就失去锚点。
**执行方自己指出的根因**：*"判据引用了 `/tmp` 这种易失路径，等于**可复现性没有跟着判据一起冻结**；写证据指针时必须同时固定保管位置。"*
**我核过的现状**：库里关于证据只有两条——`verifier.md` 要求台账里"证据指针能解析并确实支持该行"；`integrator.md` 复用旧结论要"记录可取回且运行有效"。**没有任何一条说证据该放哪、谁保管、删除前做什么、易失路径算不算合格位置。**
**性质**：**判据说"可复现"，而复现材料没有保管规则** → 真实项目里"字面可复现、事实取不回"。
**待判**：这是"加一条规则"还是"加一个保管者"？（后者要动角色表）
