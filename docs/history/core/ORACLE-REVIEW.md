# 核心闭环计划 · 思路审查

**结论：方向对了一半，但不建议照现有顺序直接实施。** C1、C2、C3、C7 都在补真正缺失的工作能力；C4/C5 有必要澄清；C8 可以瘦身。问题是计划把 C6「一条规范一个事实源」说成八项的共同根因，又先做一批规范和台账治理，再解决真实任务里的“谁来让它跑起来、谁有权定词义、谁能把结果交给 Owner”。**环境没人修是没有行动负责人，不是同一规则写了两份；性能方法和推进前说明也不是重复定义造成的。** C6 是维护纪律，不是这些缺口的因果解释。若照原顺序推进，很可能又出现“规则登记完毕，真实任务仍卡住”。

## 1. 新增环节有没有主人？

计划已给出一些名字，但**“有产出方”不等于“有人负责把阻塞解除并保证结论仍有效”**。我看到五个具体洞：

1. **环境的建造者同时给自己的装置发 `ready`。** C1 允许 Verifier/Investigator 建临时 harness，再由同一个人证明 doctor 会红、交 `ready`。这不一定违反“实现候选者不得判断候选”——测试装置不是产品候选——但当装置本身决定唯一的验收读数时，自证一次只能说明它抓得住**那个**坏条件，不能说明它接的是正确版本、正确账户、正确数据。计划要规定：普通临时探针可由使用者自建并注明证据等级；**进入仓库、触及凭据/共享数据、或成为唯一放行闸的 harness**，走候选→独立审查/验证，不由造装置者替自己判最终可用。不能把“一次 doctor 变红”写成装置普遍有效。
2. **双产出方没有确定的写权分配。** C1 说 Investigator 与 Verifier 谁先建谁持写权；两者可能同时调查同一故障，或拿着不同候选/数据状态的“同一目标”各交一份收据。先完成者不是授权者。Driver 发卡时应先指定该实例的建设者与受影响写面；`harness-receipt` 至少绑定**候选/运行环境身份与有效条件**。环境、种子数据、服务版本变了，由 Driver 重新定建设/复核人，旧 `ready` 不自动可复用。C6 的“事实源唯一”不能替代这项派工决定。
3. **环境改动后谁重新验原来的主张仍不明确。** C1 的种子数据例子只说：改到候选写入范围就换候选。但即使只改端口、依赖版本、配置或测试数据，代码树没动，运行条件也可能不等价；旧证据同样不能直接沿用。Driver 应令原 Verifier 在新环境**重跑原始失败观察与目标用户路径**，按 `pipeline.md §8` 判断哪些证据可复用。`doctor` 变绿只证明可驱动，不证明原缺陷已修。
4. **术语写者不等于术语决定者。** C2 让 Architect 负责“冲突即裁、立刻写回”，却没有说谁有权决定 Customer/User 等**业务含义**。代码、词汇表和用户说法冲突时，三者可能分别是错的，并不天然是二选一；Architect 可查证和提出备选，**领域 Owner/获授权的业务负责人**决定产品含义，Architect 才写回。若项目没有 `CONTEXT.md`，先映射其既有事实源；没有文档体系时创建新词汇表也要 Owner 同意，不能用“懒创建”绕过授权或造第二事实源。无 Architect 的批次由 Driver 指定**记录写者**，不能顺带赋予业务裁定权。
5. **性能归因与改动的交界没有明确交接。** C3 给 Investigator 定位、Verifier 测量，但优化假设由谁选、改动由谁做、噪声带内的结果由谁决定回退？应沿现有链：Investigator 交基线/竞争解释与覆盖范围 → Planner 定可否证判据 → Implementer 只改一个因素并形成新候选 → 独立 Verifier 同条件复测；回退也由有写权的 Implementer 形成**新候选**，不是 Verifier 操作。没经授权的性能目标只能报“未测出”，不能擅自把一次测量或噪声带升级成产品门槛。

**另外一个脚本层的新洞**：C8 删除版本检查后写“交回下游”，但没指明**哪个下游绑定负责人**会定义版本+内容快照格式、何时接手。在下游没有协议的现状，这可以作为公开的“当前未提供漂移检查”，不能同时宣称两层同步仍可核验。

## 2. C6 能不能当根因、能不能守住？

**不同意把它当八项共同根因；同意把它当防复发原则。** C4 同一类阈值多处定义、`identity.md` 与角色副本可能漂移，适合用 C6 解释；C1 是缺操作责任，C2 是缺业务决策权，C3 是主动省略方法，C7 是没有在推进前沟通——即便所有文字只有一处，这四个洞仍在。

它能被守住，但只能**分层**守：明确“谁有权决定”“哪份是规范”“谁有写权”“哪几份是为单角色注入而派生的副本”。对真正必须逐字相同的副本，可以生成或作确定性对照；变换过措辞的角色方法，靠修改时列出受影响位置、独立方对照真实情景。PLAN 自己承认语义重复无法靠词面门可靠判断，这是对的。**不要把 G1 的关键词检测当作六份身份规则语义一致的证明**；前几轮已见过“marker 齐而字段含义相反”。更不宜把所有重复都登记进 145KB 的 `SOURCES.md`：它的职责是来源与吸收，R4 又已经有 Owner 授权的 Ledger Custodian 负责生成落点。先只登记**高风险的有意内联**及其事实源，复用现有 custodian 的工作，不另建一套通用“重复注册表”。

C6 草案本身要先解开一个矛盾：一面说数字默认值只在 `pipeline.md §7`，一面 C4 又要求 Reviewer 保留数字 **2**，角色单独注入时还说“缺装配说明就用本库默认”却不知道默认是多少。不能三件都要。建议：若“角色文件单独注入即可开工”是硬要求，**安全上限应在该角色文件内可执行**，维护者事实源与角色内联之间做生成/一致性核对；Driver 第 3 层只能按授权调整**工作预算**，不能默默放宽防止无限补丁/自我放行的边界。否则应诚实承认角色必须依赖 Driver 的第 3 层，向 Owner 请求修改原注入契约。C4 的“两轮=一修一确认”是本库的**选择**，不是从三仓推导出的普遍定理；Reviewer 的审查轮次、同前提补丁停手、造不出回路三件事别共用一个可覆盖的计数器。若允许把“同一前提两次失败就停”覆盖到 10 次，等于用装配参数取消了这条纪律。

## 3. C8 的进退是否正确？

**同意删除无人消费、只比版本字符串的 `check-team-version.sh` 的方向，但须连同“目前没有下游快照核验协议”一起对外说明。** 它的 0 退出容易造成错误安全感，不能因为历史上有脚本就把它算能力；而“角色里没引用脚本”也不是删留判据——维护脚本本来就未必由角色直接调用。`sync-upstreams.sh` 属维护者工具，`identity-selftest.sh` 属开发回归工具，各有现成用途。

**同意保留 `check-library.py`，明确它只是维护者的结构回归工具；不同意现拟的门预算。** “新增检查必须有一次拦下**真实**错误的历史，否则删”会淘汰预防性检查、鼓励为了保门制造一个人造事故。较好的入门条件是：说清**具体受保护的断言**，给一个会红的正反对照，证明不会误伤常见合法变体，标明运行/维护成本与负责人；无区分力或高误报才删。结构工具全绿绝不是工作流可用的验收结果，但 879 行也不会因为改称 dev-only 就自动变薄；下一次该审**每类检查的价值/误报/维护成本**，删掉无用项，而不是把更多元规则塞进 checker。

PLAN C8 提议让 `roles/verifier.md §4.8` 直接点名 `scripts/log-decision.sh`，这里与本轮已定的“**角色文件仅能跨文件引用 `roles/*.md`，Driver 额外可读 `pipeline.md`**”冲突，也会让单角色注入依赖一份未保证存在的脚本。保留角色内 append-only **方法**，把调用脚本的具体命令放到 Driver 附加的工具层，或先请 Owner 明确扩大注入/引用许可；不要为了证明一个工具被消费而破坏角色自包含。

## 4. 这是补核心闭环还是补基础设施？

**C1/C2/C3/C7 是核心能力，原计划的实施顺序和验收方式却明显偏向基础设施。** 它把 C6、轮次、数字治理放第一批；C1 提一份九字段新收据、双产出方、按需表和拓扑；C8 再审八个脚本。每批的完成条件仍是 checker、台账生成与落点，**没有一条“拿一张真实的缺环境/术语分歧/性能回归卡，能否从阻塞走到可交付结果”的验收情景**。这样做完很可能是“文件都能互引，项目仍要靠 Owner 临场救火”。

建议改顺序与粒度：先请 Owner 定 C7 的“讲清楚”是**每批启动前**还是**每次具体动作前**，并明确授权未定时必须停；然后用三个纸面但具名的工作情景贯穿 C1/C2/C3：① 缺种子数据的服务如何从 blocked 到同一目标的有效验证；② 一个业务词冲突如何得到有权者裁定并进入下游实现；③ 性能慢如何先有基线、找到机制、改一个因素、同条件复测并决定留/撤。只有沿现有 `task-card → investigation-report/design-proposal → slice-plan → candidate → review/verify → integrated-baseline` 链发现真实缺的一环，才增加字段或 `harness-receipt`；如果现有阻塞说明 + Driver 一张环境修复卡就能闭合，先不加九字段收据。C4/C5/C6 是使已有规则不打架的**伴随整理**，不应成为大波次的入场仪式；C8 最后做删留裁决即可。

## 5. 对计划作者六个问题的直接回答／Owner 需定的点

- **C1 独立性**：临时 harness 自建可接受，但“我造且自测会红”不等于独立认可；变成唯一闸或仓库持久实现时必须另有人审。更关键是环境改动后旧验证证据的资格归谁判、谁重跑原主张。
- **C4 注入**：当前“数字只在 pipeline、角色缺装配则用默认”的文本不足以单独注入开工；要么角色带受控且可核对的安全默认，要么明确申请改硬契约。不可把可覆盖轮次用于取消停手边界。
- **C7 陈述/审批**：已授权、可逆工作可以**先送达解释再推进而不等批准**；需要产品决定、授权变更或不可逆动作仍等明确许可。PLAN 的“Owner 能复述”若不等回复，无法作为完成判据；自写一行 ledger 也不证明 Owner 收到消息。至少保留实际送达的消息/交接指针，发送失败不能声称“已讲清”。不能把“一句话、无风险”用于未经核对的改动。
- **C8 保护损失**：删 `check-library.py` 会失去角色结构、死链、字段对照和身份夹具的可重复预警；它不是唯一验收闸，但应保留。删版本脚本要明说尚无快照核验消费者与协议。
- **C2 写权**：Architect 可以是**默认文档写者**，不是业务意思的批准者。无 Architect 时 Driver 指定单写者并先核对 Owner 授权与项目既有文档位置；“只 append、由读方合并”会把冲突推给多个读者，反而没有裁决者。
- **C6 登记成本**：只为确实需要多份内联的承重规范登记映射，优先借已获 Owner 授权的 Ledger Custodian 维护，不把所有相似句子逐条登记。没有人能靠“语义重复不可机械查”宣称 C6 自动生效。

**Owner 应在实施前明确三项决定**：① C7 的“任何工作”粒度与“送达解释≠同意执行”边界；② C4 安全停手上限能否被项目覆盖，以及角色单注入优先于默认值单一书写哪一个；③ C8 删除版本脚本后，哪个下游负责人在什么绑定格式确定时接回内容快照核验。未定这些，PLAN 的某些“已闭环”仍只是换了一个地方等待人。
