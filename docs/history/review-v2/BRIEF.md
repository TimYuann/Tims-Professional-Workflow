## 零 · 我们最初的目标（这是判断「做得好不好」的标尺）

我们不是要做一个新的编排器。我们已经有一套跑得不错的多 agent 编排：
终端工作区管理 + 会话间消息收发 + 自己的 DAG 逻辑，能完成整页的工程推进。

**我们做这个项目，是因为质量不够好。**
具体表现为：agent 在开发过程中反复犯那些「只要有更高阶工程经验就能避免」的错误。

我们明确**不要**：
- 直接引入三个上游开发者中某一位的整套架构（它不匹配我们现有的流程）
- 一个新的调度器 / 编排器
- 与具体工具绑定的任何东西

我们要的是：**把三份被验证过好用的公开方法库里的工程经验，提炼成一套可以按任务体量
动态装配的工作流内核。** 阶段只规定判据，角色是可装配件，技能按需取用，
工具怎么调度完全交给装配者当场决定。

判定做得好不好的标准只有一条：**它能不能让 agent 不再犯那些本来可以避免的错误。**

## 轴二 · 自洽性：吸收之后是否咬合

这是本轴的重点：**逐个 agent、逐个 skill、逐个脚本地查**。

被审文件：

```

workflow/phases/P0..P6.md  7 个阶段契约（生成）

skills/*.md                49 个技能
principles/*.md            23 条原则（7 个文件）
scripts/check-closure.py  scripts/check-consistency.py
scripts/render.py          scripts/ledger.sh

```

**你要查的是：**

2.1 **上下闭环咬合**。九个角色、七个阶段、四十九个技能，横向怎么咬、纵向怎么咬？
    具体查：某个角色的技能清单里的技能，是不是真的在它该出场的阶段被用得上；
    某个阶段需要的产物，是不是真的有人产出；某个产物的字段，是不是真的有下游在读。

2.2 **49 个技能逐个查**。每个都要问：
    - 它的「方法」一节是不是**可执行的具体步骤**，还是换句话说了一遍注册表？
      **如果一个技能的方法一节里出现了你从没在上游正文见过的、本身正确但无出处的内容，
      标为 `FAIL` 并附上位置。**（这是「凭空发明」与「提炼」的分界，是本轴最关键的一条。）
    - 它的「产出」一节里引用的字段名，是不是和注册表 `artifacts` 段逐字一致？
    - 它有没有违反「技能文件不内联角色纪律」这条？

2.3 **九个角色逐个查**。每个角色问：
    - 它是不是**自包含**的？单独注入一个会话，只读这一个文件，够不够开工？
      如果必须先读别的文件才知道自己该干什么，就是 `FAIL`。
    - 它的「我不做的事」和它的技能清单是否自相矛盾？
    - 它声称的产出，是不是真的由它产出？

2.4 **两个检查器是不是摆设？** 自己造故障注入进去：
    改坏注册表、加一个游离文件、造一句互斥的话、删一条处置，
    看 `check-closure.py` 和 `check-consistency.py` 会不会红。
    **如果注入后它们仍然全绿，这是本次验收最严重的发现。**

2.5 **本库的检查器自己有没有内建漏洞？** 逐条读 `check-closure.py` 和
    `check-consistency.py` 的判定逻辑，找「看起来在检查，实际检查不到」的项。

2.6 **`render.py` 的生成区**是否真的能防住手改？改动一个生成文件，`--check` 会红吗？

## 五 · 你的工作方式（重要）

- **逐个查，不要抽样。** 轴二明确要求逐个 agent、逐个 skill、逐个脚本。
- **每一条结论都要有 `file:line` 或可复现的命令。** 「感觉写得不错」不是结论。
- **区分三种状态**：`PASS` / `FAIL` / `UNVERIFIED`。
  环境问题、能力不足、读不到 → `UNVERIFIED`。**判 `UNVERIFIED` 不可耻，判错才可耻。**
- **不要因为被审方自己的检查器全绿就认为它是对的。** 那 15 项检查只证明结构没塌。
- **先自己读 `docs/history/` 里的旧版材料**，理解它为什么会变成现在这样——
  然后你才知道现在这样是不是真的解决了问题。
- **你的怀疑是默认状态。** 每看到一个「好」的设计，先问：
  它在什么情况下会失效？谁在什么时候会因为它而卡住？
