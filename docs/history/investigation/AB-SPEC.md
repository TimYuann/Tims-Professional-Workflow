# A/B 文档体系映射规格（Owner 口述，逐字锁定）

**来源**：Owner 2026-09-27 口述。本文件是**设计输入**，不是方案。任何下游设计（investigator 取证 / Oracle 方案 / Driver 实施）以本文件为准。

## 1. 两个集合的定义

| 集合 | 定义 | 每项必须带的信息 |
|---|---|---|
| **A** | **workflow 中可能产生的所有类型的文档** | **产出方** + **产出环节** |
| **B** | **目标仓库**（下游使用这套 workflow 的仓库）其文档体系中包含的所有文档 | **什么时候写** + **由谁来写** + **发生在什么时候** |

## 2. 三种情况

### 情况 1 · B 是空的或非常薄
- **做法**：询问 Owner 后，**把 A 直接搬进 B**；再把 B 现有的文档**按 A 的标准做移植**。

### 情况 2 · B 已有一套比较厚实的文档体系
- **做法**：**映射**——看 A 的项与 B 的项能不能一一对应。
- 能对应上 → **Driver 修改它在这个项目中运行的文档体系**，形成 **adaptive 版本**。
- Owner 举的例子：A 这边是小写 `a b c d e f g`，B 文档组里是 `1 2 3 4 5 6 7`，那么可能 **a→3、b→2**。
- **Driver 要发挥主观能动性**；**不要指望三个上游仓库能有这个问题的答案**（Owner 判断：大概率没有）。

### 情况 3 · B 比较扎实时的可选路径
- 若 **Owner 同意**把 B 按 A 的方式改造（认为 A 的体系更科学、更好），**也可以做这种改造**。

## 3. feature map 的定位（Owner 定）

- 这套 workflow **必须有完整的"建立 feature map"的能力**——**完整**指：生成、维护、防腐烂。
- **由 Driver 根据当前面对的项目判断**（当前尺寸 / 预期达到的尺寸），**达到一定程度就建议 user 建立 feature map**。
- **建立过程应当与 `grill me` 那套很相似**（即：对话式、按 frontier 一轮轮推进，不是填模板）。
- **它不是"不做就不能开工"的东西**——是**可选项**，但**能力必须完整存在**。

## 4. 自我适用（Owner 定）

- 搭建文档体系的**过程中**，**要把本库自己的文档也按同一套标准优化**。
- **本库自己就是最好的实验场。**
