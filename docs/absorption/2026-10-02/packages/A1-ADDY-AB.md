# G1 · 编排与组合纪律

## G1.1 机制、触发情境、源锚、已读/尚缺

**机制**：把多方参与（多个判断位点、多个实例、多个视角）当作一种**有成本的工程选择**来管理——先判定是否需要编排，再判定用哪种形态，并给形态配上反模式、准入条件与"不值得编排"的判据。

**触发情境**：一个任务需要不止一个视角／不止一个产物；或同一个组合会重复出现；或有人想引入"总调度"式做法。

## G1.2 操作、成立条件、失败模式、反例

**操作（去平台化后可转移的部分）**

1. **先做不需要编排的判定**（模式 1）：单一视角、单一产物、能用一句话说清 → 直调，不做编排。该模式被明确指定为"应当始终与之比较的基线"。
2. **只把真正的独立子任务并行**（模式 3）：判据是"无共享可变状态、无次序依赖、每个参与者产出**不同种类**的发现、合并步骤小到能留在主上下文、等待时间确实可感"。任一不成立则退回直调或单视角形态。
3. **有次序依赖时保持人工按序**（模式 4）：由需求方按序推进，不做"LLM 生命周期编排者"；上游给出的三条理由是可转移的工程理由：转述导致步骤间丢失细节、跳过本应拦住方向性错误的人工检查点、每一步的转述使 token 成本翻倍。
4. **读多回小时用隔离读**（模式 5）：只在"消费方能保持专注、结果远小于输入、决策质量受益于消费方留有余地"时使用；上游要求"先看宿主是否已内置只读检索者，不要自造"。
5. **深度与合并位置**：编排深度至多 1（命令/用户 → 参与者），**合并在主实例**，叶子参与者不得再编排。
6. **加新组合形态前过四条准入**：真实用过至少两次；能指出一个具体产物证明它；能说明既有形态为何不适用；能说出别人会误建成的反模式形态。原文的判据句："Premature catalog entries become aspirational documentation that no one follows."
7. **重编排前满足跳过条件**（`ship.md#Rules` 第 5 条）：仅当"改动文件数 ≤2 **且** diff <50 行 **且** 不触及 auth／payments／data access／config-env"三条**同时**成立才可跳过；否则默认编排；爆炸半径非平凡时即使 diff 很小也要跑并行评审。

**成立条件**
- 各参与者**真实独立**（上游用"平台强制"与"作用域优先级"表达；我方对应 Backbone 的独立性属性）。
- 合并者握有比每位参与者更多的上下文（上游："merge step 小且受益于完整上下文"）。
- 每个参与者产出的是**不同种类**的判断，而不是同一发现的不同角度。
- 参与者不共享可变状态。

**失败模式与反例（上游逐条给出失败机理，可直接作为判据）**

| 反模式 | 失败机理（源文要点） |
| --- | --- |
| A · 路由器人格（meta-orchestrator） | 纯路由层无领域价值；两次转述 → 信息丢失 + 约 2× token；需求方本可直接调用被路由者；重复了入口层已有的映射 |
| B · 人格调用人格 | 单视角设计被破坏；调用方转述丢掉被调用方需要的上下文；失败模式相乘（谁的输出格式/规则生效）；成本对需求方不可见 |
| C · 转述式顺序编排者 | 丢失人工检查点；每次交接都做摘要 → 长链条累积漂移；每步双份 token；在最需要判断的地方移除了人的代理权 |
| D · 深层人格树 | 每层增加时延与 token 而无决策价值；排障变成多层调查；叶子因多次摘要丢上下文 |

**例外（上游自己保留的例外，吸收时必须保留）**
- 平台强制是"天然豁免"：宿主已禁止参与者再生成参与者、禁止嵌套；因此 A/B/D 在某些宿主上"构不出"而不是"不该建"——**判据仍是判据，不因平台拦截而免于写出**。
- 结构性 fan-out（模式 3）**只**在 `/ship` 一处被背书，并被明确写为"本仓唯一背书的多角色编排形态"。
- `web-performance-auditor` **被明确排除**在 `/ship` 扇出之外，理由是非 Web 项目会产生噪音（`agents/web-performance-auditor.md#Composition`）——即"编排成员资格按适用面裁剪"，不是"名单越长越好"。

## G1.4 我方当前正文、已覆盖、具体缺口

**已覆盖（确切段落）**
- `profiles/driver.md` §心智模型末条：「组合失效信号（权责冲突、真实独立性受损、注意力跨度损害专业深度）出现时拆分或补能力，**不建固定 Role matrix**。」
- `profiles/README.md` §选择规则：「一次任务可以只调用一个或两个预设…**选择预设 ≠ 授予权限**」；「组合使用时，若权责冲突、真实独立性受损，或注意力跨度损害专业深度（责任基线 §6），拆分实例或补充能力；**不以"戴不同的帽子"解决**。」
- `charters/README.md` §Rules：「**Choosing a Profile is composition, not authorization**」；「the package intentionally has **no schema validator or general permission engine**」。
- Backbone §6「实例组合与最短调用」、§4「Voice 与 Driver：连接责任，不吞掉责任」。

**具体缺口（逐条）**
1. **没有反模式目录**：我方只有"组合失效信号"一句与"拆分/补能力"动作，没有命名反模式 + 失败机理 + 成本 + "反而应做什么"。实际后果：重复出现的错误组合（总调度式入口、转述式串联、多层树）只能靠现场重新论证。
2. **没有准入条件**：想新增一个组合形态或新方法时，我方**没有**"用过两次 / 有一个具体产物 / 能说明既有做法为何不适用 / 能说出它的反模式影子"这四条判据。这一条同时是我方"不建 registry/框架"纪律的**配套**：它是防膨胀判据，不是新平台。
3. **没有深度与合并位点的判据**：深度 ≤1、合并在主实例、叶子不得再编排——我方无对应表述。
4. **没有并行前检查表**：4 问（能否无次序问题同时执行 / 是否各产出不同**种类**的发现 / 合并是否装得下 / 省下的等待时间是否可感）。
5. **没有"不值得编排"的条件式判据**：我方有"已有适用结论可直接复用"，但没有"同一视角单一产物 → 直调；组合不重复出现 → 不做固定组合；有次序依赖 → 人工按序"这组判据，也没有"人工按序优于 LLM 编排者"的三条理由。
6. **上下文保全式隔离缺失**：我方的拆分信号只有责任/独立性/注意力；上游的"读多回小 → 隔离读、只回 digest"是**上下文经济**理由，可作为第四条信号（不改变责任放置）。

**为何值得吸收**：这六条全部是**判断判据**而非流程节点，与我方"不要无适用条件的 ceremony"一致；同时它们直接服务 Driver 的核心 concern（谁上场、要不要多实例、合并谁做），且能在不引入平台机制的前提下使用。

## G1.6 可讨论正文草稿 + 验证方案与边界（未执行）

**草稿（候选，供 gate 改写）**

> ## bounded composition（按需方法草稿）
>
> **Use**：当一项工作看起来需要不止一个视角，或同一个组合反复出现，或有人提出"设一个总调度"时。
>
> **判据（先答前面，答完再决定要不要组合）**
> 1. 是不是一个视角、一个产物？是 → 直调，不做编排。
> 2. 这个组合会不会重复出现？不会 → 临时直调，不做固定组合。
> 3. 参与者之间有没有次序依赖或共享可变状态？有 → 由需求方按序推进，不要设"生命周期编排者"（理由：转述丢细节、跳过人工检查点、每步双倍成本）。
> 4. 各参与者是否产出**不同种类**的判断？否 → 合并为一次判断。
> 5. 合并者是否握有比每位参与者更多的上下文？否 → 先在主实例补齐上下文。
> 6. 是否需要读大量材料而只回流一小段结论？是 → 隔离读，只回 digest。
>
> **形态边界**：深度至多 1；合并在主实例；被组合者不得再组合（叶子不得扩大参与集）。
>
> **边界例（来自一个具体仓库语境，仅作例）**：某次改动 ≤2 文件、diff <50 行、且不触及 auth／payments／data access／config-env 时，可跳过并行评审；否则不做这个判断，直接跑。爆炸半径非平凡时，diff 小不是理由。
>
> **何时允许新增一种组合形态**：真实用过至少两次；能指出一个具体产物；能说明既有形态为何不适用；能说出别人会误建成的反模式形态。四条不全 → 先作为 issue/线索，不写成方法。
>
> **已知失败形态（不要内置）**：只做路由而不做判断的入口；被组合者自行调用被组合者；由 LLM 逐步转述的整条流水线；多层嵌套树。

**验证方案（未执行）**
- 机械核：草稿中每条判据能否在不点名任何宿主/模型的前提下读懂；是否出现命令名、工具名、专有开关（若出现，即为耦合残留）。
- 情境核（需另行授权才能执行）：给 3 个既有任务（单一视角任务、重复组合任务、有次序依赖任务），只看草稿能否得出与源文一致的形态选择；只做形态选择判定，不执行被选形态。
- 边界核：确认草稿**不**产生"必须编排"，也不产生"禁止编排"；两向都要有例。

**边界（必须写进正文的否定句）**：本方法不产生参与者名单、不产生权限、不产生独立性结论；它只回答"要不要多视角、用哪种形态、谁合并"，独立性仍由 Charter 与真实贡献记录判定。

## G2.2 操作、成立条件、失败模式、反例

**操作**

1. **意图→能力映射表**：以"用户会怎么说"为准（"功能/新功能""规划/拆解""缺陷/失败/意外行为""代码评审""重构/简化""API 或接口设计""UI 工作"），而不是以能力名称为准。
2. **宿主无命令层时的隐式生命周期映射**：把 DEFINE→PLAN→BUILD→VERIFY→REVIEW→SHIP 映射到能力，并明确"这不是命令别名，而是执行者内部必须走的序列"。
3. **执行模型的偏向条款**：每条请求先问"是否有任何能力适用（即使 1% 可能）"，命中则绑定；且**不得部分套用**（"Always follow the skill instructions exactly (do not partially apply them)"）。
4. **反理性化清单**：把执行者自己的话列出来并逐条否定——"这个太小不需要方法""我可以直接快速实现""我先收集一下上下文"。
5. **最小集与按需集**：给出"最小三件套"（定义/证伪/评审）与"按阶段加载"，并明确**不要**把所有能力一次性加载（浪费上下文、稀释该起作用的）。
6. **多条最小路径的示例**（缺陷修复只需 3 个能力的序列），并明确"不是每个任务都需要每个能力"。
7. **并行/串行的注记**：序列中标注哪个能力与其他步骤**并行**而非其后（上游把观测能力标注为与实现/对抗复核并行）。

**成立条件**
- 映射表要以**触发词**为键（否则路由不到）；这正是上游 Tier-2 触发评估要测的东西（"描述是否包含用户真正会说的词汇"）。
- 决策树要有**负向分支**（"还没有想清楚要什么"→ 访谈能力；"不适用"→ 明确指向别的能力）。
- 偏向条款必须配"不得部分套用"，否则偏向绑定会退化成"提一句就过"。

**失败模式与反例**
- **路由表多处存放 → 漂移**：同一映射在本 pin 内至少 9 处出现（`AGENTS.md`、`CLAUDE.md`、`README.md`、`using-agent-skills`（决策树 + 生命周期 + 速查表三处）、`docs/cursor-setup.md`、`docs/opencode-setup.md`、`docs/getting-started.md`、`docs/adoption-guide.md`、各命令 frontmatter）。**已观察到的实际漂移**：能力计数在 README/CLAUDE.md 为 25，而 `.codex-plugin/plugin.json` 的 longDescription 写 24（本包复核 pin 后确认该差异仍在）。
- **只写正向映射**：没有"什么时候**不**用"，会让相邻能力互相抢触发（上游用 `trigger.negative` + `owner` 断言来处理；这是 EF 族的机制，本包只记边界）。
- **反理性化清单被写成说教**：上游把它放进能力正文（运行时被读到），而不是放进贡献指南。

## G2.6 可讨论正文草稿 + 验证方案与边界（未执行）

**草稿（两段，供 gate 取用）**

> **（a）适用性存疑时的默认（Driver 段）**
> 命中明确触发时直接路由。适用性存在专业歧义时，不要沉默跳过，也不要自行判定"不适用"：先绑定该判断（写入本次 Charter 的 `Applicable methods`）并写明你据以认为它触发的条件；若你确实认为不适用，把"不适用"作为一条**待确认结论**交回拥有该判断的责任方，附理由与依据。绑定即按其正文的条件与步骤执行——**不得只取其中一句当口号**，因为条件就是内容的一部分。
>
> **（b）跳过借口的最小清单（Profile 常见误区段，改写自源文表的形态）**
> - "这次太小，不值得按方法走" —— 小是规模判断，不是适用性判断；规模从来不是适用条件。
> - "我先做起来，边做边补" —— 先做会产出没有依据的结论，之后补的是解释而不是依据。
> - "现在我大概知道怎么做" —— 那正是适用条件命中时的状态，不是免于执行的理由。
> - "以后一起清理" —— 延后很少发生；要么现在处理，要么记成一条明确交给某人的未决项。

**验证方案（未执行）**
- 机械核：草稿中不出现任何具体方法名以外的机制名；"不适用"路径必须落到"交回拥有该判断的责任方"而不是"由执行者裁定"。
- 一致性核：草稿的"不得部分套用"与 Charter 现有 `Applicable methods` 字段说明、以及各方法 §Limits 的"not a universal gate"不冲突（前者约束执行方式，后者约束适用前提）。

**边界**：本组不产生新的责任位点，不改变"方法是条件化操作"的既有立场，也不把上游的"1% 即调用"照搬为强制条款。

## G3.2 操作、成立条件、失败模式、反例

**操作（逐条，含源文的具体判据）**

1. **批准标准（先设标尺）**：在"确实改善整体代码健康"时批准，即使不完美；不要因为"不是我会写的方式"而阻断；若改善且遵循项目约定 → 批准。反面：把评审当成"改到作者满意"。
2. **五轴 + 每轴的**具体探针**（不是口号）：
   - 正确性：是否匹配 spec/任务；边界（null/空/边界值）；错误路径；测试是否真的在验证；off-by-one、竞态、状态不一致。
   - 可读性/简洁：命名是否描述性（禁止无上下文的 `temp`/`data`/`result`）；控制流是否直白（不要嵌套三元、深回调）；"更少的行能否做到"（1000 行能做 100 行是失败）；抽象是否在挣得复杂度（第三个用例再泛化）；**死代码残骸**（`_unused`、向后兼容垫片、`// removed` 注释）；**新条件被焊到不相关的流程上 = 设计异味而非 nit**；**同一形状的重复条件 = 缺模型/缺分发器**（"临时分支通常是永久债"）。
   - 架构：是否遵循既有模式，新模式的正当性；模块边界；重复；依赖方向（无环）；抽象层级；**"这次重构是减少复杂度还是只是搬移复杂度？"**——判据是"读者必须同时持有的概念数"，数不变就不更干净；优先让**分支/模式/层消失**的重构，而不是重新集中同一批逻辑；**是否把特性逻辑泄进共享模块**；类型边界是否显式（质疑无谓的 `any`/`unknown`/可选/断言与掩盖不变量不清的静默回退）。
   - 安全：边界处校验；密钥不入代码/日志/版本控制；认证授权；参数化查询；输出编码；依赖来源与已知漏洞；**外部数据（API/日志/用户内容/配置文件）一律按不可信处理**，并在边界处校验后才进入逻辑或渲染。
   - 性能：N+1；无界循环/无约束取数；该异步的同步操作；多余重渲染；列表端点缺分页；热路径里的大对象。
3. **结构性补救要给"动作"而非"问题"**（8 条命名动作）：把条件链换成类型化模型或显式分发器；合并重复分支；把编排与业务逻辑分开；把特性逻辑移到拥有该概念的包；复用既有规范 helper 而非近重复；让类型边界显式化以消除下游分支；删除只增加间接性的直通包装；抽 helper 或拆文件。总原则："优先选能**减少活动部件**的补救，而不是把同样的复杂度摊开。"
4. **变更规模判据**：~100 行改动=好；~300 行=若属单一逻辑变更可接受；~1000 行=太大，拆。**同时看文件规模**：单文件约 1000 **总**行是"常见观察信号，不是硬上限"；改动显著增长已很大的文件时，先问"是否该先抽 helper/子组件/模块"——**先分解，再加**。"一次变更"的定义：单一自包含改动、只解决一件事、含相关测试、提交后系统仍可用（是特性的**一部分**，不是整个特性）。四种拆分策略（Stack / 按文件组 / 水平 / 垂直）各配适用时机。大改动可接受的例外：删除整文件、自动化重构（评审者只需核对意图而非每一行）。**把重构与功能分开提交**（小清理如变量改名可由评审者裁量并入）。
5. **变更描述规范**：首行短、祈使、可独立检索（"Delete the FizzBuzz RPC"）；正文说"改了什么、为什么"、含代码里看不到的上下文/决定/理由、链接缺陷号或基准或设计文档、**承认方案的不足**；反模式词表（"Fix bug""Fix build""Add patch""Moving code from A to B""Phase 1""Add convenience functions"）。
6. **评审顺序（5 步）**：先理解意图（这个改动要达成什么/实现哪个 spec/预期行为变化）→ **先看测试**（有没有、测行为还是实现、边界、命名、能否抓住回归）→ 逐个文件过五轴 → 分级 → **验证作者的验证故事**（跑了什么测试、构建是否通过、是否手工验证、UI 有无截图、有无前后对比）。
7. **分级 + 作者动作语义**（源文表）：*无前缀=必改*（合并前必须处理）；**Critical**=阻断合并（安全漏洞、数据丢失、功能损坏）；**Nit**=次要可选（作者可忽略）；**Optional/Consider**=建议（值得考虑但非必须）；**FYI**=仅供知悉。并配两条排序纪律：**按杠杆排序**（正确性/安全在前，结构性回归与漏掉的简化次之，其余在后）；**"若你有一个结构性问题与十个 nit，那个结构性问题就是这次评审"**。
8. **多模型评审形态**（A 写 → B 审正确性与架构 → A 处理 → **人做最终决定**），配一段可直接用的评审提示词（把 spec 与预期写进去，要求按分级标注）。
9. **死代码卫生**：找出 → 明确列出 → **问过再删**（给出 `DEAD CODE IDENTIFIED:` 模板），"不要留下死代码，也不要静默删除你没把握的东西"。
10. **评审时延与过载**：一个工作日内响应（是**上限而非目标**）；典型变更一天内多轮；优先快速单次回应而非快速终审；**大改动要求作者拆分**而不是硬审。
11. **分歧判决序**（四层）：技术事实与数据 > 风格指南（风格问题的绝对权威）> 软件设计（按工程原理而非个人偏好）> 代码库一致性（若不降低整体健康则可接受）。并且**不接受"我以后再清理"**——要求提交前清理，除非是真紧急；确有周边问题不能本次解决的，要求**开单并自派**。
12. **评审中的诚实**：不橡皮图章（"LGTM"而无评审痕迹毫无价值）；不软化真实问题（把会打到生产的缺陷说成"小顾虑"是不诚实）；**尽量量化**（"这个 N+1 会让列表每项多 ~50ms"优于"这可能有点慢"）；对有明显问题的方案直言并给替代；**接受合理推翻**（作者有完整上下文时从其判断）；"评论代码，不评论人"。
13. **依赖纪律**：
    - 新增依赖前 5 问：既有技术栈能否解决（通常能）；依赖多大（看包体影响）；是否活跃维护；有无已知漏洞；许可是否兼容。规则："**优先标准库与既有工具**；每个依赖都是负债。"
    - 升级依赖**按变更评审**：**读 changelog 而不是只看版本号**（semver 是维护者的承诺，不一定信守；主版本要读迁移说明并找出破坏点）；**一次一个依赖**（批量 bump 出问题就丢失了归因，单包变更让原因与回滚都干净）；**让测试裁决**（升级由绿测试前后夹住，而不是"装上了"；若围绕该依赖行为的覆盖很薄，**那个缺口才是真正的发现**，先补测试）；**看传递依赖图**（审 lockfile diff 而非只看 `package.json`）；**让 lockfile 诚实**（提交、审 diff、绝不手改——lockfile 才是真正钉住发布内容的东西）。
14. **评审清单与结论**：Checklist（Context/Correctness/Readability/Architecture/Security/Performance/Verification/Verdict）+ 结论二值（Approve / Request changes）+ 评审后的 Verification 检查（Critical 全解；Required 全解或明确延后并有正当理由；测试通过；构建通过；验证故事成文；依赖升级按上述五条核过）。
15. **"假定阻断项"（presumptive blockers）**：重构只是搬移复杂度而未降低；改动把文件推过规模边界且未分解；特性逻辑加进共享模块；既有规范 helper 的近重复；掩盖不变量不清的静默回退——**处理方式是"显露并提出更简单的设计"，只有在该改动确实使结构变差时才升级为 Required**。

**成立条件**
- 评审者必须拿到 **spec/任务描述**与**变更意图**；否则只能审风格。
- 分级必须**带作者动作**（否则作者把全部反馈当必办）。
- 结论只有二值（批准/要求修改）；"有条件批准"由 Required 项承载。
- 评审是**针对具体变更与版本**的判断，不是对作者的评价。

**失败模式与反例（源文明确列出）**
- 只看测试是否通过就批准（忽略其他四轴）。
- 无严重度标注的评论 → 作者分不清必办与可选。
- 大 PR"大到没法好好审"（应当要求拆分）。
- 缺陷修复 PR 不带回归测试。
- 接受"以后修"（源文断言"以后永远不会来"）。
- 只搬移复杂度、不减少读者需持有概念数的重构被当成"更干净"。
- 新增依赖/批量 bump 跳过 changelog 与逐包隔离；lockfile 被手改或未提交。
- **词表漂移的实例（本 pin 内实际存在）**：`skills/code-review-and-quality/SKILL.md#Step 4` 用「无前缀/ Critical / Nit / Optional / Consider / FYI」，`agents/code-reviewer.md#Output Format` 用「Critical / Required / Optional / Nit」，`.claude/commands/review.md` 正文要求「Critical / Important / Suggestion」，而插件评估的机器判据 `evals/plugin/code-review-fires/graders/severity-labels.md` 的正则只接受 `Critical|Required|Nit|Optional|Consider|FYI`。**后果**：按命令层产出的 `Important`/`Suggestion` 标签不被该判据命中（只有 `Critical` 有交集）。这是一个可直接引用的"同一分类多载体 → 漂移 → 下游不可用"的失败案例。

## G3.6 可讨论正文草稿 + 验证方案与边界（未执行）

**草稿（候选正文骨架，节选最缺的三处）**

> ## 变更评审 · 按需方法草稿
>
> **Use**：当一个具体变更需要进入主线、且需要一个非作者的判断时。产出是**证据判断 + 分级发现 + 批准/要求修改建议**；它不授予合并、发布、风险接受或关闭许可。
>
> ### 顺序
> 1. 先要意图：这个变更要达成什么、实现哪条已接受约定、预期行为变化是什么。拿不到意图，只能审风格——把这一点当缺口说出来。
> 2. **先看测试**：测的是行为还是实现；边界是否覆盖；测试名是否描述性；若代码改了这些测试会不会变红。
> 3. 逐文件过五轴（探针见附录）。发现按杠杆排序：正确性与安全在前，结构性回归与漏掉的简化次之，其余在后。**一个结构性问题加十个 nit，这次评审就是那个结构性问题。**
> 4. 每条发现带分级与作者动作（必改 / 阻断 / 可忽略 / 建议 / 仅供知悉），并**尽量量化**（"列表每项多 ~50ms"优于"可能有点慢"）。
> 5. **核作者的验证故事**：跑了什么、对哪个基线、构建是否通过、有无手工/界面验证。记录与本次代码不符的验证声明。
>
> ### 结构性问题要给动作
> 条件链 → 类型化模型或显式分发器；重复分支 → 合并；编排与业务逻辑 → 分离；特性逻辑 → 移回拥有该概念的包；近重复 helper → 复用既有规范 helper；类型边界 → 显式化以消除下游分支；直通包装 → 删除；过大文件 → 先分解再加。
> 判据是"读者必须同时持有的概念数"：数不变就不是更干净。
>
> ### 规模
> ~100 行改动可一次审完；~300 行需是单一逻辑变更；~1000 行应拆。单文件总行数接近四位数是**观察信号，不是上限**：改动在长大文件时先问"是否该先分解"。
> 重构与功能分开提交。大改动可接受的两种例外：删除整文件、自动化重构（核对意图即可）。
>
> ### 分歧
> 判决序：技术事实与数据 > 风格指南 > 工程原理 > 代码库一致性。
> 不接受"以后再清理"：要么本次清理，要么开一条明确交给某人的未决项。
>
> ### 依赖
> 新增前五问：既有栈能否解决 / 多大 / 是否活跃维护 / 有无已知漏洞 / 许可是否兼容。优先标准库与既有工具。
> 升级按变更评审：读 changelog 而非只看版本号；一次一个；让测试裁决；看传递依赖；lockfile 提交且不手改。
>
> ### 边界
> 本方法产出判断与建议，不产出合并/发布/风险接受许可；结论只有"批准"或"要求修改"两种建议形态。分级词表由方法正文唯一持有。

## G4.2 操作、成立条件、失败模式、反例

1. **产物即交接**："同一个产物就是会话之间的交接"——把工作带向前的是**获批的文件**，不是对话。小任务一个会话跑完；非平凡工作按阶段各起新会话以保持上下文聚焦。
2. **切换前必须落到产物上的五类事实**：仍然适用的决定、已批准的范围、仍开放的问题、下一个任务、当前验证状态（**跑了哪些测试、对什么跑的**）。
3. **新会话进入时的动作**：先读**实际文件**并看 `git status`；**不要假定你看不见的批准**。
4. **把"已记录的通过"当作对特定基线的 claim**（本组最可操作的一条）：
   - 触发重跑的三条件：代码自那以后移动过；记录没说"对什么跑了什么"；你即将触及它所覆盖的区域。
   - 不触发的默认：基线仍成立就直接接续，**做与改动成比例的检查，而不是每次交接都跑全量**。
5. **可重启边界由什么构成**：逐任务的状态更新、验证结果与提交，使每个已完成任务成为一个可重启边界；外部 harness 可以从那里退出并恢复而不依赖对话历史。（原文同时给出两条边界：**进程退出不是任务通过的证据**；**重启不得绕过批准闸门**。）
6. **活文档纪律**：`SPEC.md`/`tasks/plan.md`/`tasks/todo.md` 是进行期的工作产物——开发期入库以便人与执行者有共同真源；范围或决定变化时更新；若仓库不想长期保留，合并前删除或加入忽略。
7. **隔离读（digest-only）**：当消费方要保持专注、且结果远小于输入（读 50 个文件回一段摘要）时，把"读"隔离出去只回结论。

**成立条件**
- 交接产物本身必须**是**工作产物（spec/plan/状态），而不是为交接另写的总结——否则出现第二份真源。
- 恢复点必须可被另一实例**按材料**重建（与我方"结果能否被另一个会话按材料复现"同构）。

**失败模式与反例**
- 以对话历史为交接（上下文丢失后无法重建，且产生"我们上次说好了"式的不可核主张）。
- 把"进程正常退出/收到结束信号"当作任务通过。
- 用"重启后继续"绕过原本未获的批准。
- 把已记录的"测试通过"当作对**当前**代码的结论而不问基线。
- 交接产物写成第二份真源（与 spec/plan 不一致的"交接总结"）。
- 新会话凭记忆假定上游批准存在。

## G5.2 操作、成立条件、失败模式、反例

**操作**

1. **对照表（四行判据）**：范围（一个任务/每个增量）；是否变化（每项不同/固定复用）；回答什么（"做对了没有"/"够不够格算完成"）；owner（规划该任务时定/项目层定义一次）。
2. **合成规则**：任务完成 = 本次验收条件满足 **且** 常备门槛满足；跳任一个都会得到"看起来完成但其实没有"的结果。
3. **常备清单五段**：正确性（验收条件达成；**在运行时验证过，不只是编译/类型通过**；新行为有能在改动前失败、改动后通过的测试；既有测试仍通过无回归；边界与错误路径）；质量（命名与结构自证意图；无重复业务逻辑；无死代码/调试输出/注释掉的块；改动限于任务范围、无顺带重构；lint/format 通过）；集成（与系统其余部分协同；迁移/配置/开关已计入；公共接口变更考虑向后兼容）；文档（公共接口与用户可见行为有文档；值得保留的架构决定有记录；文档描述的是当前状态而非变更史）；可发布（不可信输入/认证/数据安全已评审；新关键路径有观测；有回滚路径；合并或部署前有人类评审）。
4. **按层应用**：每任务查正确性+质量；每特性查集成+文档；每发布用全表为底线并叠加发布专项。
5. **稳定性纪律**：项目层裁剪**一次**后原样复用；"每个 sprint 重新谈判的门槛不是门槛"。
6. **红旗（可直接作为负向判据）**："做完了，只是还没跑"（未验证的工作不算完成）；"测试过了"被当成完成的同义词而跳过文档/回归/运行时验证；按截止压力换标准；把验收条件当作全部门槛（没有常备质量底线）；在需要人评审的变更上先宣布完成。
7. **"单调不减"判据（取自采纳指南末条）**：每次引入门槛后，被强制的东西不应回退；自检问句——"过一段时间后，你能说出现在被强制而过去没有的是什么吗？"说不出即为停滞。

**成立条件**
- 门槛必须在项目层有**唯一 owner**（否则每次重新谈判）。
- 门槛必须是**可判定的**（清单项要能回答"怎么算满足"，否则退化成口号）。
- 门槛与验收条件的**归属不同**：验收条件来自 A/B 对本次任务的约定；门槛来自项目层质量政策。

**失败模式与反例**
- 把验收条件当成全部门槛 → 通过验收但不满足质量底线（源文红旗第 4 条）。
- 每次重新谈判门槛（尤其在有压力时）→ 门槛失去意义。
- 用"测试通过"代表完成 → 覆盖不了文档、回归与运行时行为。
- 把门槛写成不可判定的清单（"代码要干净"）。
- 门槛由实现者自己定义并自己判通过（我方独立性问题：门槛的**内容**可由项目层定义，但**本次是否满足**仍由有独立性的评价给出）。

**草稿（候选正文骨架）**

> ## 常备质量门槛与本次验收条件（按需方法草稿）
>
> **两句区分**
> - **本次验收条件**：随任务变化，回答"我们做的是不是对的东西"。由本次任务已接受的约定给出，规划时定。
> - **常备门槛**：对每个增量都相同，回答"它够不够格算完成"。在项目层定义一次，之后原样复用。
>
> 一个任务算完成，是两者**都**满足；只满足一个，会得到"看起来完成但其实没有"的结果。
>
> **常备门槛的五段（每段配判定问句与判定者）**
> 1. **正确性**——验收条件是否达成？**是否在运行中验证过，而不只是编译或类型通过**？新行为是否有"改动前会红、改动后会绿"的测试？既有测试是否仍绿、有无回归？边界与错误路径是否处理？
> 2. **质量**——命名与结构是否自证意图（不需要注释解释"它在做什么"）？有无重复的业务逻辑？有无死代码/调试输出/注释掉的块？改动是否限于本次范围、没有顺带重构？项目自己的 lint/format 是否通过？
> 3. **集成**——是否与系统其余部分协同而不只在隔离下成立？迁移、配置、开关是否已计入？公共接口或 API 变更是否考虑向后兼容？
> 4. **文档**——公共接口与用户可见行为是否有文档？值得保留的架构决定是否已记录？文档是否描述**当前状态**而不是变更史？
> 5. **可发布**——不可信输入、认证、数据处理是否已做安全评审？新的关键路径是否有观测？有风险的部分是否有回滚路径？需要人评审的变更是否已经过人评审？
>
> **按层应用**：每个任务至少查前两段；每个特性查集成与文档；每次发布以全表为底线并叠加发布专项。
>
> **稳定性**：项目层裁剪**一次**，之后原样复用。每个周期重新谈判的门槛不是门槛。门槛只应单调变紧：若过一段时间说不出"现在被强制而过去没有的是什么"，说明门槛没有真正生效。
>
> **常见红旗**："做完了，只是还没跑"（未验证的工作不算完成）；用"测试过了"代表完成而跳过文档、回归与运行时验证；按时间压力换用不同的门槛；把验收条件当作全部门槛；在需要人评审的变更上先宣布完成。
>
> **边界**：门槛的**内容与 owner** 在项目层；本次**是否满足**由具备独立性的评价给出，不由实现者自判。本方法不定义发布许可，也不产生风险接受。

# G6 · 方法库自身的变更纪律

> 本组不落在 A–F 责任位点上，落在**包维护**（载体落点、真源、豁免、负结果留存）。它与 Driver 的"不建 registry/框架"纪律直接相关，故列入 AB。

## G6.2 操作、成立条件、失败模式、反例

**操作**

1. **反重复预检（新增前六问）**：搜现有目录；查在飞工作（是否已有人在做）；查**被拒台账**里是否有因评估证据被拒的重叠提案；确认想法符合既有格式（可操作流程而非泛泛建议）；在提案里**明确论证缺口**（为什么现有方法/在飞工作/已被拒的方案覆盖不了）；**剥掉模型特定的 workaround**（凡不能在不点名某模型/版本/私有工具的前提下说明的步骤都不属于方法正文）。附判据句："若你的想法是既有方法的一个改良，优先对那个方法做一次聚焦的编辑，而不是新建一个目录。"
2. **不要复制，要引用**：跨能力/跨方法不得复制内容；改为按名引用。我方对应："不复述真源，只给指针。"
3. **唯一真源 + 指针**：`CONTRIBUTING.md` 是流程的唯一真源；护栏文件只写指针并显式声明"它是唯一真源、本文件不复述清单"。
4. **豁免的位置**：豁免**写在检查器内**并附理由，不写在被检查对象里；理由原句："这样贡献者就不能通过编辑自己的技能文件来绕过校验器"。另一面：某种宿主配置不支持某字段时，用户须把文件复制到用户级目录（即"能力缺失"被写成明确的能力边界，而不是静默降级）。
5. **同步面 vs 自由面**：三个宿主载体的 `description` 必须逐字相同（CI 检查），而**正文允许按宿主差异**；命名不一致靠显式映射表处理。
6. **约定变更的生产者/消费者同批更新**：工件路径这类约定只有一个白名单；改约定 = 改白名单 **且** 同批改所有受保护文件；CI 在二者一致之前一直失败。范围刻意收窄（只查该类工件，不做通用 markdown 检查器）。
7. **负结果留存（被拒台账）**：只增行、只记被拒、必带"用什么证据被拒"（rank-1 分前→后）与结果；并**单独落在默认分支**——理由是"若只留在被拒提案的分支上，关闭或强推该分支会把记录一起丢掉"。
8. **方法正文的去耦合判据（Procedure, not Workaround）**：一条步骤若无法在不点名模型/版本/某宿主私有工具名的前提下说明，它属于 issue 而不属于方法；描述**能力**（"运行聚焦的测试命令"）而非某个运行时的机制名。两个 smell：**过度规定的机制细节**（"某模型否则会做错"作辩护 → 它是 workaround）；**碎片化诊断**（多步检查中任一步就能确认同一件事 → 每多一步都在花掉别人真正需要的回合）。依据是跨模型迁移测量（源文引 WikiSkill/arXiv:2608.27454）：针对某一模型执行失败写的方法，可能让更强的模型**比不带方法更差**。
9. **上下文经济**：正文 <500 行；渐进披露（支持文件只在流程走到时读）；引用只一层（不要链式）；**优先脚本而非内联代码**（执行脚本不占上下文，只有输出占）。
10. **共享素材的位置权衡要写明代价**：集中式（多处引用同一份）避免复制与漂移，但**牺牲可移植性**（按单能力安装时共享文件不在包内 → 链接失效），源文把该缺口记为已知 issue 并保留权衡说明。

**成立条件**
- 检查器要能"检查得了"被判定的东西：豁免必须集中可查、理由必须可读。
- 台账要落在不会被提案生命周期带走的地方。
- 判据必须能在不点名具体实现的前提下写成（否则它从判据退化为 workaround）。

**失败模式与反例（可直接作为我方负向判据）**
- 无预检新增 → 近重复方法并存，选择入口出现两行近义。（**本 pin 内的实例**：同一"意图→能力"映射存在于至少 9 处载体，其中两处计数不一致：留存 25 与 24 冲突。）
- 复制而非引用 → 同一事实多处漂移。（**实例**：severity 词表在三处载体 + 一处机器判据中不一致，见 G3.2。）
- 豁免写在被约束对象里 → 自授豁免。
- 把"约定变更"只改一处 → 生产者与消费者不一致而无人发现（源文引用了真实事故：把生产端工件移到新目录而消费端仍要求旧路径，CI 无检查可捕获）。
- 把某次踩坑写成对所有模型都强制的步骤 → 对更强的模型造成净损失（源文附跨模型迁移测量）。
- 负结果不留存 → 下一个提案者重复同一条已被证据否掉的路线。

## G6.3 判断位点与拟供 Profile

本组不落在 A–F，落在**包与方法的维护者**（谁提出、谁检查器化、谁更新同步面）。与责任位点的唯一接口：

> ## 方法库变更的四条 house rule（草稿）
>
> **1. 新增前先查重。** 在提出一个新方法前：(a) 搜 `methods/` 正文与 `profiles/*.md` 的"按需方法入口（候选）"清单是否已有同一机制；(b) 查在飞工作与被暂缓/拒绝的候选记录；(c) 能说明既有做法为何覆盖不了（不能说明 → 改为对既有方法做一次聚焦编辑）；(d) 若该步骤无法在不点名某个模型/宿主/版本的前提下说明，它属于 issue 而不属于方法正文。
>
> **2. 不要复制，只引用。** 同一事实只应有一个真源；其余位置只写指针。方法正文不得在 Profile 或 README 里被复述。
>
> **3. 判据优先于机制。** 写方法时，描述**能力**（"运行聚焦的检查命令"）而不是某个运行时的机制名（"跑 `npm test`"）。两个自查点：**过度规定机制**（辩护词是"否则某个模型会做错" → 它是 workaround，不是方法）；**碎片化诊断**（多步检查里任一步就能确认同一件事 → 每一步都在花掉消费方真正需要的回合）。理由：针对某个模型的具体失败写下的步骤，可能让另一个更强的消费方比不带该方法时更差。
>
> **4. 约定变更要同批更新。** 路径、摘要、入口文字这类约定只有一个真源；变更时必须同批更新所有列出该约定的位置（本包内的清单见 `methods/README.md`）。若没有自动检查，由一次显式机械核对代替——并在记录里说明核对过哪些位置。
>
> **附：例外与状态写在哪。** 例外不写在被约束对象里（否则等于自授豁免）；候选、暂缓、被拒的理由与证据写在 `methods/README.md` 的对应段落，并保证它不会随某个分支被丢弃。

# G7 · 在存量工作里引入门槛的顺序

## G7.1 机制、触发情境、源锚、已读/尚缺

**机制**：把一套质量门槛引入**已经在运行的**工作体系（不是新项目）时的顺序与速率纪律：先引入只读与保护性的判断，再在将要改动的区域建"现状表征"安全网，然后让新工作走完整门槛，最后才谈回收与观测；整体质量单调不减。

**触发情境**：把一个方法库/门槛集引入一个已有代码库、已有团队习惯、覆盖不均的体系；或在吸收过程中决定"先落哪几条"。

**源锚（本轮已读全文）**
- `addy@2686b620:docs/adoption-guide.md`（`#Which path are you on?` 六行信号表、`## Path A`（Day 0 接线、Day 0 先定义、always-on 四项、按增长加载表、绿地反模式）、`## Path B`（Phase 1 只读与保护、Phase 2 先测后改、Phase 3 两速、Phase 4 回收/弃用/观测、棕地反模式）、`## The two paths converge`（收敛表））
- `addy@2686b620:skills/code-simplification/SKILL.md#Step 1: Understand Before Touching (Chesterton's Fence)` 与 `#When to Use` 的排除条件（性能关键且更慢 / 即将整体重写 → 不简化）

- `addy@2686b620:CONTRIBUTING.md#Modifying Existing Skills`（"保持改动聚焦最小、保留既有结构与语气"）

## G7.2 操作、成立条件、失败模式、反例

**操作**

1. **先判路径（六行信号表）**：代码龄（天/周 vs 月/年）、测试覆盖（自始可控 vs 不均、部分无覆盖）、约定（边做边定 vs 已建立且常无文档）、团队习惯（形成中 vs 已固化）、坏改动的风险（低爆炸半径 vs 可能弄坏没人记得怎么修的东西）、采纳策略（**立刻全生命周期** vs **增量、验证优先**）。中间态（已上线但年轻）→ 走增量路径并加速，两条路径终态相同。
2. **增量路径的四阶段**：
   - **Phase 1 只读与保护**：先让执行者**理解**再动手。第一件是上下文/约定文件（写**代码里真实存在的**约定，不是 wiki 里的；含构建与测试命令、目录含义、已知雷区，例："别碰 `legacy/billing`，没有测试且有三处已知变通"）；第二件是**对进来的改动做评审**（零风险且立刻有价值）；第三件是**调试方法**（在不熟悉的代码里最有效，且"防复发"这一步顺带开始积累回归网）；第四件是**对抗式复核**（遗留代码正是"不熟悉 + 出错代价高"的场景，用来抓"自信的幻觉"）。
   - **Phase 2 先测后改**：不追求全局覆盖，只追求**将要改动处**的覆盖；对无测试的遗留行为先写**表征测试**——把代码**当前**的行为钉住（对错皆然）再改。"Beyonce 规则"：若执行者已经依赖某个行为，就该给它一个测试。行为不变的简化 + 表征测试是让遗留代码变得可改的最低风险手段。原子小提交在存量代码里**更重要**：改老代码出问题时，~100 行提交可以二分，2000 行"现代化"提交不能。
   - **Phase 3 两速并存**：新工作按完整门槛走（含"边界段落"声明该特性可以碰与不可以碰的遗留面）；在新旧交界处**契约先行**；安全类判断先做一次存量审计再作为新改动的门槛。
   - **Phase 4 回收与观测**：退役/迁移用"把遗留面**缩小**"而不是"包起来"；观测按**你真正会调试的路径**加装；性能只在回归重要时做，且"先测量"防止在从来不是瓶颈的地方优化。
3. **绿地路径的反模式对照（同样是判据）**：以"只是原型"为由跳过定义（原型会变成产品）；把所有能力一次性加载（浪费上下文并稀释真正要用的）；把观测推迟到"有东西可观测时"（等于主动制造后续的存量问题）。
4. **单调不减（棘轮）**：每次只增加，不回退；自检问句："过一段时间后，你能说出**现在被强制而过去没有**的是什么吗？说不出来，就是推广停滞了。"
5. **收敛判据**：两条路径最终都到同一稳态（新工作走完整门槛；始终在线的测试与提交纪律；合并前评审；按需加载而不是批量加载）。差别只在安全网是否已存在。

**成立条件**
- Phase 1 的判断必须**先于**任何改动（顺序不是仪式，而是风险顺序：库存代码里"改变"的代价高于"理解"的代价）。
- 表征测试必须**只钉现状**、不夹带修正（否则它同时是变更与安全网）。
- 两速制要求有明确的分界（哪些面属遗留、哪些面按新标准）。

**失败模式与反例（源文逐条给出）**
- **大爆炸式采纳**：第一天就把完整门槛压到遗留库上 → 为已存在的代码写规格、在没有安全网的情况下重构。
- **放任执行者重构无测试的代码**：源文称其为存量采纳中**最昂贵的一条捷径**。
- **以"代码就是文档"为由跳过上下文**：执行者会从它碰巧读到的最差文件里推断约定。
- **默认把遗留行为当错的**：Chesterton's Fence——那个古怪的重试循环可能是承重的。
- **不棘轮**：采纳后没有任何东西被真正强制。
- 以及：把"测试通过"当完成（与 G5 共享红旗）；在性能关键处做"更简单但可测量更慢"的简化（`code-simplification#When NOT to use` 已列出该排除条件）。

## G7.6 可讨论正文草稿 + 验证方案与边界（未执行）

**草稿（候选正文，节选）**

> ## 在存量工作里引入门槛（按需方法草稿）
>
> **先判你在哪种情形。** 看六件事：工作体系已运行多久；覆盖是否均匀（有没有"没有测试且没人记得怎么做"的区域）；约定是边做边定还是已固化（常常没有文档）；习惯是形成中还是已定型；一次坏改动的爆炸半径；因此该"立刻引入完整门槛"还是"增量、验证优先"。已上线但年轻的体系：按增量路径走并加速；两条路终态相同。
>
> **增量顺序（顺序是风险排序，不是仪式）**
> 1. **只读与保护**：先让执行者理解，再让它动手。先写**真实的**约定（构建与检查命令、目录含义、已知雷区——例："不要碰 X，没有测试且有三处变通"）；再对进来的改动做评审（零风险、立刻有价值）；再用调试方法（在不熟悉的代码里最有效，顺带积累回归网）；最后用对抗式复核抓"自信的幻觉"。
> 2. **先测后改**：不追求全局覆盖，只覆盖**将要改动的地方**。对没测试的既有行为先写**表征测试**——把当前行为钉住（对错皆然）**再**改，且不夹带修正。若某个行为已经有人依赖，就该给它一个测试。改动越小越好：老代码里 ~100 行提交可以二分，几千行的"现代化"提交不能。
> 3. **两速并存**：新工作走完整门槛，并显式声明它可以碰与不可以碰的遗留面；新旧交界处契约先行；安全类判断先在存量上做一次审计，再作为新改动的门槛。
> 4. **回收与观测**：用退役/迁移**缩小**遗留面，而不是把它包起来；观测按你真正会调试的路径加装；性能只在回归重要时做，且先测量。
>
> **门槛只应单调变紧。** 自检问句：过一段时间后，你能说出**现在被强制而过去没有**的是什么吗？说不出来，说明引入停滞了。
>
> **不要这样做**：第一天就把完整门槛压上去（会为已存在的代码写规格、在没有安全网时重构）；放任执行者重构无测试的代码（这是最贵的捷径）；以"代码就是文档"为由跳过约定（执行者会从最差的文件里学）；默认遗留行为是错的（那个古怪的重试循环可能是承重的）；不棘轮。
>
> **边界**：本方法只安排**引入顺序与速率**，不定义门槛内容（那是项目层门槛，见常备质量门槛方法），不产生授权，也不要求任何固定阶段必须发生。

**验证方案（未执行）**
- 机械核：草稿中"顺序"必须带风险理由；每个阶段必须能回答"何时**不**适用"（至少一处例外）。
- 覆盖核：与 `local-defect-feedback-loop`（回归接缝）和 `cross-module-design`（接缝/替身）逐条对照，确保"表征测试"只在一处定义，其余引用。
- 反例核（需另行授权，只读）：取一个"改动无测试区域"的历史案例，检查草稿能否给出"先钉现状"的判断而不是"先重构"。
