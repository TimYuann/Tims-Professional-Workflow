# 冷启动：在一个新仓库里装上这套工作流

假设 Owner 在某个仓库里说：「用 TIM Professional Workflow 开始开发。」
一个新会话拿到这句话，接下来的几分钟决定这次协作是通的还是断的。

这份文件就是那几分钟该做的事。

---

## 第 0 步：先问，不要先读

进入一个陌生仓库，**第一件事不是读代码，是问 Owner 三个问题**：

1. **这个仓库已有的文档体系是什么？** 有没有任务管理、设计文档、决策记录？
   → 决定你走[下游映射](downstream-mapping.md)的哪一种情况。
2. **这次任务的诉求是什么？** 一句话。
   → 没有这一句就开不了工，去走 `P0`。
3. **台账落在哪？** 这条不许商量。一个找不到落点的 `A9` 等于没有台账。

三个问题问完，才进入下一步。顺序反了，你会先花两小时读代码，
然后发现 Owner 真正想要的是另外一件事。

---

## 第 1 步：确认底座能力

这套东西需要四项能力。任何一项没有，改造流程的某部分——告诉 Owner，而不是绕过。

| 能力 | 确认方法 |
|---|---|
| 能起一个独立会话并注入一段文字 | 起一个空会话，把装配好的角色 prompt 发进去，看它认不认（**用 `scripts/compose-role.py <角色>` 装配，不要直接发角色文件正文**，见下） |
| 能读写真实文件 | 写一个临时文件再删掉 |
| 能在会话之间收发消息 | 让两个会话互相打一次招呼 |
| 能并行跑多个会话 | 起两个，看是不是真并行 |

**「我这边可以」不是确认，「我试过了并且成了」才是。**

---

## 第 2 步：把脚本落到下游

**脚本不能留在本库。** 本库在运行时不一定可读，下游仓库也不能依赖一个外部路径。

需要落到下游的：

| 脚本 | 落在下游的哪个位置 |
|---|---|
| `check-closure.py` / `check-consistency.py` | 下游的检查目录（如果有 CI，接到 CI 里） |
| `render.py` | **要**。派生视图（阶段契约、横切带、产物表、闭包报告）全部由它从注册表生成，下游改了注册表就得重跑它 |
| `ledger.sh` | 随 `A9` 的落点一起放 |
| `upstreams.lock.yaml` | 随注册表一起拷。下游没有三仓克隆，靠这份锁文件核对处置表 |
| `sync-upstreams.sh` / `_render-lock.py` | **不拷**。它们是本库维护上游用的，下游不需要更新上游 |

装法：复制 + 改掉里面的库内路径。**复制，不引用。**
一个指向本库绝对路径的脚本，在别人机器上必然跑不起来。

**在下游，`C7`（上游处置完备）与 `C9`（来源声明与锁文件一致）正常情况下是 `PASS`。**
它们核对的 `upstreams/` 不随包分发，但 `upstreams.lock.yaml` 随包分发——
所以这两项在干净 clone 里直接对锁文件判，**实测全绿**。
有克隆的本库里，**`C9`** 会**额外**逐条比 sha256 与 pin（`C7` 在有克隆时行为不变），
克隆漂了就变红；克隆不在场时 `C9` 的输出会自己写明「未做上游实物 sha256/pin 对照；
不证明锁文件与真实上游一致」。
**所以：漏拷 `upstreams.lock.yaml` 的下游会直接红，而且不止一项**——
实测 `C7`、`C9`、`C20` 三项同时红（`C20` 的来源段也要对锁文件里的上游 id）。
`C7` 的 detail 显示「锁文件 0 个上游 skill，处置表 101 条」这样的对账差，
**不是**「锁文件过期」——那句只在「锁在、但索引与处置表对不上」的分支里出现。
**这是故意的，不是「下游跑不了」。**

> `SKIP` 是可达的，但它只表示**这一项在这个环境里判不了**，不表示通过：
> 挂了 `upstreams/`、而某个上游仓的 git 元数据不可信（例如只拷了子目录、
> 或软链到本库之外）时，`C9` 无法核对 pin，判 `UNVERIFIED`（渲染为 `SKIP`）并点名是哪个仓；
> 无 git 元数据（`git archive` 导出）时 `C1` 同样判 `UNVERIFIED`。
> **本库按上面第 2 步 vendored 进下游后，它就是一个无 tag 的子目录——`C1` 照样判 `UNVERIFIED`**，
> 因为「tag 即本库 release」这件事只在本树是该 release 仓库的根时才成立，
> 而 monorepo 与 vendored 副本从树内看一模一样。本库的 release 身份由**本库自己的仓库**或
> **外层仓库的发布流程**保证，`C1` 在这棵树里判不了。代价是那种形态下
> 「tag 与 `VERSION` 对不上」会静默——**责任在外层的发布流程**。
> v2.0.5 之前 `C7`/`C9` 在下游一律 `SKIP`，后来矫枉过正成「绝不可达」——
> 现在的实况是：**能判的判，判不了的如实 `SKIP`，判出坏的红。**

剩余项必须全过。

---

## 第 3 步：把产物映射到下游

走 [下游映射](downstream-mapping.md)。三条纪律里最容易丢的是「谁写」，
所以逐项确认时重点问：**下游那个位置，是由谁在什么时候产出的？**

映射结果记进 `A9`。

---

## 第 4 步：判档

看诉求的体量：

- **小**（一个会话装得下）→ `solo`。装配者自己转成特殊 driver，
  按需读角色文件、加载技能、最小化做完、直接向 Owner 汇报。不发派。
- **中** → 少量几个角色，必要时合并会话。
- **大** → 全链条。

**不写数字。** 编号会诱导凑数。判据是**这次变更的风险与仓库成熟度**——
单点可逆的改动降档，影响面大或不可逆的改动升档。
**「闭环完整」不是判据，是结果**：装配完之后每一环需要的东西都有人产出，
那是装配对了的证据，不是用来决定装多少的依据。用它当判据会让人凑数。
装配完之后，每一环需要的东西都有人产出。

小任务时把两个角色合并进一个会话是允许的：把两份角色文件 +
两份技能的并集 + 相关脚本一起喂给它。
**但提出候选的人不能给这个候选下结论**，这条在任何档位都不放宽。

> **角色必须先装配，不能直接发角色文件正文。**
> 原则正文只存在于 `principles/`；角色文件里只有 principle 引用（形如 `@p-type-system-discipline`）与该角色何时加载它的
> `trigger`。直接把 `roles/architect.md` 发进会话，里面的 `@p-type-system-discipline`
> 只是一个没有定义的符号。
> `python3 scripts/compose-role.py architect` 会把角色正文 + 它引用的全部原则正文
> 拼成一段可直接注入的 prompt。`--all` 装全部角色。
> 装配完可以跑 `python3 scripts/compose-role.py --check` 验结构——
> 它断言每一条 principle 引用都真实存在、正文只有一个 canonical location、
> 角色里没有第二份释义。

---

## 第 5 步：起 P0，并且**先说不做什么**

起 `P0` 之前，强制 `voice` 拿到 `A1.non_goals`。

这一步最容易被跳过，后果是范围缓慢扩张：
每加一个小需求都合理，三个月后没人说得清这次到底要做什么。

---

## 自检清单

装完之后，对着这张表核一遍：

- [ ] 底座四项能力都实测过，不是「应该可以」
- [ ] 脚本已复制到下游，不再依赖本库路径
- [ ] 9 类产物各有落点，`A9` 的落点已确认
- [ ] 映射表记进了台账
- [ ] 档位已判，理由是变更风险与仓库成熟度，不是数字也不是「闭环完整」
- [ ] `P0` 已经在跑，且 `A1.non_goals` 已被追问过
- [ ] 冷启动这件事本身记进了 `A9`

任何一项没核完就开工，代价会在几天后以「返工」的形式出现，
而那时候已经没人记得当初是哪个决定造成的。
