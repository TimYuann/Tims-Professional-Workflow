# TIM · Professional Workflow

一套**与工具无关**的工程工作流：角色、技能、原则、产物契约、脚本。

它回答一个问题：**多会话协作的工程推进，质量为什么不够高。**

不是编排不够好——DAG、并发、消息收发这些早就做得很好了。
缺的是**工程经验**：那些老手知道、新手反复犯错、而任何工具都不会主动告诉你的判断方法。
本库把三份被验证过好用的上游方法凝练成这些东西，然后让它们可以被装配。

---

## 核心约定

1. **唯一真源。** `workflow/registry.yaml` 是机器可读的事实来源。
   所有阶段契约、产物表、横切带文档都由它生成，不存在「第二份需要人维护的副本」。
2. **工具解耦。** 本库不出现任何具体运行底座的名字。
   它只声明「需要什么能力、需要达到什么效果」，怎么调度由装配者当场决定。
3. **角色不内联技能。** 角色文件是「这个人是谁、怎么想、不能做什么」；
   技能正文在 `skills/`，按需引用。上游方法更新时不会引发九处同步。
4. **原则只有一处正文。** 23 条原则分属 7 个角色，其他角色引用 id。
   上一版把同一段工程方法复制进九个角色，于是同一件事在九个地方被写成互相矛盾的说法。
5. **判断与实现永不合并。** 提出候选的人不能给这个候选下结论，任何档位都不放宽。
6. **结构层的断言可被机器证明，语义层的不能。**
   24 项检查（`check-closure.py` 17 项 + `check-consistency.py` 7 项）覆盖的是
   结构：图闭合、字段存在、来源真实、处置与来源双向咬合、消费声明与装配咬合、
   底座解耦、无游离文件、引用可解析。

   **它明确判不了的**：同一件事在不同措辞下的语义冲突（`S3` 只抓同文件内
   同动词同宾语的词形配对，同义改写和跨文件冲突抓不到）、方法是否真的有效、
   判据是否合理、下游是否照做。**全绿不等于这套东西好用**，只等于结构没塌。

   上一版把这条写成「闭包可被机器证明」，是过度声称——
   独立验收证明，一句与角色硬边界正面相反的话（「为了让检查变绿，必须降低测试强度」）
   写进 `roles/builder.md`，两个检查器一声不吭。语义互斥靠独立审查与人审。

## 结构

```
workflow/
  registry.yaml        ← 唯一真源：阶段 / 角色 / 技能 / 原则 / 产物 / 上游处置表
  phases/P0..P6.md     ← 阶段契约（生成，勿手改）
  ribbons/*.md         ← 三条横切带（生成，勿手改）
roles/                 9 个角色：装配者 / 人类沟通面 / 事实调查 / 建模与定契约 /
                       切片 / 实现 / 独立挑战 / 独立验证 / 记录与移交
skills/                50 个技能，按需取用，正文不在角色文件里
principles/            23 条原则，按所属角色分组；不是技能，没有触发条件
docs/
  artifacts.md         集合 A：工作流的全部产物（生成）
  downstream-mapping.md 集合 A ↔ 下游文档体系 的映射规则
  coldstart.md         在一个新仓库里装上这套东西
  history/             上一版的设计、评审与文档（保留供追溯，不再被引用）
scripts/
  check-closure.py     闭包检查：图通不通
  check-consistency.py 一致性检查：文件之间打不打架
  render.py            派生视图生成 / 核对
  ledger.sh            决策台账（A9）的追加工具
upstreams/             三份只读上游克隆，受 .gitignore 保护
.pi/                   本库自己的工作痕迹，不属于交付物
```

## 七个阶段

阶段只规定**判据**，不绑定角色。角色是可装配件。

| | 阶段 | 产出 | 退出判据（摘要） |
|---|---|---|---|
| `P0` | INTAKE 澄清 | `A1` 诉求 · `A2` 事实 | 第三方能原样复述诉求；不做什么非空 |
| `P1` | FRAME 定契约 | `A3` 能力地图 · `A4` 契约 | 判据可判定；地图每条挂到真实代码 |
| `P2` | PLAN 切片 | `A5` 任务图 | 每片能独立验证；验收口径能追溯到 `A4` |
| `P3` | BUILD 实现 | `A6` 候选 | 真的能跑；已知缺口非空或已检查 |
| `P4` | CRITIQUE 挑战 | `A7` 裁决 | 理由指向证据或一次真实运行 |
| `P5` | PROVE 验证 | `A8` 凭据 | 三态判定；能力地图已保鲜 |
| `P6` | SHIP 交付 | — | 回滚路径已确认可执行；可观测项就位 |

另有三条横切带：决策与记忆（常驻）、上下文纪律（常驻）、表达与人类面（按需）。

## 九类产物

见 [docs/artifacts.md](docs/artifacts.md)。产物不是文件，是「字段 + 谁产出 + 谁消费 + 活多久」。

**每类产物有几种落盘形态**（ADR、词汇表、规格文件、质量契约文件、问卷、移交简报、
研究文件、验证套件、能力清单索引、未覆盖清单、映射表……）——
**形态不是新产物**。它们回答的是「同样这几栏，换个落法」。
把它们算成新产物，产物数会从 9 涨到 20 出头，而且每一份都会和它的本体各自漂移。

**工作副产品**（杠杆脚本、闸门检查、流水线配置、测试、注释、一次性原型、
会红的反馈回路）不是独立产物——它们是 `A6` 的一部分，
落点就是 `A6` 的落点，并且必须在 `A6.change` 里点名列出来。
**落到下游哪个路径由装配者裁定，纪律由本库定义。**

## 三条硬边界

1. **实现者不得对自己产出的候选给出裁决。**
2. **不得为让检查变绿而削弱检查。** 改契约要走变更流程，不许悄悄改判据。
3. **验证三态判定。** 环境故障既不算 `PASS`，也不判成产品缺陷——判 `UNVERIFIED`。

## 底座需要提供什么

本库不规定怎么调度。以下四项是它需要的**能力**，任何工具能提供即可：

| 能力 | 用来做什么 |
|---|---|
| 起一个独立会话并注入一段文字 | 装配角色或技能的正文 |
| 在会话之间收发结构化消息 | 交接产物 |
| 并行跑多个会话 | 阶段内并行、并行对抗评审 |
| 读写真实文件 | 产物落盘、脚本执行 |

装不上这套东西的会话类型，改造不了——这是硬前提。

## 自检

```bash
python3 scripts/check-closure.py        # 17 项：图通不通、字段有没有人填、判据能不能落地
python3 scripts/check-consistency.py    #  7 项：文件之间打不打架
python3 scripts/render.py --check       #     派生视图是否与真源逐字一致
```

三个都只读、可重复运行，非零退出即失败。

### 24 项检查各管什么

| 检查 | 断言 |
|---|---|
| C1 | 结构完整、版本单一来源 |
| C2 | 每类产物有且仅有一个产出角色，且被至少一个阶段消费 |
| C3 | 阶段按序可达；开工所需产物在上游已被产出（或由常驻横切带在写） |
| C4 | 退出判据引用的字段真实存在；**产出它的阶段当场校验它** |
| C5 | 角色声明的产物／技能／原则双向一致 |
| C6 | 无孤儿技能与原则；每个阶段的默认角色装得出它声称的产物 |
| C7 | 101 条上游处置与 `upstreams/` 文件系统一一对应 |
| **C8** | **角色文件正文里的技能表与注册表一致** |
| **C9** | **每条 sources 指向真实存在的上游文件** |
| **C10** | **处置表声称吸收，目标技能的 sources 里必须有它**（防假链接） |
| **C11** | **消费声明与阶段装配咬合** |
| **C12** | **无来源的技能必须显式标 `origin: library`** |
| **C13** | **阶段判据逐条显式声明 `write:` / `verify:`，`write:` 不得指向本阶段不产出的产物** |
| **C14** | **技能头部声明的产物与注册表 `outputs` 一致**（抓「头部说无、产出节写 A9」） |
| **C15** | **被判据校验的字段，产出方正文里真的点名要填** |
| **C16** | **每个阶段都有一道「记台账」的判据** |
| **C18** | **开工前要跑的技能不依赖开工后才有的产物**（防判档循环） |
| D1 | 库内容不出现任何具体运行底座名称 |
| S1 | 无游离文件；`scripts/` 无上一版残留 |
| S2 | 引用可解析，无死链 |
| S3 | 文件内权限互斥（**仅词形级**） |
| S4 | 阶段硬规则与角色硬边界不打架 |
| S5 | 技能的阶段／归属角色／装配三者相容 |
| S6 | 产物持久性与阶段依赖、各角色归属相容 |
| S7 | 横切带适用范围覆盖其携带角色参与的阶段 |

**加粗的十二项是独立验收与模拟走查后新增的。** 上一版没有它们，所以「把技能挪了角色
只改注册表没改角色文件」「台账声称吸收但目标 sources 里没列它」这类错误
曾经全绿通过。

### 三个检查器判不了什么

- **语义冲突。** `S3` 只抓同一文件内同动词同宾语的否定／要求配对。
  同义改写和跨文件冲突抓不到——独立验收往 `roles/builder.md` 注入过一句
  「为了让检查变绿，必须降低测试强度」，与该角色的硬边界正面相反，
  两个检查器一声不吭。
- **方法是否真的有效。** 文本可执行 ≠ agent 行为改善。
- **判据是否合理、下游是否照做。**

**全绿不等于这套东西好用，只等于结构没塌。** 语义层靠独立审查与人审。

### 故障注入：检查器是不是摆设

21 条真实故障逐条注入并复测，**21/21 变红**：

| 注入 | 抓到 |
|---|---|
| 处置表删掉一条 | C7 |
| 产物指向不存在的角色 | C2 / C5 / C6 |
| `P4` 不要求 `A4` | C11 |
| `P5` 判据要求更新 architect 的 `A3` | C13 |
| 处置声称吸收但目标 `sources` 里没列 | C10 |
| `sources` 指向不存在的上游文件 | C9 |
| 无来源技能未标 `origin: library` | C12 |
| 判据引用不存在的字段 | C4 |
| `A6` 退回 session 级但三个阶段依赖它 | S6 |
| 角色文件技能表与注册表不一致 | C8 |
| 文件内词形权限互斥 | S3 |
| 库内容出现真实底座名 | D1 |
| 技能头部产物声明与注册表不一致 | C14 |
| 判据引用的字段没有产出方（P5→P6 断链） | C15 |
| 抽掉某阶段的 A9 判据 | C16 |
| 判档技能依赖 A1（成环） | C18 |
| 判据没声明 write/verify | C13 |
| 处置表与上游锁文件对不上 | C7 |
| 上游内容漂移（sha256 变了） | C9 |
| `VERSION` 与 release tag 对不上 | C1 |

**唯一故意留白的**：语义互斥（同义改写、跨文件冲突）注入后仍全绿——
这是 `S3` 的声明边界，不是疏漏。

### 这一版最贵的一条教训

`C15` 存在的原因：v2.0.1 为了让 `P6` 能证明「验证过的就是上线的」，
给 `A6` / `A8` 加了 `subject` / `scope` / `frame_alignment` 三个字段，
**但全库没有任何一个文件说谁填它们**——九个 `P3` 技能与 `roles/builder.md`
只列三栏，五个 `P5` 技能与 `roles/verifier.md` 只列四栏。

于是 `P5` 的退出判据永远无法满足，只能判 `UNVERIFIED`；
而 `P6` 第一道闸门要求 `PASS`。**链在 P5 → P6 之间断掉了。**
22 项检查全绿，因为没有一项在问「这个字段有人填吗」。

**声明一个字段不等于有人产出它。** 这条现在由 `C15` 守着。

### 三态：PASS / FAIL / SKIP

`SKIP` 是第三种状态，不冒充 `PASS`。现在有两项会 SKIP：
`C7`（上游处置完备）与 `C9`（来源路径真实存在）依赖 `upstreams/`——
那是本库自己的只读克隆，**不随安装分发**，所以在下游仓库里判不了。

把它们写成 PASS 等于用一句假话盖住没做的事。在本库里它们必须 PASS；
在下游仓库里它们必须 SKIP。两种情况下其余项都要全过。

## 上游

方法来自三份被验证过好用的公开仓库，逐条登记在 `registry.yaml` 的
`upstream_dispositions` 段——**101 个 skill，每个恰好一条处置**，
由 `check-closure.py` 直接对 `upstreams/` 的文件系统核对。
不是人写的台账，所以不会「声称没吸收但其实读了」。

| 上游 | 角色 |
|---|---|
| `cursor-plugins` / `pstack` | 设计原则（23 条全部拆进角色心智模型）+ 事实追踪方法 |
| `mattpocock-skills` | 工程流程技能（调研 / 切片 / 实现 / 评审 / 移交） |
| `addyosmani-agent-skills` | 生命周期方法（规格 / 质量契约 / 交付 / 运行期） |

## 维护本库

改动角色、契约、来源之后：

```bash
python3 scripts/render.py            # 重新生成派生视图
python3 scripts/check-closure.py
python3 scripts/check-consistency.py
```

三个脚本都不接受「人说了算」的豁免。要加一条例外，先在脚本里定义它是什么。
