# R4 任务卡 · 台账改为生成物 + 专职台账管理员

**Owner 的指令（本节是权威，与之前的卡冲突时以本节为准）**：
> 用一个台账管理 agent 专门处理每次修改后的台账更新。

**我的诊断（承认之前方向错了）**：我把 `SOURCES.md` 的落点当"待核实的声明"，于是搞抽样、搞门、反复失败。**正确做法是把它降级为"派生视图"**：人写"来源与理由"，**落点与步骤原文由脚本生成**，改完就重跑，规则没了就报错。这样"写错步骤号""声称的动作不存在"这两类错**在构造上不可能发生**，不需要任何人去核对。

---

## 1. 交付物

### D1 `scripts/render-ledger.py`（新脚本，只读源文件 + 只写生成区）

- **人写部分**：`SOURCES.md` 里保留：来源 `file:line`、上游机制、处置（保留/改写/删除/不采纳）、理由。
- **生成部分**：每个落点由人写一个 **规则 key 短语**（取自目标角色那条规则里的**实质短语**，例如 `注释只写 why`），脚本按 key 在目标文件里定位，**把真实的文件 + §节 + 步骤号 + 该步原文**填进生成区。
- **生成区用标记包裹**，头部写明不得手工改：
  ```
  <!-- BEGIN:landings (generated by scripts/render-ledger.py · 不得手工改) -->
  …
  <!-- END:landings -->
  ```
- **必须 fail closed**（这是本项的核心）：
  - key 在目标文件里**找不到** → 非零退出并列出该 key；
  - key **命中多处**（歧义）→ 非零退出；
  - 目标文件不存在 → 非零退出。
- `--check` 模式：重新生成并与当前生成区逐字比较，不一致 → 非零退出（供 CI/自检调用）。

### D2 `roles/ledger-custodian.md`（第 10 个角色）

- 和其它 9 个角色**同构**：注入契约块 + 8 个必需节（`使命 / 我收到什么 / 我必须交出什么 / 我的工程方法 / 权限边界 / 升级条件 / 退出判据 / 常见自欺`），§4 至少 6 个小节、每节带触发条件/步骤/判断依据/≥2 条反例或"不适用"。
- **职责**：每次改动落盘后**重跑 `render-ledger.py`**，把生成区的 diff 与它对账（哪条落点因为规则被移动而**步骤号变了**、哪条 key **找不到**了），把结果写进交付。
- **硬边界**：**不得手工编辑生成区**；key 找不到时不得改 key 去迁就，只能**报回产出方**（规则被删/被改）或改人写的处置列。
- **可由专门会话承担**（Owner 的原话），也可由现有会话兼——但兼的时候不得同时是实现该改动的人。

### D3 接线（改这几处，checker 会验）

- `scripts/check-library.py`：`ROLE_IDS` 加 `ledger-custodian`；**P5′ 改为调用 `render-ledger.py --check`**，删掉自己那套正则锚点解析（它已被证明会漏解析粗体等形态）。
- `closure.md`：加 `ledger-custodian` 的按需行（输入=本批改动的文件与落点声明 / 输出=`ledger-report`：生成区 diff + 待人工处置的 key 失效清单）。
- `pipeline.md`：档位表与拓扑块补这条边；说明它**不参与实现/判断链**，是记录侧职责。
- `README.md` / `AGENTS.md`：角色数 9→10 同步。
