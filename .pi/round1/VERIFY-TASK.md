## 2. Owner 的标准（验收依据）

1. **方法 > 流程**。流程薄到够 Driver 干活即可，主体是工程经验。
2. **经验装进角色，不放在 skill 里**。角色文件是唯一注入单元。
3. **工具解耦**：只有 `roles/driver.md` 提"检测当前工作环境的能力并据此装配"；其余文件零工具字样。
4. **每个 agent 最终收到四层**：`工作纪律 + 工作方法`（本库，来自角色文件）+ `本轮工作流切片 + 工具安排`（Driver 附加）。角色文件必须显式声明这个接缝，且**单独注入即可开工**。
5. **闭环**：角色组合后能闭环执行完整开发——**上一环的输出字段就是下一环的输入字段**，且每条可跳过路径都有明确的职责移交。
6. **三仓深度吸收 + 重复/冲突逐条裁决**（不许"综合两者"）。
7. **自洽无断档**：无死引用，单一版本源。

### B. 引用忠诚度抽查（**这是最容易出假绿的一项**）

## 4. 结论格式（硬要求）

输出 `.pi/round1/VERIFY-REPORT.md`，必须含：

```
## 1. 结论（三态，只许选一个）
PASS / FAIL / UNVERIFIED
—— UNVERIFIED 只用于"环境或对象原因导致检查没能有效执行"，且必须写明是哪一条检查、什么原因。
   不得用 UNVERIFIED 掩盖"我发现了问题但不想下结论"。

## 2. 我实际执行了什么
逐条：命令 / 环境 / 退出码 / 输出要点。没跑的一律列进「未执行」并写原因。

## 3. 阻断项（Blocking）
每条：现象 / 证据（file:line 或命令输出）/ 为什么阻断 / 最小修复方向。
没有就明确写"无"。

## 4. 非阻断项
每条同上，但不阻断。

## 5. 我的核验边界（这条不许省）
我覆盖了什么、没覆盖什么、我的判据在哪些地方可能失效。

## 6. 与需求对照
Owner 的 7 条标准，逐条给「满足 / 部分 / 不满足」+ 依据。
```

**纪律**：
- 三态里没有"基本通过"。有阻断项就是 FAIL。
- **先只看产物下结论**；你的结论定稿之后，才允许读 worker 的 `.pi/round1/REPORT.md`，用来核对"它声称做了、但产物里没有"的部分（这一项写进第 3 或第 4 节，标明来源是自述）。
- 你自己的结论里禁止出现"我觉得应该没问题"。
- 完成后再用 intercom 回我一条 ≤20 行的摘要（结论 / 阻断项条数 / 没跑什么 / 核验边界）。
