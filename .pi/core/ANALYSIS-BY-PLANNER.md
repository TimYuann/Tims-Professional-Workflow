## ② check-library 是什么、它该在哪儿触发

Owner 的定性：**它本质上是「结果确定性」工具**，对付的是**指令遵循退化的模型**——尤其是上下文占满、或者被压缩过一两轮之后。

**它现在的问题不是"该不该有"，而是"站在哪儿"。** 现在它的位置是"每批收口时跑一次"，等于**事后体检**。按这个思路，它应该站在**交接点上**——因为它能兜的那三件事，全都是交接问题：

| 它能兜的 | 这是谁的活 |
|---|---|
| 上一环交出的名字，下一环收的名字对不上 | **收件人**核对时才该发生 |
| 引用的文件不存在 | 收件人**打开来才知道** |
| B 拿到的 A 的文件里，东西齐不齐 | 同上 |

**判断：它不该是"每批跑一次的独立体检"，而应该是「收件人核对这一动作的机械部分」。** 三个触发点：

1. **每次交接** —— 收件人拿它核"我声称要收的东西是不是真的在"
2. **每批收口之前** —— 给 Owner 汇报之前做一次
3. **上下文被压缩之后** —— 这正是指令遵循最弱的时候

## ③ UCBIP 那串，应该从哪儿被截断

那串是：**verifier 收到一个"验证某功能修好了没"的任务 → 发现没人给它造任何基础设施 → 自己造了 → 自己测 → 回"测试通过"。**

**现状实测**：十个角色文件里，"收到件先核对声称的东西是否真的存在"这类规矩有几处：

| 角色 | 处数 |
|---|---|
| Driver | 8 |
| Implementer | 6（含"开工前收据核对"） |
| Reviewer | 4 |
| Verifier | **2**（两条都是"缺则不开始/按最小范围处理"） |
| Integrator | 2 |
| **Investigator** | **0** |

**而 Verifier 的输入契约里只有两样东西**：一个"候选代码"，一个"审查结论"。**没有第三样——"环境/夹具是否已经就绪"。**

**应该从哪儿截断？两刀，且都不在"不许它自己造"上：**

**第一刀：收件时的交接纪律。**
> 收到任务，**第一步是清点**：这个任务声称有的东西，是不是真的在？**不在 → 立即退回，不许自己补上再继续。**

在那一串里，任务声称"要验证修复"，但**没有任何一处声称"环境是可用的"**。所以 Verifier 没有依据说"你没给我能跑的东西"——它只能自己造。**缺的是"任务必须声明环境状态"+"收件人必须核对这个声明"。**

**第二刀：自己造的东西必须进交付。**
> 如果它**必须**自己造前提（**环境建设本来就归 Verifier**），那"造了什么、怎么造的、它是产品的一部分还是临时装置、证据等级多少"**必须写进交付物**。

否则就是"自己搭台、自己测、报通过"——**结论本身无法被评估**。

**合起来就是一条明确的「交接纪律」**，而这条纪律现在**散在各角色里、不完整、而且没有名字**：

> **清点**（我收到了什么）→ **核对**（声称有的，实际有没有）→ **缺则退回**（不许猜、不许自己补上再往下走）→ **齐则开工**

`check-library` 这类工具，就是**第 2 步的机械执行部分**。

**自我纠正**：之前说这事儿是"过度防御"，只对了一半——**预防"搭台接错线"确实是过度防御**；但**"收件人核对声称的东西是否存在、不存在就立即退回"不是防御，是交接纪律**，而且它现在是缺的。

## ④ 造回路 = TDD，我们缺一环

**三仓都有 TDD，两处都有：**

- **addy**：`test-driven-development` —— 红-绿-重构；明确写了 **"Prove-It Pattern"：修 bug 之前，先用一个测试把 bug 复现出来**。原话：*"For bug fixes, reproduce the bug with a test before attempting a fix. Tests are proof — 'seems right' is not done."*
- **matt**：`skills/engineering/tdd` + `docs/engineering/tdd.md`

还有一条可能没吸收好的：**"先摸清这个仓库的工具链"**——*"The TDD cycle is universal; the commands are not."*（先找 `Makefile`/`gradlew`/仓库脚本，别上来敲 `npm test`。）

**"谁负责造回路"：不是一个人，是四个人用同一条思路做不同的事。**

| 角色 | 它用"先红后绿"干什么 | 现在有吗 |
|---|---|---|
| **Implementer** | 写代码：先写能失败的检查，再写实现 | 有 |
| **Investigator** | 诊断：先让问题稳定重现，再找原因 | 有 |
| **Reviewer** | 判断"这条判据真的能失败吗" | 有 |
| **Verifier** | **验证：先证明我的判据能红，再证明它变绿** | **没有单列** ← 缺的就是这个 |

**所以"是否应该写进 verifier"——应该。** 现在 Verifier 有"判据必须能失败"和"变异测试"，但没有一条是**"收到任务后，第一件事是把原始问题先复现成红灯"**。

**更重要的发现**：这说明"同一条规范只能有一处"那条原则**需要限定语**。同一思路在不同角色里出现**不算重复定义**——只要每个角色写清"我用它干什么"。真正要禁止的是"同一件事被两个人用不同措辞各自定义"。

## ⑤ "假设去修"这个问题，从根上判错了

Owner 原话：*"bug 排查一定有固定的方法论，就在这三个仓库里。如果这三个仓库被妥善吸收，仍然不能解决'假设并修复'的问题，那这个项目就没有存在的必要了。"*

**三仓的方法论比我们现在全：**

**addy 的 `debugging-and-error-recovery`** 开头就写：*"**Guessing wastes time.**"* 然后是一条 **Stop-the-Line 规则**：

```
出任何意外 →
1. 停止加功能、停止继续改
2. 保存证据（报错输出、日志、复现步骤）
3. 用固定的分诊清单诊断
4. 修根因
5. 防复发         ← 这条我们没有
6. 验证通过才恢复
```

**matt 的 `diagnosing-bugs`** 是六个阶段：**建反馈回路**（含怎么收紧回路、不确定性问题怎么办、**真的建不出回路时怎么办**、完成判据=能变红）→ 复现+最小化 → 假设 → 插桩 → 修+回归测试 → 收尾。

**对照我们现在有的**（investigator 七节：先建反馈回路 / 复现与最小化 / 真实路径追踪 / 历史考古 / 竞争性假设与区分性实验 / 连续失败质疑前提 / 结束调查）：

- matt 的六阶段我们**基本都有**
- **缺的是 addy 那两条**：① 出问题后"**停止、保存证据**"这个前置动作；② "**防复发**"
- **更关键**：我们"造不出回路"那条只写到"**停手、说出来**"就结束了；**matt 专门有一节 "When you genuinely cannot build a loop"**——**我们没吸收那一节。**

**所以"假设并修复"还能发生，不是因为它需要一条新禁令，而是因为我们把上游的方法论吸收漏了一块。**

**立个标准记着：三仓方法论吸收对了，这个问题就该消失；如果补完还在，那是这个项目没有存在必要。**

## ⑥ 版本漂移：三仓的答案跟原来的设想不一样，worktree 的猜想是对的

**addy 的 `git-workflow-and-versioning`** 关键那句：

> **"Derive the version from the tag rather than hand-editing it in scattered files, so the artifact, the tag, and the changelog can never disagree."**
> （版本**从 tag 派生**，不要手写在散落各处的文件里。）

**这句话正对着我们的病**：我们之前就是**手写版本号，而且三个地方不一致**（`VERSION` 文件、角色文件头部、提案文档）。

**pstack 那边**只有一句相关的：*"Regenerate lockfiles with package manager tools instead of hand-editing."*

**三仓里没有任何一处**是"下游锁定上游快照 + 漂移检测"这种做法。

**三仓的解法是：在源头消除，不靠事后检测。** 单一派生源（从 tag 派生）+ 标准工具（包管理器生成 lock）。

**worktree 的猜想是对的**：

- 下游**用固定 commit 引用**（submodule、worktree、写死 sha）时，**"内容变了没有"这个问题不存在**——commit 本身就是内容指纹。
- 真正会漂移的只有：**① 把目录复制走**；**② 跟随可变分支或可变目录**。
- 而规矩里本来就写着：**"下游必须引用固定的 Release 快照，严禁执行期动态跟踪可变目录。"**

**结论：选 A，但理由变了。** 不是"诚实地少一个能力"，而是——**之前那个比版本号的脚本，是在解决一个我们自己制造出来的问题**。正确做法：**把引用方式要求写死（必须按固定 commit 引用）**，漂移在源头就不存在。
