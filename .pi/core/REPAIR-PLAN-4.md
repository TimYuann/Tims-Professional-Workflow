## 2. 先把“适配”限定为载体映射，不许项目文档改库级纪律（问题 ①/⑤）

**Driver 的判断成立**：A→B 可改路径、标题、文件/工单形式、字段所在节、存储与项目的实际写入通道；**不可在 adaptive 版本中改**角色收件四步、完整必需字段、证据身份、有效授权、两轮硬上限、独立判断、写窗、停止/三态与清理边界。B 已有条款与上述纪律冲突，**项目照旧可存在，但不得被用来宣称 TIM 已满足这条纪律**；把冲突原文、受影响环节、选项单列交 Owner。Owner 如想改变库级规则，要走**单独的本库规则修订/版本与独立审查**，不能通过映射表上的“已批准”覆盖当前版本硬边界。Owner 只批准项目 B 增字段、改审批流程或选情况 3 时，无须篡改 TIM 原规则。

**机械边界（只验证形状，不伪称能机器判语义）**：项目的 **A→B 映射表**每行有 `A id / applicability / A producer+step / B canonical locator / required-field locators / B physical writer / authoritative decider / lifecycle / mapped library version+B revision / status`。`status=active` 行仅允许 `carrier`（载体）变更；凡涉及字段不足、权力、门限、判据或状态语义的行必须写成 **`discipline-conflict`，不可标 active，并具名交 Owner**。一个轻量只读检查可从当前 `pipeline.md`/`closure.md` 与角色 §2/§3 取 A id/必需字段，核：适用 id 均有行、每个必需字段有可读 locator、引用能解析、物理写者有权、唯一权威位置/版本存在、没有 active 的 conflict、映射绑定的 TIM 版本/B revision 未漂移。对故意删掉 `blocking` 字段、把 Reviewer→作者完成状态的 fixture 应红；合法的“不同标题/目录/一个项目工单承载两个 A 类型”应绿。**脚本不能证明 B 的文字“完成”在业务上等于独立 `PASS`**：Driver/独立 Reviewer 仍读一次真字段/状态和权限；不借脚本 green 代签。

## 3. 情况选择、映射位置及寿命（问题 ③/④）

Driver **在初次绑定项目、发第一张卡以前**盘 A 的适用类型与 B 的真实文档/权限/保留机制，按“能否实际交齐适用 A 的字段、取回、签收和保全”判断 B **空/薄或厚实**，**不按文件数**：B 有很多页面却容不下独立判断仍是对 TIM 不足的薄；B 小但有版本化 tracker、合规字段和写权可属厚实。Driver 可建议情况 1（先问 Owner 授权），或在 B 厚实走情况 2；情况 3 必须先有 Owner 对改造 B 的明确批准。分类事实由 Driver 核，模式取舍/扩权/项目迁移归 Owner。把判断依据与该次 `B revision` 记在映射自身，不能把“项目有 README”当完成探测。

**初次绑定做一次全量；每批开工/每次消费者用到映射前只核受影响项**：TIM 版本、B 的文档位置/字段/权限/状态语义/保留条件是否变。任一变化则先停止该映射行的下游交接，Driver 仅重算受影响行，通知相关生产者/消费者并取得新接收确认；旧冻结结论仍指向旧 B 版本，不自动沿用。未变的行不每批重做全图；已被接收的批不能因修改配置而悄悄“改写过去”。

**映射表本体必须自说明**：优先落在 B 现有工作流/agent 配置或 tracker 的一个已获授权位置；没有合适容器时，Owner 批准**一份**项目自有的配置文档（如 `docs/document-map.md`），不是新收据或运行底座。其文件头自记：`producer=Driver`、`event=项目接入/映射修订`、`physical writer=本轮唯一授权维护者`、`canonical path=this file`、`version=...`、`retention=仍有被它解释的交付/授权/历史结论时可取回`、`successor/owner=...`。这条**自指元数据**使映射本身有产方/写者/落点/寿命，不递归生成“映射的映射”。项目日后更换维护者由 Owner 指定，Driver 在活跃批次负责触发/写窗；Driver 离开后不能假定它还在维护。`README`/项目规则只保留一条“何时读 mapping”的指针，**角色会话拿到 Driver 已解析的 B 落点与写权，不被迫另读一份核心方法**。
