# 任务分解

> 把工作拆成有序任务，每片可独立验证。

- 阶段：P2　归属角色：`cartographer`　产物：A5

## 什么时候用

- 有契约在手，需要把它变成一组能实现、能测试、能验收的单元。
- 一个任务大到或者虚到不知道从哪下手。
- 工作要分给多个会话或多个工人并行。
- 实现顺序不明显：不确定先做哪一块。
- 需要把范围向人讲清楚，好让对方能说「这不是我要的」。

不适用：单文件、范围显然的改动；或者契约里已经写好了任务清单——那时的活是核对而不是分解。

## 开工前要拿到

- 冻结契约 A4：全局判据从 A4.`done_definition` 来，不自造。
- 已有任务图 A5：同一片工作的现存拆法先读；里面有未完成项时**不许覆盖重写**——那些项可能正在别的会话里施工。先问清楚是接着做完、明确作废，还是把新工作放到别处。
- 拿不到任何一份可读的 A4 就退回。

## 方法

1. **进入只读模式。** 读契约、读要改的那几处代码、认出现有约定、画出依赖、记下风险与未知项。**这一阶段不写实现**，产出是计划，不是代码。
2. **画依赖图。** 谁依赖谁：存储结构 → 类型与接口 → 对外接口 → 调用方 → 界面；旁支是校验逻辑与种子数据/迁移。实现顺序按这张图自下而上。
3. **纵向切。** 不做「先建完所有表、再建完所有接口、最后建界面」，而是「用户能注册」「用户能登录」「用户能建一条任务」这样一条条完整的通路，每条都自带它需要的那几层。
4. **每片写全。** 一段话说清这片达成什么；可判否的验收判据若干条；验证动作（跑什么、看到什么算过、证据将留在哪里）；依赖（片号或「无」）；大致会碰哪些区域；体量估计。计划写预期证据，不预填实际观察；执行者交回的观察另按产物契约记录。
5. **排序与设检查点。** 依赖先满足；每片结束系统都处于可用状态；高风险、最不确定的片排最前（要失败就早失败）；每 2–3 片设一个检查点：跑一遍受影响检查、确认整体可用，再往下走。
6. **照体量表切。** 极小＝单函数或配置；小＝一个组件或一个接口；中＝一条功能通路；大＝多组件功能；超大＝再拆。以下任一条成立就继续切：一次聚焦工作做不完；验收判据写不成三条以内；跨了两个以上互不相干的子系统；标题里出现了「和」。
7. **判断能不能并行。** 安全的并行：互不相干的功能片、已实现功能的测试、文档。必须串行：迁移、共享状态改动、有依赖链的部分。需要协调：共用同一个接口契约的功能——先冻结契约，再并行。
8. **核一遍再交付。** 确认每片都有判据、都有验证动作、依赖顺序正确、没有覆盖别人未完成的计划、没有一片碰超过约五个文件、检查点都在、并且人看过点头了。

当本次诉求只是交付计划时，任务图本身就是交付物；给出 A5 和未解决的问题后停下。实现属于后续明确授权的任务，不因计划已经写完就自动开工。

## 产出

落到 A5：

- `slices`：有序任务清单，每片含目标、验收判据、验证动作、依赖、体量。判据是「每片结束时能跑一个检查」——跑不出来的说明切横了。
- `edges`：依赖边按拓扑序排好，并标明哪些是必须串行（迁移、共享状态）、哪些可并行、哪些需要先冻结共享契约。
- `acceptance`：每片的判据逐条可判否，写明验证动作、可观察终态和预期证据落点，且能追溯到 A4.`done_definition`。追溯不到的任务要么删掉，要么回到契约里补一条。

## 常见做错

- 边做边分解：分解是只读阶段的产物。一边实现一边记待办，等于在错误的图上记录进度，返工时连改哪片都说不清。
- 覆盖一份还有未完成项的旧计划：那些未完成项是别的会话的工作状态，删掉它们等于删掉全库唯一记录这件事的地方。正确做法是停下来问。
- 判据写成「实现某某功能」：无法判否。合格的判据是第三方只凭它就能给出对或错。
- 所有任务都很大：每片都「大」，意味着没人能保证它被独立验证过。正确的信号是标题里出现「和」、判据写不成三条、或者要碰两个不相干的子系统。
- 把测试单独推到最后一大片：那时它已经无法定位哪一步引入了问题。测试要跟着片走，每片自带。
