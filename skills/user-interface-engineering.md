# 界面工程

> 把界面当成一件要被验收的工程产物来做：结构、状态、响应式、无障碍、视觉依据，
> 缺一条都不算做完。

- 阶段：P3　归属角色：`builder`　产物：A6

## 什么时候用

- 改动会渲染给人看：页面、组件、布局、样式、交互、可见状态。
- 要新写组件或页面、改已有界面、加交互或状态、修界面的视觉与体验问题。
- 有人要求「做个界面」「这页不好看」「这里点不动」。

**什么时候不用**：不渲染给人的改动（纯后端、命令行、批处理）——那里没有界面可收尾，
别为了凑一条界面凭据硬套。

## 开工前要拿到

- **A4（冻结契约）**：`done_definition` 里**已经写好这次界面的完成判据**（下面「收尾闸门」那几条，
  或它指向的等价条目）。契约里没有界面判据，就退回给 `architect` 补上——**没有判据的界面改动
  进了 `P5` 也没人知道该验什么**，这一栏空着往下走是最贵的漏。
- **A3（能力地图）**：这个界面挂在哪条能力上，我要落在哪个既有位置上。
- **A5（任务图）**：我负责的这一片。
- 拿不到就退回，并说明这一轮没有可实现的界面面。

## 方法

1. **先分结构，再谈样式。** 一个组件只做一件事；组合优于配置（把内容当孩子传进去，
   而不是给父组件堆上一排 `headerVariant` / `bodyPadding` 之类的旋钮）；一个组件的测试、
   故事、hook、类型跟它放在同一处，拆出去就没人知道它们是一件事的。
   **取数与呈现分开**：容器管数据与四种状态（加载 / 空 / 错 / 有），展示组件只管把给定的东西渲染出来。
   混在一起的组件没法单独测渲染，也没法在换数据源时不动界面。
2. **状态按需要的共享范围往上选，选到刚好够用为止。** 组件自己的界面状态留在组件里；
   两三个兄弟组件要共享就提到共同父级；主题、鉴权、语言这类「读多写少」的用上下文；
   筛选、分页、任何「应该能被分享出去」的界面状态放进地址；
   远端数据交给带缓存的服务端状态层；只有真的全应用共享的复杂客户端状态才上全局 store。
   props 往下穿超过三层就停下来——那说明缺了上面某一档，选它，并说得出为什么本地上升不够。
3. **用项目已有的刻度，不发明数值。** 间距只用现成的间距刻度，字阶按层级用且不跳级，
   颜色用语义记号（正文色、面色、边线色）而不是裸色值，正文对比度不低于 4.5:1、大字不低于 3:1。
   状态不能只靠颜色承载——配文字、图标或形状。凭空写出来的数值和色值，
   下一个界面不会跟着走，这套设计系统就是这么散掉的。
4. **视觉方向要有依据，先写下来再动手。** 产品需要特定视觉方向时：先找可信的参考界面，
   认真研究两三个相关页面，把层级、密度、导航、控件、响应式与交互状态上的决定，
   写成一份短设计契约——**这一页是来干什么的、主操作是什么、必须有哪些状态、
   响应式怎么断、哪些样式明确拒绝**——然后在产品自己的组件、变量、文案与视觉语言里
   重建其中有用的结构。**参考是证据，不是模板**：不复制别家的品牌、专有文案、图像或逐像素布局。
   找不到参考时，把你做的假设写下来，并按产品现有的设计系统核对结果。
5. **避开「一眼是机器生成的」那套外观。** 这不是审美问题，是层级信息被抹平了：
   满屏同色系紫蓝、到处大圆角、通用大标题区、占位文案、到处一样的留白、
   整齐划一的卡片网格、堆阴影。用产品真实的调色板、真实的间距刻度、内容优先的布局——
   真实内容会暴露占位文案藏起来的排版问题（长度、换行、溢出）。
6. **响应式从最窄那一档开始。** 先让最窄视口可用，再往上加宽；不是反过来。
   改动后在 **320 / 768 / 1024 / 1440** 四档各看一遍，这四档是固定的检查点，不是建议。
7. **先把状态补齐，再谈好看。** 加载（内容区用骨架屏而不是转圈；转圈只给不确定时长的短操作）、
   空、错误、成功、无权限——每一种都要有明确的样子**和下一步动作**（重试、去创建、申请权限）。
   缺状态是这类改动最常见的漏项，而且它只有在真实数据状态下才暴露。
8. **交互要经得起只用键盘走一遍。** 每个可交互元素键盘可达（优先用真正的按钮，
   而不是给一个普通容器挂事件处理）；没有可见文字的控件要有可访问名；
   内容变化时把焦点送到该去的地方，弹层打开时要把焦点圈在里面。
9. **交付前过一遍收尾闸门（finish gate），逐条打勾，不许跳：**
   组件渲染无控制台报错与警告 → Tab 能走遍所有交互元素 → 屏幕阅读器能讲出页面结构与内容 →
   四档视口都可用 → 该有的状态齐备 → 遵循项目设计系统（间距、颜色、字阶）→
   自动化无障碍扫描无告警 → 界面专项收尾审查通过。**没过完这一遍就不算做完**，
   别把「看起来正常」当结果。

## 产出

落到 **A6（实现候选）**：

- **`change`**：组件与状态怎么分的（为什么选了这一档而不是更低或更高的一档）、
  取数与呈现的分界在哪、视觉方向的依据是什么（参考了哪些页面、提炼成什么设计契约）、
  以及你做的假设（找不到参考时）。**工作过程建出的每一样东西都点名列进来**——
  组件故事、截图脚本、响应式检查脚本、无障碍扫描配置、一次性对照页。它们不是独立产物，
  但漏列就等于这一轮没人对它们负责。
- **`runnable`**：怎么把它跑起来，**加上收尾闸门九条的逐条结果**——
  哪几条 PASS、哪几条没做、为什么没做。第三方照着这一栏应该能重放整个核对过程。
- **`known_gaps`**：没补齐的状态、没走的那几档视口、没做的键盘与读屏核对，
  以及哪些响应式断点根本没试。**这些正是 `P5` 要复核的地方**，写出来它才知道该盯哪里。
- **`subject`**：**候选的对象身份**——开工时的基线 commit，交付时的结果 commit。
  `P5` 验证的对象必须与它逐字一致。**每个产出 `A6` 的技能都要在交付时填上它。**

界面这一条有个硬联动：`A4.done_definition` 里没有写界面的完成判据，**就不许开工**。
本技能不另立一套「界面做完了」的标准——标准在契约里，这里只负责照着做完并交出证据。

## 常见做错

- **先把界面做漂亮，状态以后再补。** 加载、空、错误、无权限是后加的，形状就永远拼不进去。
- **响应式留到「以后再做」。** 事后补的响应式比一开始就做难得多。
- **props 往下穿了四层还在想办法。** 缺的是上面某一档状态归属，不是再加一层组件。
- **拿别的产品的界面当模板抄。** 抄回来的是别人的品牌、别人的信息优先级，
  和自己的内容对不上，还洗不掉。
- **界面做完了，但契约里没有对应的完成判据。** 结果是 `P5` 不知道该验什么，
  整条界面工作在最后一环失去判据。
- **用「看起来正常」当收尾闸门的结果。** 「正常」不是可判定的观察；
  是截图、控制台读数、四档视口各自的实际状态。
- **把设计系统换成自己的审美。** 产品里已有的刻度、记号、层级就是约束，不是建议。
