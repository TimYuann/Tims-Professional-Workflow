# 安全加固

> 对已知脆弱模式做加固验证。

- 阶段：P5　归属角色：`verifier`　产物：A8

## 什么时候用

- 候选接受任何外部输入：请求体、查询参数、表单、文件上传、回调、消息队列、外部接口返回、模型输出，以及那些「看起来像内部」其实由别的进程写进来的值（另一个进程的命令行与环境、共享卷上的文件名、任务载荷里的路径）。
- 涉及鉴权与会话、敏感数据存储与传输、对外集成、支付与个人数据。
- 要审一个新引入的依赖：它有多大、还在维护吗、有什么已知问题、锁文件里拉进来多少间接依赖、许可证兼不兼容。
- 用户界面上有无障碍与可被绕过的交互（这一面属于同一批脆弱模式：靠颜色单独承载状态、没有键盘可达的交互元素、错误提示不与字段关联）。

## 开工前要拿到

- **A6（实现候选）**：候选的身份，以及本次变更触及的信任边界、资产与入口清单。没有 A6 就无法确定该按哪些模式去验。
- 拿不到就退回，并说明这一轮没有可验的安全面。

## 方法

1. **先做威胁建模，再谈控制。** 四步，五分钟：画出信任边界（不可信数据在哪里进入系统）；点名资产（凭据、个人数据、支付数据、管理员动作、资金流动）；对每条边界过一遍六类威胁——冒充（能否被伪装成用户或服务）、篡改（数据在途中或静止时能否被改）、否认（事后能否不认账）、信息泄露（数据能否被读走）、拒绝服务（能否被压垮）、提权（能否拿到不该有的权限）；为每个功能写一条滥用场景，**并把它写成第一条测试**。说不出信任边界的功能还不该进入加固——大多数事故起于设计而不是代码。
2. **按不可妥协项先过一遍。** 边界处校验一切外部输入；所有查询参数化，绝不把输入拼进查询串或命令；输出编码，框架自带转义不绕过；对外通信走加密链路；口令用慢哈希存，绝不明文；响应带安全头；会话凭据设成不可被脚本读取、仅安全传输、限制同站；每次发布前对**已提交的锁文件**跑包管理器自带的审计。
3. **按需先问的项。** 新增或改动鉴权流程、开始存新类别的个人数据、接入新的外部服务、改跨域配置、加文件上传、改限流、给谁提权——这些不自行决定，先拿到授权。
4. **绝不做的事。** 不把凭据写进版本库；不把敏感数据写进日志；不拿客户端校验当安全边界；不为省事关掉安全头；不把用户数据交给可执行的动态求值或原始 HTML 注入；不把会话存在脚本可读的存储里；不把内部错误细节返回给用户。
5. **重点查几类真会被穿透的地方。** **越权**：每个请求都查权限，而不只查「是不是登录了」——已登录的人必须确实拥有或被允许访问那个具体资源。**注入与跨站脚本**：查出来源（谁写了这个值）而不是来源渠道；外部数据一律不可信。**服务端取回用户给的地址**：这类地址能被指向内部服务——要限定协议与主机，解析全部域名记录并拒绝私有或保留地址，禁止跳转。**破坏性操作作用于派生路径**：删除、移动、覆盖的安全等级只等于给它命名那个值的可信度；执行前要同时满足三件：解析软链后的目标落在允许的根下、比该根至少深一层、有在操作之前读到的归属证据；拒绝时记录被拒的目标并停下，绝不回退到更宽的默认路径。**限流**：多实例时内存计数等于「上限 × 实例数」，在无服务器形态下则等于永不触发——必须挂在共享存储上。
6. **依赖与供应链。** 找到安装边界与包管理器（锁文件、声明的工具管理器、流水线三处一致才动手，不一致就停）；首次执行前拦住依赖的安装脚本，只批准必要的部分，然后用干净的可复现安装验证；审计只匹配已知公告，抓不到新出现的恶意或仿冒包，所以要人看：新依赖、锁文件差异、脚本策略变化一起看所有权、维护状况、发布年龄、传递依赖规模。凡是用强制方式自动修的，都要先看会不会跨过声明的版本范围；每一次延后处理都要写下理由和复审日期。
7. **个人数据与隐私。** 加字段时就分类（非个人 / 个人 / 敏感）——你找不到的数据既保护不了，也履行不了删除请求。只为已声明的目的收集：「以后可能有用」是潜在的泄露范围而不是目的。事先定保留期并真的删得掉，包含备份、缓存、索引、统计副本。导出、更正、删除这三件事要端到端可用。往第三方发个人数据就是共享，要有可审计的同意记录。
8. **模型输出也是外部输入。** 它可能是查询串、脚本标签或命令行；必须先按 schema 防御性解析再编码，权限用代码强制而不是指望提示词；工具参数逐个校验，破坏性动作要确认；上下文里不放密钥、他人的数据和完整系统提示。
9. **顺手过一遍无障碍。** 键盘可达（每个可交互元素都能用键盘到达，优先用真正的按钮而不是带事件处理的普通容器）、可访问名（无可见文字的控件要有标签）、焦点管理（内容变化时把焦点送到该去的地方，弹层要圈住焦点）、对比度达标、状态不能只靠颜色。
10. **用「先破坏再证明检查有效」来验。** 加固是代码，它自己也会写错：造一个能触发该路径的非法输入，跑到它，看它是否真的被挡住；顺手把正确实现改坏一次，看检查会不会变红。只会变绿一次的自检不能证明它可靠。

## 产出

产出 **A8（验证凭据）**：

- **`claim`**：指明它证明的是 A4 里哪一条 `done_definition`（例如「未授权用户无法读取他人资源」），或哪个脆弱模式已被堵住。
- **`observation`**：实际观察——用哪条非法输入打的、返回了什么、哪个文件或行是拦住的、日志里记了什么。对界面项则是实际键盘走一遍的结果、读到的可访问名与对比度读数。
- **`environment`**：在什么环境、什么身份（未登录 / 普通用户 / 被授权用户）、什么数据状态下验的；结论能否外推到生产配置要看什么条件。
- **`verdict`**：PASS／FAIL／UNVERIFIED。环境本身不给这条路径的访问（缺授权、缺外部服务、缺隔离数据）时记 UNVERIFIED，并写清「这条边界没有被验到」——**不许**把验不了判成缺陷，也**不许**判成通过。

依赖类结论要附：审计命令、锁文件版本、每条未处置的问题及其理由与复审日期。

## 常见做错

- **认为「内部工具不用管安全」。** 内部系统同样被攻破，攻击者专挑最弱的一环。
- **在产品代码里改掉脆弱行为来让验证变绿。** 正确做法是把这一条记成缺陷交回去；自己修完再宣布安全通过，验证者就不再独立。
- **只查「登录了没」，不查「有没有权访问这一条」。** 已登录用户读别人数据是越权中最常见的一种。
- **把审计通过当成依赖安全。** 它只匹配已知公告，拦不住新出现的仿冒包，也放行未审过的安装脚本。
- **看到路径形状合法就直接删。** 形状合法只说明拼写没错，不说明谁写的这个值；归属证据要在操作之前读。
- **把验不了的东西算成通过。** 起不来的环境记 UNVERIFIED；把它并进 PASS，安全面从此不可信。
- **把「等有空再清」写进结论。** 延后处理必须有理由和复审日期，否则它会一直延后。
