# 深模块设计

> 用深模块的词汇设计边界与接口，目标是可测试与可替换。

- 阶段：P1　归属角色：`architect`　产物：A4

## 什么时候用

- 要设计或改造一个模块的接口，或者决定接缝落在哪。
- 你想加一个新的可替换点（换个存储、换个外部服务、换个渲染方式），但不确定该不该开这个接缝。
- 代码难测：测试要绕过接口去戳内部，于是测试跟着实现一起变形。
- 一个改动要同时改六个调用方，说明深度加错了地方。
- 审查代码时找不到「问题出在哪个模块」——可变作用域铺得太开。

## 开工前要拿到

- A2 事实集，至少 `claims` 与 `evidence` 有内容。深浅的判断只能对着真实调用方和真实依赖做，
  对着想象出来的调用方做，结论必然偏。
- **拿不到 A2 就退回**。退回去的是「现在谁在调它、它现在依赖谁」还没查；
  不知道现状就去设计新形状，只会设计出另一个没人用的抽象。

## 方法

**这一节是一条持续三个动作的回路：先画，再写，然后一直在场。**
画出来的东西不是画完就归档的参考件，它是实现时要照着填的契约；在场也不是「有空看一眼」，
是整个填装过程中持续对着它做判断。下面先固定词汇，再按三步展开。

### 词汇

**先用对词。** 这一节的整套词汇就是产出的一部分，用别的词替代会让设计讨论滑回泛泛的架构空话。

- **模块**：有接口和实现的东西。故意与规模无关——函数、类、包、跨层切片都算。
  不用「单元」「组件」「服务」。
- **接口**：调用方为了正确使用这个模块必须知道的一切：类型签名，还包括不变量、调用顺序约束、
  错误模式、必须的配置、性能特征。不用「API」，也不用「签名」（太窄，只指类型层那层）。
- **实现**：模块里面的代码。与**适配器**区分：一个适配器可以有大实现（一个数据库仓储），
  也可以是小实现（一个内存假件）。谈接缝时说「适配器」，其它时候说「实现」。
- **深度**：接口处的杠杆。调用方（或测试）学一点接口能驱动多少行为。
  小接口后面藏着大量行为 = 深；接口和实现一样复杂 = 浅。
- **接缝**：能不改那里就改变行为的地方；模块接口所在的位置。接缝落在哪本身是一个设计决定，
  和接缝后面放什么无关。不用「边界」（和领域建模里的限界上下文混了）。
- **适配器**：接缝上满足某个接口的具体东西。描述的是**角色**（填哪个槽），不是内容。
- **杠杆**：调用方从深度里得到的东西。一份实现，在 N 个调用点和 M 个测试上回收。
- **局部性**：维护者从深度里得到的东西。改动、缺陷、知识和验证集中在一处，而不是摊在各个调用方。

**深与浅**
深模块：小接口 + 厚实现。浅模块：大接口 + 薄实现——通常是层层转发。
设计接口时反复问三句：方法能不能再少几个？参数能不能再简单？还能把多少复杂度藏进去？

**四条判据**

1. **深度是接口的属性，不是实现的属性。** 一个深模块内部完全可以由一堆小、可换、可测的零件组成，
   那些零件不是它接口的一部分。模块可以有**内部接缝**（只给自己的实现和测试用），
   也可以有接口处的**外部接缝**。这两层不要混。
2. **删除测试。** 想象把这个模块删掉。如果复杂度一起消失了，它是个转发层；
   如果复杂度在 N 个调用方里重新出现，它在挣自己的饭钱。
3. **接口就是测试面。** 调用方和测试走同一个接缝。
   想越过接口去测内部，多半是模块形状不对。
4. **一个适配器意味着假接缝，两个适配器才是真接缝。** 没有东西真的在这个接缝上变化，就别开它。

**为可测试性设计**
接受依赖而不是自己造；返回结果而不是产生副作用；表面尽量小——
方法少则要写的测试少，参数少则测试的搭装简单。

**问自己这两个问题**
「如果接缝后面换一种实现，接口要变吗？」变了说明实现细节漏进了接口。
「我能不能只通过接口把这个模块测一遍，而不碰它内部任何东西？」不能，说明接口没盖住该盖的东西。

### 第 1 步 · 画

**先写调用方怎么用，再从它反推类型。** 落笔顺序是固定的：调用方的用法（消费者读到的说明
加两三个真实调用点——导入什么、调什么、回来什么）→ 数据形状 → 函数签名 → 模块结构与接缝。
两者不一致时，**以用法为准回头改类型**，不是反过来。调用方的体验就是规格，类型是伺候它的。
函数体先留空（写成 `not implemented`），流程用伪代码占住。改动小就一个文件装下；
改动大就再加一张模块地图加类型定义。

**至少两个结构上不同的整体形状。** 第一个看着够用也要再画一版。要的是整体形状不同，
不是在同一个形状里改点细节——形状是这件事里最难回头的决定，形状错了后面全白写。
（并行的具体做法按 `arena` 走。）

**每一版进合成前先过红旗。** 四类形状直接打回或要求改：

- **浅模块**：接口大、藏起来的东西少。看得见的征兆有三条——调用方要协调好几个方法才完成一件事；
  公开出来的选项暴露了内部阶段或实现选择；学完接口仍然要学实现。
- **信息泄漏**：同一个内部决定在多处被依赖（一个表示、一条策略、一个协议细节出现在不止一个地方），
  改它就要联动改。对外把传输层或存储层的类型再导出出去，就是泄漏。
- **时序分解**：按执行顺序切模块，而不是按它拥有的知识切。加载、校验、转换、存储各成一段时，
  同一份表示和它的不变量会在好几个边界上重复一遍。
- **转发方法**：同样的参数、同样的形状转发给另一个方法，加了一层没藏住任何复杂度。

**深调用链不等于深模块。** 深调用链把理解摊到各层上；深模块把能力收到一个接口后面。
比选时只看接口深度：哪一版把更多复杂度藏在了更小的公开面后面，就选哪一版。

**选完的草图是契约。** 默认直接进实现，不设人工关卡；只有被明确要求时才停在签认点把草图亮出来。
签认点上对方对形状提出异议，等于新的现状信息——回到第 1 步重新对一遍现状再画，不是在草图上打补丁。

### 第 2 步 · 在场

**把留空的函数体换成实现，把伪代码换成逻辑——对着草图填。** 「在场」在这一步的意思是：
实现的每一步都在拿草图当尺子，而不是填完再回头看像不像。

**偏差是信号，不是要吸收掉的摩擦。** 一个函数需要草图没预料到的参数时，不要直接加上，
先在三种可能里判定：草图错了、需求漏了、实现越界。判定结果要落下来：

- 判「草图错了 / 需求漏了」→ 走契约变更回写，不许在实现里静默改形状。
- 判「实现越界」→ 实现改回去。

**同类偏差一次不说明问题，两次以上说明形状不对。** 填装过程中反复要同一类打补丁，
是草图没扛住真实数据的信号，直接进第 3 步。

### 第 3 步 · 回收

**弃用草图的判据是模式，不是个例。** 个别复杂的地方是正常的，数据本身复杂不等于设计复杂。
以下任何一条反复出现，指向的是形状错了：

- 同一种绕行做法在互不相关的代码里反复冒出来。
- 多个互不相关的边界情况各自都要开一条专门分支。
- 类型需要逃生舱（`any`、强制转换、实际上总会赋值因而「可选」的字段）才编得过。
- 草图说过状态不共享，代码里却反复冒出「得加个锁」的反射。
- 调用方得知道抽象的内部规则才能用它。
- 第 2 步里同类偏差出现两次以上。

命中就按顺序来：对着已经建起来的东西重新过一遍现状 → 把新学到的约束当成
「一开始就存在的基本假设」重新设计 → **先减后加**（新版草图必须比旧版更小，之后才允许长回来）
→ 回到第 1 步重画。**不要在错的形状上打补丁。**

### 在场 ≠ 下结论

`architect` 参与实现的整个填装过程，但**不参与对最终候选的裁决**。
在场指的是：对着草图判断、对形状提出异议、把偏差记下来、把弃用触发。
不参与指的是：对自己参与过的实现出 PASS／FAIL／挑战这类判断——
「我写的，我看好」把判断和实现绑在了一起，这条绑定的破除靠的是裁决者与候选分离。
最终候选由没写过它的人裁，裁判的输入里带不带你的在场记录可以，结论不由你下。
在场的全部记录进决策台账，台账是追加的；记录不是盖章。

**在场的分工**：改形状的决定回写契约，触发回收的决定连同理由进台账。
**裁决的分工**：按 `code-review`／`interrogate` 出结论，本节不产出结论。

## 产出

A4 冻结契约，字段落法：

- `what`：用深模块词汇写建什么：哪些模块、每个模块的接口是什么、接缝落在哪、每个接缝上现在有谁在当适配器。
  合格形态是每个模块都能对着上面四条判据过一次。前面还要附上**调用方的用法**（说明加两三个真实调用点），
  类型与签名从它反推；小改动一个文件装下，大改动另附模块地图与类型定义。
- `why`：写深度的理由，不写「结构更清晰」。写清楚**深在哪**：哪一大块行为被藏进了小接口后面，
  现在有哪几个调用方和哪几个测试在回收这份深度。**另附至少一个具体备选形状**，
  每个一行落选理由，并且按接口深度判（说清它把什么暴露给调用方、藏起了什么），不只看实现简不简单；
  约束逼得没有选择余地时，写成「只有这一种可行，因为……」。再附上这一版接受的取舍
  （形式：拿 X 换 Y），包括以后的人可能误读成疏漏的地方。
- `done_definition`：可判定的接口口径，判据是调用方需要知道的事实条数下降，以及
  「越过接口去测内部」这件事被消除。每条口径写成可观察的样子（某个测试现在能只通过接口驱动某个行为）。
- `boundaries`：写死**哪些东西属于接口、哪些属于实现**。这一栏要明确：
  内部接缝不对外承诺；接口后面换实现不许顺带改接口；不许为了少一个方法而把复杂度摊回 N 个调用方。
  草图里判为「不做」的项原样进这一栏，实现期发现少做一项就走契约变更，不许在实现里默默扩大范围。

在场期间的两类记录各自落法：**改形状的决定回写契约字段**（走变更，不静默改），
**触发回收的判断连同理由进决策台账**（只追加）。在场的产出到记录为止，不出裁决。

## 常见做错

- 把「深」当成实现行数除以接口行数：这个算法奖励把实现写胖。
  深度是接口处的杠杆，不是行数比。
- 该用「接缝」的地方说「边界」：两个词在一个文件里指两件事，
  讨论会自动滑向领域建模，而这一节要谈的是替换与测试面。
- 为假想的可替换性开接缝：现在只有一个适配器，说明这里还没有东西会变。
  开出来的接缝是一层没人会换的间接层。
- 用「组件」「服务」「API」这些词：它们不区分接口与实现，于是讨论无法落到深度上。
- 追求把复杂度从模块里推出去：把分支从模块内部挪到 N 个调用方，
  局部性没了，杠杆也降级了——那不是简化，是卸载。
- 一次设计只给一个方案：接口形状是这件事里最难回头的决定，
  值得先按放射性的不同思路各出一个，再按深度、局部性、接缝位置比选。
- **画完就走**：草图交了差就当它不存在，实现阶段对着它填不出来的地方随手改。
  这条回路的第二个动作「在场」被跳过，等于第一个动作退化成一份没人对照的文档。
- 把草图当参考不当契约：出现偏差时的默认反应应该是判定（草图错了／需求漏了／实现越界），
  而不是吸收。每吸收一个偏差，草图离真实需求就远一步。
- **把深调用链当成深模块**：调用链长只说明理解被摊到了各层。判深度看的是公开面后面藏了多少。
- 按执行顺序切模块：加载、校验、转换、存储各成一段，同一份表示和它的不变量在每个边界上重复一遍，
  改一条不变量要改四个地方。
- 拿几只不相关的边界情况就宣布设计作废：弃用判据是模式不是个例。数据本身复杂不等于设计复杂。
- **自己给自己写的实现盖章**：在场记录里写「这版没问题」是可以的，出 PASS／FAIL 不是。
  结论交给没写过它的人。
