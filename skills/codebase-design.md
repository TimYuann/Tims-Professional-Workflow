# 深模块设计

> 用深模块的词汇设计边界与接口，目标是可测试与可替换。

- 阶段：P1　归属角色：`architect`　产物：A4

## 什么时候用

- 要设计或改造一个模块的接口，或者决定接缝落在哪。
- 你想加一个新的可替换点（换个存储、换个外部服务、换个渲染方式），但不确定该不该开这个接缝。
- 代码难测：测试要绕过接口去戳内部，于是测试跟着实现一起变形。
- 一个改动要同时改六个调用方，说明深度加错了地方。
- 审查代码时找不到「问题出在哪个模块」——可变作用域铺得太开。

## 开工前要拿到

- A2 事实集，至少 `claims` 与 `evidence` 有内容。深浅的判断只能对着真实调用方和真实依赖做，
  对着想象出来的调用方做，结论必然偏。
- **拿不到 A2 就退回**。退回去的是「现在谁在调它、它现在依赖谁」还没查；
  不知道现状就去设计新形状，只会设计出另一个没人用的抽象。

## 方法

**先用对词。** 这一节的整套词汇就是产出的一部分，用别的词替代会让设计讨论滑回泛泛的架构空话。

- **模块**：有接口和实现的东西。故意与规模无关——函数、类、包、跨层切片都算。
  不用「单元」「组件」「服务」。
- **接口**：调用方为了正确使用这个模块必须知道的一切：类型签名，还包括不变量、调用顺序约束、
  错误模式、必须的配置、性能特征。不用「API」，也不用「签名」（太窄，只指类型层那层）。
- **实现**：模块里面的代码。与**适配器**区分：一个适配器可以有大实现（一个数据库仓储），
  也可以是小实现（一个内存假件）。谈接缝时说「适配器」，其它时候说「实现」。
- **深度**：接口处的杠杆。调用方（或测试）学一点接口能驱动多少行为。
  小接口后面藏着大量行为 = 深；接口和实现一样复杂 = 浅。
- **接缝**：能不改那里就改变行为的地方；模块接口所在的位置。接缝落在哪本身是一个设计决定，
  和接缝后面放什么无关。不用「边界」（和领域建模里的限界上下文混了）。
- **适配器**：接缝上满足某个接口的具体东西。描述的是**角色**（填哪个槽），不是内容。
- **杠杆**：调用方从深度里得到的东西。一份实现，在 N 个调用点和 M 个测试上回收。
- **局部性**：维护者从深度里得到的东西。改动、缺陷、知识和验证集中在一处，而不是摊在各个调用方。

**深与浅**
深模块：小接口 + 厚实现。浅模块：大接口 + 薄实现——通常是层层转发。
设计接口时反复问三句：方法能不能再少几个？参数能不能再简单？还能把多少复杂度藏进去？

**四条判据**

1. **深度是接口的属性，不是实现的属性。** 一个深模块内部完全可以由一堆小、可换、可测的零件组成，
   那些零件不是它接口的一部分。模块可以有**内部接缝**（只给自己的实现和测试用），
   也可以有接口处的**外部接缝**。这两层不要混。
2. **删除测试。** 想象把这个模块删掉。如果复杂度一起消失了，它是个转发层；
   如果复杂度在 N 个调用方里重新出现，它在挣自己的饭钱。
3. **接口就是测试面。** 调用方和测试走同一个接缝。
   想越过接口去测内部，多半是模块形状不对。
4. **一个适配器意味着假接缝，两个适配器才是真接缝。** 没有东西真的在这个接缝上变化，就别开它。

**为可测试性设计**
接受依赖而不是自己造；返回结果而不是产生副作用；表面尽量小——
方法少则要写的测试少，参数少则测试的搭装简单。

**问自己这两个问题**
「如果接缝后面换一种实现，接口要变吗？」变了说明实现细节漏进了接口。
「我能不能只通过接口把这个模块测一遍，而不碰它内部任何东西？」不能，说明接口没盖住该盖的东西。

## 产出

A4 冻结契约，字段落法：

- `what`：用深模块词汇写建什么：哪些模块、每个模块的接口是什么、接缝落在哪、每个接缝上现在有谁在当适配器。
  合格形态是每个模块都能对着上面四条判据过一次。
- `why`：写深度的理由，不写「结构更清晰」。写清楚**深在哪**：哪一大块行为被藏进了小接口后面，
  现在有哪几个调用方和哪几个测试在回收这份深度。
- `done_definition`：可判定的接口口径，判据是调用方需要知道的事实条数下降，以及
  「越过接口去测内部」这件事被消除。每条口径写成可观察的样子（某个测试现在能只通过接口驱动某个行为）。
- `boundaries`：写死**哪些东西属于接口、哪些属于实现**。这一栏要明确：
  内部接缝不对外承诺；接口后面换实现不许顺带改接口；不许为了少一个方法而把复杂度摊回 N 个调用方。

## 常见做错

- 把「深」当成实现行数除以接口行数：这个算法奖励把实现写胖。
  深度是接口处的杠杆，不是行数比。
- 该用「接缝」的地方说「边界」：两个词在一个文件里指两件事，
  讨论会自动滑向领域建模，而这一节要谈的是替换与测试面。
- 为假想的可替换性开接缝：现在只有一个适配器，说明这里还没有东西会变。
  开出来的接缝是一层没人会换的间接层。
- 用「组件」「服务」「API」这些词：它们不区分接口与实现，于是讨论无法落到深度上。
- 追求把复杂度从模块里推出去：把分支从模块内部挪到 N 个调用方，
  局部性没了，杠杆也降级了——那不是简化，是卸载。
- 一次设计只给一个方案：接口形状是这件事里最难回头的决定，
  值得先按放射性的不同思路各出一个，再按深度、局部性、接缝位置比选。
