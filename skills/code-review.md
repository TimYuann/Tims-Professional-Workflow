# 双轴审查

> 相对一个固定基点，沿标准轴与意图轴两条线审。

- 阶段：P4　归属角色：`adversary`　产物：A7

## 什么时候用

- 手上有了一个可被独立评价的实现候选 A6，需要判断它收不收。
- 变更相对某个基点可数：能取出「基点 → 当前」之间的完整改动集，而不是零散几段粘贴。
- 「写法不合本仓规范」和「做的不是要的那个」这两类问题需要分开摆清楚——它们互相不能抵消。
- 实现者之外的任何人第一次完整读这个候选，准备给出裁决之前。

## 开工前要拿到

- **A6（实现候选）**：至少要能确定被审对象的身份与改动范围。没有 A6 就没有「审的是哪一份」，不开工。
- **A4（冻结契约）**：意图轴的全部依据。`done_definition` 决定「做的是不是要的那个」，`boundaries` 决定「多出来的东西」算不算越界。
- 拿不到 A4 就退回：只报标准轴，并把意图轴标成「无契约可比」。此时给出的「附条件通过」是空条件，不算真条件。

## 方法

1. **钉住基点。** 固定点由发件方指定（提交、分支、标签、合并基点）。先确认这个引用能解析，再确认改动集非空——引用错了或改动为空，要在这里失败，不要等到两个审查上下文里才失败。
2. **定位意图的来源。** 依次找：提交信息里引用的需求编号、对方给的文件路径、仓内与分支名或主题匹配的规格文件。找不到就不要猜——标「无规格可比」，让意图轴只做范围检查。
3. **定位规范来源。** 仓内任何写着「代码该怎么写」的文件（贡献指南、风格约定、工程规范）。除此之外，标准轴固定带一份与语言无关的坏味道基线（神秘命名、重复逻辑、依恋情结、数据泥团、基本类型偏执、重复分支、霰弹式修改、发散式修改、过度抽象、长链调用、纯转发、拒绝继承）。
4. **让仓内规范压过基线。** 文档化的规范永远优先；基线只在仓里没写的地方补位。基线上的每一条都标成「疑似」而不是「违规」——它是启发式，不是判决。
5. **两条轴在互不污染的上下文里各跑一遍。** 需要一个能把材料路由出去的执行环境（能创建独立 pane 或独立上下文、把提示投进去、把结果取回来的那种）。标准轴拿改动集、规范文件清单、以及**完整粘贴的**基线（它没有别的渠道拿到基线）；意图轴拿改动集与规格原文。两边各写自己的报告。
6. **汇合，但不合并、不重排。** 两个报告分节呈现。理由：一条轴通过、另一条轴不通过是完全可能的，合在一起报等于让一条轴掩盖另一条。最后各给一句小结：这条轴上最严重的问题是什么。不要在两轴之间挑唯一赢家。
7. **核实验证故事。** 读了测试才知道作者声称了什么。检查：改动有没有对应测试、测试断的是行为还是内部、构建过没过、有没有界面证据、改动前后对比。声称跑过而拿不出观察的，按「未验证」记，不按「通过」记。
8. **给严重度标签。** 阻断合并的（缺陷、数据丢失、越权、契约违反）、必须改的（可修的实质问题）、值得考虑的、可忽略的。每条标注它属于哪条轴。这样作者不会把全部意见当成同等强制。

## 产出

产出 **A7（裁决）**，三个字段逐条填满：

- **`stance`**：采纳／挑战／附条件通过。标准轴干净而意图轴有实质缺口，就不能是「采纳」；两轴都只是偏好层面的不满，也不是「挑战」。
- **`reason`**：每个结论都要能指到改动集里的具体位置，并指明它违反了哪条规范或哪条 `done_definition`。写不出位置的怀疑，标成待查，不进结论。上游的双轴分离要保留在 reason 里：标准轴的理由和意图轴的理由分开写，不合成一段。
- **`conditions`**：附条件通过时逐条写「改什么、谁验收」。条件要可判定到能回答改没改完；「优化一下」「注意质量」不是条件。条件为空却给了「附条件通过」，属于自相矛盾，退回重判。

## 常见做错

- **把两条轴揉成一张按严重度排序的清单。** 排序就是掩盖：意图轴的致命项会被压到标准轴的十条小意见下面。分节呈现是这套方法唯一不可让的部分。
- **意图轴在猜意图。** 没有规格就把自己的推测当规格用，最后必然得出「这不符合要求」而其实只是没找到原文。要么拿到契约，要么明写无契约可比。
- **审查者替作者改代码。** 一次审查只出裁决与条件；顺手改完再给通过，评价者就不再独立。
- **只跑一次自动检查就说审过了。** 自动检查能判的只是其中一小部分；架构、意图、验证故事都没有被它覆盖。
- **给「附条件通过」但条件不可判定。** 下游收到的是一个无法验收的裁决，条件就退化成一句愿望。
