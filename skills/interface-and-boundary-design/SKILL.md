# Interface & Boundary Design · 接口与模块边界设计技能

## 概述
当设计新模块、重构现有架构或定义跨系统 API 时调用本技能。融合了 John Ousterhout 的“深模块”思想与 `pstack` 的“非法状态不可表示”原则，**确保小接口承载大能力，内部复杂度不向调用方泄漏**。

## 核心操作规程（Process）

### 步骤 1：调用方视角先行（Write the Callers First）
- 严禁先从内部实现或数据库字段开始构思；
- 首先写出调用方最理想的使用代码（2-3 行极简调用）：
  - 检查调用方是否需要知道内部时序（如“必须先调 init 才能调 run”）；
  - 检查调用方是否需要捕获繁杂的底层异常；
  - 努力将时序与状态收进模块内部，提供简洁有力的接口。

### 步骤 2：使非法状态不可表示（Make Illegal States Unrepresentable）
- 利用语言类型系统（TypeScript 判别联合 Union / Python 数据类枚举）：
  - 表达严格的业务状态，使得“既成功又有错误码”或“有支付凭证却没有订单 ID”这种荒谬状态在编译期就无法通过；
  - 边界处严格解析（Parse, don't validate），内部纯函数安全信任入参类型。

### 步骤 3：强制双重设计对比（Design-It-Twice + 第三基准）
必须对比至少 3 个方案：
- **方案 A（深度重构方案）**：创建全新抽象，彻底隔离旧逻辑；
- **方案 B（演进结构方案）**：在现有数据流基础上进行正交解耦；
- **方案 C（Astra 关键基准：维持现状或做最小局部修改）**：
  - 严谨评估：“维持现状是否足够好？”
  - 如果新抽象带来的概念复杂性超过了其隐藏的复杂度，**坚决退回方案 C**！

## 反借口与典型红线（Common Rationalizations & Red Flags）

| 典型借口 / 行为偏差 | 严厉反驳与纠偏纪律 |
| :--- | :--- |
| “我写了一个只包装了内部函数一行的中间类，这是为了扩展性” | **浅模块害死人！** 这只是无谓的转发层，增加了代码行数却没有隐藏任何复杂度，立即拍扁！ |
| “虽然现在的接口很别扭，但我可以在文档里写清楚调用顺序” | **代码设计缺陷不能靠文档弥补！** 调用方一旦忘记顺序就会崩溃，必须通过接口强约束时序。 |
| “我就试一个方案，直觉告诉我它是对的” | **违反纪律！** 必须写出结构迥异的第二个备选方案并对比权衡。 |

---

## 退出判据（Exit Criteria）
- [ ] 调用方示例代码清晰极简，不暴露内部私有状态；
- [ ] 核心类型定义完成，排除了明显的非法状态组合；
- [ ] 完成包含方案 C（维持现状基准）的对比说明，形成接口设计草案。
