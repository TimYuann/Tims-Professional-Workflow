# 版本与提交结构

> 组织提交、分支与版本，使每个提交可独立验证。

- 阶段：P6　归属角色：`verifier`　产物：无

## 什么时候用

- 要把一批改动切成可独立验证、可独立回滚的单位：提交、分支、待合并请求。
- 工作区里有几处不相干的改动，需要拆成干净的原子提交。
- 一切对外发布：选版本号、打了标签、写变更日志。

## 开工前要拿到

- **A5（任务图）**：片与依赖边。每个提交要对应哪一片、哪些片必须在一个提交里，这决定堆叠顺序。
- 拿不到就退回：没有片的边界，提交就退回成「把手上改的都提交了」，这正是这里要防的事。

## 方法

1. **主线随时可发布，分支短命。** 长期开发分支是隐藏成本：它会分叉、冲突、拖慢集成。分支从主线开出，一到三天内合回去；合并后删掉。未完成的功能优先用开关带着上线，而不是在分支上挂几周。
2. **每个可验证增量一个提交。** 工作方式是「做一片 → 验 → 提交 → 下一片」，不是「全做完 → 希望它是对的 → 一个巨型提交」。提交是存档点：下一步搞坏了，立刻退回已知良好的那个点。这就是存档点模式——一个存档点出了问题就复位到上一个提交去查，而不是在当前状态上继续猜。
3. **一个提交只做一件逻辑上的事。** 混着改格式化、加功能、升依赖、挪工具函数的提交既审不了也退不了。重构与新行为是两个变更，分开交（小的顺手清理可以并进功能提交）。目标规模：约 100 行很好；约 300 行可以，前提是一个逻辑变更；上千行就该拆。
4. **提交信息写「为什么」。** 首行是短句祈使、能脱离上下文看懂（不是「更新了某个文件」）。正文补上代码里看不见的东西：为什么需要、依据是什么、否决了什么方案、关联的缺陷或度量。类型前缀用固定集合：feat／fix／refactor／test／docs／chore。
5. **并行时用互相隔离的副本。** 多条工作流同时改不同分支时，用各自的隔离工作副本（各自目录、各自分支），不切分支、不共享工作区。某个方向失败了直接删掉那个副本，没有损失。
6. **每次提交前过一遍。** 看清将要提交的内容（暂存区的实际差异）、在里面搜一遍凭据形态的字样（口令、密钥、令牌）、跑一遍测试与静态检查。大件工作目录与构建产物必须被忽略清单覆盖。
7. **并行编辑冲突按结构解，不按标记解。** 两个并行写同一份状态时，先想办法消掉共享，实在消不掉再按结构串行化——这比一次一次地解冲突更省事。解冲突时不要顺手采纳任一侧：回到 A4 的契约，看这段代码本该是什么。
8. **版本号是给消费者的承诺。** 对外有消费者的东西用「主版本.次版本.修订号」：破坏性变更升主版本，向后兼容的新功能升次版本，修 bug 升修订号。**看起来像修订号、实际改了消费者依赖的行为，就是伪装成小版本的破坏性变更**。拿不准时当它是破坏性的。
9. **标签是真源，版本号从标签派生。** 发布是一个不可再移动的历史点，不是一条会移动的分支。给它打标签并推上去，版本号从标签派生而不是手改各处的文件，这样制品、标签、变更日志三者永远不可能对不上。改动文件的哈希锁进历史并提交；锁文件手改是不允许的，因为它是钉住实际出货内容的那件东西。
10. **变更日志是写给人看的，不是提交日志。** 按「新增／变更／修复／弃用／移除／安全」分组，最新在上，每条都围绕用户影响来写而不是内部机制。**在做出这个变更的同一次里写**，那时影响还新鲜；留到发布时再从提交里考古，重要的那半已经丢了。破坏性变更要配迁移说明和弃用窗口。
11. **每次改完给一张结构化的改动说明。** 三段：改了什么（逐文件、逐处）；**故意没动的**（同类问题存在但不在本次范围）；潜在顾虑（新加的依赖多大、新方案收紧了什么）。第二段尤其重要：它证明这次是被范围纪律管着的，而不是顺手巡检改了一圈。

## 产出

本技能不产出 A8 类的凭据；它交付的是版本控制层的结构，随决策台账留存：

- 提交序列：每个提交一行——它对应 A5 的哪一片、做了哪一件逻辑事、验证到哪一步。
- 分支与合并：分支名、开出点、合并点、存续时长。
- 忽略清单的覆盖范围，以及本轮是否发生凭据形态内容的误入（若有，写明处置）。
- 发布时：版本号及其依据（破坏性／新增／修复）、标签名、变更日志条目、以及「故意没做的」那一段。
- 未提交残留的清单：有就写明为什么留着。

## 常见做错

- **攒到最后一次性提交。** 一个巨型提交审不了、定位不了、退不了；存档点越多，坏掉时损失越小。
- **提交信息只写「改了文件」。** 提交信息是文档，将来的人和下一个会话都要靠它理解为什么；只复述 diff 等于没写。
- **把重构和新行为混在一个提交里。** 它既不是独立可验证的单元，回退时也带不回另一件事。
- **小 bug 就升修订号。** 先看消费者能观察到什么；他们依赖的行为变了就是破坏性变更，与 diff 大小无关。
- **发布只写「依赖升级」。** 依赖升级是别人写的行为变更：读变更说明（修订号也可能带行为变化），一个依赖一个变更来合，锁文件的传递差异也要看。
- **变更日志留到发布时补。** 那时影响已经在记忆里散了一半，而且是从提交里倒着推的。
- **手改版本号或锁文件。** 三处（制品、标签、日志）从此可能永久不一致，且没人知道哪个是对的。
