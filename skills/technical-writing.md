# 技术写作分层

> 分层的技术写作标准：教程 / 参考 / 说明 / 决策。

- 阶段：横切带　归属角色：`driver`　产物：无

## 什么时候用

- 要写或改任何一份给人读的文档：说明、计划、提案、变更请求、变更记录、仓库首页的说明。
- 一段文字读了两遍还是读不懂：先怀疑混了两种模式，再怀疑句子。
- 收口汇报、变更请求描述、给新来者看的上手材料——它们各有各的模式，不能用同一套语气写。

## 开工前要拿到

本技能的 `inputs` 为空——它是写作规范。开工前要确定两件事：

- **这份文档属于哪一层**。四层各回答一个问题：内容是驱动动作还是提供理解？服务学习还是服务工作？两个问题定一层，一份文档一层。
- **读者要拿它干什么**。要照着做、要查一件事、还是要理解为什么。这三种对应不同的层，写法完全不同。

## 方法

**先选层。** 一份文档，一种模式：

- **教程** —— 动作 + 学习。你是老师，读者做成事是你的责任。开头写他会做出什么，不写他会「学到」什么。每一步都尽快产生一个看得见的结果，并告诉他应该看到什么：预期的输出、界面上的变化、日志里多出来的那行。解释压到一个从句加一个链接；教学式的停顿会打断课。始终具体。用「我们」，写成命令。
- **参考** —— 理解 + 工作。只描述，不描述以外的任何东西：不指导、不劝说、不发表意见。要干、要准。镜像被描述对象的结构，让代码和文档能对着导航。尽量从代码生成，让它保持为真。
- **说明** —— 理解 + 学习。围绕一个有界的主题，离开这个产品也能读。每个标题前面加一个「关于」都还成立。锚在一个真实的「为什么」上：设计决策、历史、约束、被否掉的方案。这一层可以有观点，别的地方不行。
- **决策** —— 把一个决定连同当时的约束、备选和代价写下来，供后来者查为什么长成这样。写清它决定了什么、当时的依据是什么、否决了什么、以及什么条件下这个决定应该被重开。判据是后来者能否只凭它复述当时的取舍，而不是复述结论。

**不混层**。教程里塞参考表、参考里塞手把手、说明里吵架——拆开、互相链接。宁可多一篇，也不要一篇里四种读者。

**句子写给读者。**

- 用「你」，用现在时。真的是以后才发生的事才用将来时。
- 说出谁做了什么：「编译器检查」，不是「被检查」。施动者未知或不重要时才用被动。
- 指令写成命令：「点击提交」。事实直说。永远不要写「应该被……」。
- 条件写在指令前面：「要删除该文档，点击删除。」读者会跳过不适用于自己的部分。
- 常用的情况写在前面，例外写在后面。
- 写得像一个懂行的朋友：不要行话，不要比喻，指令里不要「请」，程序步骤里永远不要「简单地」「容易地」「快速地」——真简单的话读者不会来这里。

**一次只装一件事。**

- 指令一句一个动作；其余句子一句一个想法。承载两个想法的句子拆开，承载一个想法的长句子留下。
- 警告或条件写在它守护的那一步前面。
- 「删掉备份文件」有两种读法，「删掉那个备份文件」只有一种。留着「那个」和「一个」。
- 一个动作只用一个词：「启动」，不要这里写启动、那里写初始化。
- 能不用就不用「-ing」式的词——它们的语法岗位太多，容易被读错。

**不给任何句子留第二种读法。**

- 「只」「不」紧挨着它们修饰的那个词：「只在增长时失败」和「只在……才失败」是两句话。
- 拆开名词串：「proto 导入预算检查脚本」→「检查 proto 导入预算的脚本」。
- 让每个「它」「他们」「这个」只指向一个东西；拿不准就重复那个名词。绝不让「这个」指向一整个从句。
- 不丢动词：「第一阶段迁移转换器，第二阶段运行时」把第二阶段的宾语丢了。给它一个。
- 保留那些表示结构的小词。为了少几个字牺牲唯一读法，是这笔交易里唯一不能做的。
- 并列时重复那个「那个」：「客户端和主机」，不是「客户端和主机」——当它们是两个东西的时候。
- 说清「和」「或」连的是哪一部分：「a、b，或者两者」。
- 用句号，不用分号。破折号改成另起一句。括号里的内容要是一个完整语法单位或独立成句。
- 不用斜杠：写「a、b，或者两者」，不写「a/b」「and/or」。
- **一件事只叫一个名字，到处都这么叫**。一份文档里同一个东西被叫作三个名字，就是教会了读者三件事。另外，改稿时把没改动的句子重写一遍，代价和上面一样大。

**以上规则之上还有三条。** 砍掉不做工的每一个词（去掉「为了」「需要注意的是」之后句子还成立，那个词就走）。用短的日常词（用，不要「利用」；做，不要「执行」——长词要用它的长度买到精确）。**当一条规则把句子弄得更差时，换个办法改，或者不改**——规则服务读者，一个遵守了全部规则却读起来像机器写的句子，已经失败了。

**仓库就是词表。** 写真实的符号名、文件名、开关名、命令名，不用同义词或对它的描述。不生造行话；一个被命名过的模式，第一次出现时要说清它是什么意思。**节奏也要有意为之**：长短句混用——短句落点，长句带着条件和后果把一个事实讲完。有观点的地方（说明层、决策层）就把你的判断说出来，而不是罗列利弊。

**变更请求描述也是写作。** 除了选层，其余各条都适用。它是一份一分钟能读完的简报：不要粘日志、编号清单、指标表——链接过去。每一处计数、每一句树结构的描述，在它落地的那个提交上都得为真，并附上重新生成它的命令。

## 产出

无产物——它改变的是判断，不是文件。

它改变的是写出来的文字本身：选了哪一层、句子怎么切、哪里留了第二种读法。判定它做完了的标准：随便抽三句，每句只有一种读法；整篇只有一种模式；所有名字与仓库里的真实符号逐字一致；所有计数在落地的提交上为真。

## 常见做错

- **一层写到底**。手把手混着参数表，读者要么读得太浅要么读不进去。正确是拆成多篇互相链接。
- **指令写成被动或「应该」**。「组件必须先安装」读者会问：谁来装？正确是「安装该组件」。
- **该近的词离得太远**。「只在失败时」和「失败只在」意思不同，而「不」离它修饰的词太远时会滑到别的词上。正确是把它挪到该在的位置。
- **把没改的句子也重写一遍**。每一处改写都是一次引入新错误的机会，代价和改掉的一样大。正确是没动的地方不动。
