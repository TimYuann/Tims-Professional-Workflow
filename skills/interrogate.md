# 多模型对抗

> 每个模型拿同一份提示与评分表，从独立角度挑战同一个变更。

- 阶段：P4　归属角色：`adversary`　产物：A7

## 什么时候用

- 同一个候选需要不止一种判断倾向去挑毛病：单一口径容易把「自己也会犯的错」漏过去。
- 变更够大，值得用多个彼此独立的上下文各读一遍——因为两个共享同一套先验的判断，看不见彼此的盲区。
- 常规双轴审查给出的结论过于「稳」，需要一个不带既有立场的一遍来交叉。
- 需要的是「多份独立意见的合并」，不是「一次更狠的审查」。

## 开工前要拿到

- **A6（实现候选）**：改动集或候选正文，加上看懂它所需的周边文件。拿不到就不开跑——没有对象的挑战不产出任何东西。
- 拿不到就退回，并把 A7 标成未出具，而不是先出意见再补对象。

## 方法

1. **定范围。** 对方点名的文件或改动集就是范围；点的是特性分支就取它相对基点的全量改动集；只提到「最近那件事」就去把相关文件收齐。范围写死，不要让每个审查者各自决定看什么。
2. **先把意图写成一段话。** 从对方的话、提交信息、变更说明和代码本身推出这段意图，在开跑之前写完。推不出来就先回去问，不要把猜测当意图发给审查者。
3. **同一份提示，逐个座位。** 每个座位拿完全相同的四样东西：意图、改动集、评分表、代码质量视角。座位之间唯一的差别是判断所用的模型档位——对抗信号来自多样性，不来自写进提示里的人格设定。需要一个能把同一段提示分发到 N 个独立上下文、并把各自报告收回来的执行环境。
4. **每份提示里不含「谁在写」这类信息。** 提示里出现结论、出现「我认为这没问题」，回来的就是对你结论的附和，不是独立判断。
5. **合成，不是投票。** 四步：抽出全部发现 → 标出被两个以上座位独立提出的（信号最高）→ 把措辞不同但同一件事的发现合并、记下是谁提的 → 标出座位之间的直接分歧（分歧本身就是给裁决的上下文）。
6. **落定判断。** 把每条发现归到四档：要处理（影响正确性、安全或可维护性）／可以考虑（成立，但现在改的代价大于收益）／已记录（技术上成立但当前阶段不 actionable）／已驳回（错的、吹毛求疵的、缺上下文的），每条附一行归类理由。
7. **对驳回给出理由。** 驳回是判断，不是丢弃；没有理由的驳回等于没读过。

## 产出

产出 **A7（裁决）**，结构固定为七块：意图 / 各座位发现数 / 要处理 / 可以考虑 / 已记录 / 已驳回 / 一致性图。

- **`stance`**：要处理档非空时不能是「采纳」。多条独立座位同时提出的发现，直接进要处理档。
- **`reason`**：每条发现都要标「哪个座位提出的 + 归到哪档 + 一行理由」，并且至少有一条指向 A2 里的证据或一次真实运行的观察。只有座位数、没有证据的裁决不成立。
- **`conditions`**：要处理档的每一条转成可判定的条件，注明要改哪一块、由谁复验。驳回档不写进条件——写进去等于让人去满足一条你已判为错的要求。
- 一致性图要写清楚：哪些点全部座位一致、哪些点分岔、分岔模式本身说明了什么（多数座位共同盲区，或某座位缺上下文）。

## 常见做错

- **给每个座位配不同人格或不同关注点。** 对抗信号来自模型多样性；一旦提示不同，报告就在比谁更关注自己被指定的那件事，交叉验证失效。
- **投票决胜。** 三个座位同意不等于正确——它们可能共享同一个盲区。同意只用来排优先级，不用来替代证据。
- **把意图段漏掉或不写。** 审查者会按自己的猜测补上意图，然后批评你没做到它猜的那个需求。
- **把合成变成转发。** 直接把 N 份原始报告拼起来不下判断，等于把裁决策定的责任推给了下游。
- **静默地只跑了一个座位。** 交出的报告写着「多模型对抗」，实际是单次审查。跑了几席要写进报告。
