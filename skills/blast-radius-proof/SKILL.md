# Blast Radius Proof · 影响面代码可验证证明技能

## 概述
当修改底层共享函数、全局状态、公共配置文件或核心库依赖时调用本技能。来自 `pstack` 的核心硬纪律——**“不相信任何纸面上的影响分析说明书”**。一份听起来合理的分析报告毫无价值，必须找出变更安全性所依赖的关键事实，**通过运行真实代码或测试来客观证明它**。

## 核心操作规程（Process）

### 步骤 1：超越简单的 Grep 调用者清单
- 列出一堆文件被调用了毫无意义；
- 深入排查符号搜索（Grep）看不见的隐蔽传播路径：
  - 动态反射调用；
  - 序列化数据（JSON / Protobuf）跨进程传输；
  - 数据库字段读取与迁移依赖；
  - 环境变量与隐式配置生命周期。

### 步骤 2：提炼核心安全前提（The Key Safety Facts）
- 审视这个改动：**“我们声称这个改动是安全的，根本上取决于哪 1–2 个核心事实？”**
  - 例如：*“事实 1：所有调用方在入参为 null 时都已经做好了兜底处理”*；
  - 例如：*“事实 2：上游网关在转发请求前已经剥离了敏感头”*。

### 步骤 3：编写可执行探针进行证明（Prove by Running Code）
对于每一个关键安全事实，按以下梯队尽可能推进，并诚实标明止步于哪一层：
1. **口头宣称（You said so）**：零价值，不可采信；
2. **指出代码行（Pointed at line）**：指出具体 `file:line` 的防御逻辑，较弱；
3. **推导不可达（Showed it can't happen）**：静态全分支排查证明异常路径不可达，中等；
4. **运行代码证明（Proved by running real code）**：**最高等级**。编写一个可执行脚本或测试用例，真实模拟调用并执行，用绿灯日志或抛出的错误断言，确凿证明安全前提成立！

## 反借口与典型红线（Common Rationalizations & Red Flags）

| 典型借口 / 行为偏差 | 严厉反驳与纠偏纪律 |
| :--- | :--- |
| “我搜过了，整个项目只有两处调用了这个函数，所以改动很安全” | **轻信静态搜索！** 必须检查是否有动态解构、RPC 调用或反射，并跑代码证明。 |
| “我写了一份两千字的影响分析，逻辑天衣无缝” | **纸面文章不顶用！** 把两千字浓缩成 1 个核心安全前提，并用一段可运行的脚本证明它。 |
| “这个改动太底层了，没办法测安全前提” | **借口！** 越是底层改动越需要用隔离的小探针脚本证明，否则绝不允许合入。 |

## 退出判据（Exit Criteria）
- [ ] 提炼出变更安全所依赖的 1–2 个关键事实；
- [ ] 提供可被复现执行的代码或测试脚本及其运行输出证据；
- [ ] 明确声明当前证明所达到的确定性等级。
