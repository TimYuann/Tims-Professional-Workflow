# 入口整备

> 把外来 issue / PR 过一遍状态机，分类、验证、必要时追问，产出可交给 agent 的简报。

- 阶段：P2　归属角色：`cartographer`　产物：A5

## 什么时候用

- 有人问「现在有什么需要我处理」，需要把入口项按状态摆出来。
- 有人点名某一条外来 issue 或外部 PR 要处理。
- 有人要你把某一条移到「可以直接开工」的状态。
- 手上积压了一堆没人分类的入口项，状态混乱、标签打架。
- 上一轮整备留了追问，对方刚回复，需要接着往下走。

## 开工前要拿到

- 事实集 A2。没有 A2 就没有「这件事是不是已经做过了」这个判断的底座，整备会退化成照着描述转述。
- 拿不到 A2 就退回：查过没有命中与没查过，在这一步产生的后果完全不同——前者可以直接判定不修，后者只能退回调查。
- 手上若有该条目上一次的整备记录，先读它，标出哪些问题已经有答案，不要重复问。

## 方法

1. **分类（一个类别 + 一个状态）。** 类别只有两个：有东西坏了；要做新东西或改进。状态只有五个：待评估；在等报告人补信息；已经完全说清、可以交给机器独立开工；只适合人来做；不会做。**状态打架就先停下来问，不要先动手。**标签的确切字符串由所在系统决定，但角色语义不能改。
2. **摆出待处理的三堆。** 从未整备过的；正在评估的；在等补信息且报告人自上次整备后有新动作的。**最老的排在前面**，每条给一行摘要和计数，让人来挑。外部 PR 和 issue 一起进这三堆并各自标明类别；只显示真正的外部 PR——协作者自己正在做的 PR 不是整备对象，但如果被点名了，照样整备。
3. **收齐上下文。** 读全量：正文、评论、标签、作者、日期；是 PR 的话把改动也读完。先解析上一次整备的记录，避免重问已解决的问题。
4. **查两条底。** （a）**冗余**：按领域概念而不是按对方措辞，去代码里找这个行为是不是已经实现了，并报告你搜了哪里。找到了就是「已经做过了／不做」。（b）**既往否决**：翻已否决项的知识库，把相似的请求拎出来。
5. **给建议，不要自己定。** 把类别建议、状态建议、理由，以及跟这条请求相关的代码现状一并发出去，等人给方向。**在拿到方向之前不推进状态。**
6. **验证声明。** 追问之前先验：报 bug 就照报告人的步骤复现；是 PR 就把改动取下来跑相关命令，确认它做的确实是它声称的。报「确认了（附上代码路径）／没复现／信息不足」三种结果——信息不足本身就是强「等补信息」信号。验过之后写出的简报，比只读过描述的简报有用得多。
7. **必要时追问。** 一次问一轮，把模糊的请求问成有形状的，同时把领域词磨准；每落定一个决定就地更新对应的记录。**不要自己回答自己的问题**——那不是追问，是自问自答。
8. **落状态。** 可机器开工的：发一份机器可用的简报（从使用者视角写要建什么、验收判据、它被什么阻塞）。只适合人做的：同样的结构，另加一句为什么不能外派（判断题、外部权限、设计取舍、要人手工验）。等补信息的：发一条整备记录，分「已经确认的」与「还差你回答的」，问题必须具体可答，不许写「请提供更多信息」。不做的：关掉，并按原因分三种处理——**已经做过了**就指出它活在哪，不要写进已否决知识库（那里放的是被否决的请求，不是已建成的）；**否决的 bug** 给一句解释再关；**否决的新功能** 写进已否决知识库并在评论里链过去再关。
9. **外发文本要标明来源。** 整备期间发出去的每一条评论都必须带一句「这是机器在整备过程中生成的」，不得冒充人写的。
10. **被要求直接改状态时照做。** 人说「把它移到可开工」，就照做——先复述你将要做哪几件事（改哪个状态、是否发评论、是否关掉），再做。跳过追问环节；如果在没追问的情况下直接放到「可开工」，问一句要不要补一份简报。
11. **接着上一轮往下走。** 有既往记录就读，检查报告人有没有回答尚未解决的问题，把更新后的图景摆出来再继续，不重问已解决的。

## 产出

落到 A5：

- `slices`：每个通过整备的条目落成一片，写清它是建什么（从使用者视角）、归哪个类别、判为什么是它最终落到的那个状态。要落到「不做」的也要留片，写清理由与去向。
- `edges`：每片声明它被什么阻塞——等补信息的条目把未答问题本身写成阻塞边；依赖别人先迁的旧代码的条目，写清它等哪一片。已否决的条目边上无阻塞，但要有明确的终止标记。
- `acceptance`：每片的验收判据写成可判否的端到端行为。**判据只能来自 A4 的 `done_definition` 口径或条目自身写明的行为，不得由整备阶段发明新的验收标准**；条目没写清行为的，先追问再落片。

## 常见做错

- 不查冗余就分类：按措辞搜一遍没搜到就判「新需求」，结果是把已有功能当成新功能排进图里。正确做法是按领域概念去找，并报告搜过哪里。
- 自己把追问里的问题回答掉：条目立刻变得「完全说清」，而那个说清是编的。人在场时追问，人不在场就写进「等补信息」。
- 把「无法复现」当成「没有 bug」：复现不了只说明现在的信息或环境不够，它是追问的输入，不是结论。
- 已经做过的请求写进已否决知识库：那个库记录的是被否决的请求，不是建成的东西。写错会让以后同类请求全被一句话挡掉。
- 状态标签冲突时顺手挑一个：状态打架说明有人在别处改过这件事，静默选定会把别人的意图覆盖掉。正确做法是停下来问。
