# 先写规格

> 写代码前先写规格；规格是人与工程之间的事实来源。

- 阶段：P1　归属角色：`architect`　产物：A4

## 什么时候用

- 新项目、新特性，或者一次动到多处的大改，还没有写下来的规格。
- 需求本身就是模糊的，或者只以一个模糊想法的形式存在。
- 你正要做一个架构决定，而这个决定的判据还只是「感觉这样更好」。
- 诉求已经谈透了，只差一份能开工的规格：决定都定过、但还没落成文字。这时走合成，不要再访谈一轮。
- 一次要做的事长到一次会话装不下，不切开会做偏。
- 反过来：一行修复、错别字、需求自包含且无歧义的改动，不需要规格。

## 开工前要拿到

- A1 诉求陈述，`ask` 与 `non_goals` 非空。**规格的边界只能从诉求的排除项里来。**
- A2 事实集，至少 `claims` 与 `evidence` 有内容。事实不足时写出来的规格，
  每一处「我们假设……」背后都是一次返工。
- **拿不到 A1 就退回**。退回去的是「这个特性到底要解决什么还没定」，
  带着模糊诉求写规格，等于把模糊固化成了看起来正式的文档。
- **判断走哪条起手方式**：能不能说出这件事的关键决定（建什么、不做什么、给谁、什么算完成），
  而且说得出来的东西有依据？能 → 合成路径；不能，或者能说出来的只是推测 → 访谈路径。
  判错的代价不对称：该合成时多问一轮只是浪费时间，该合成时直接合成会把假设固化成正式文档。

## 方法

**先选起手方式：合成还是访谈。** 两条路径写出来的东西不一样，**产出都是同一份 A4**。
判据只有一条——诉求谈透了没有。谈透了走合成，没谈透走访谈。
分不清就按没谈透处理：合成省下的时间补不回一份被固化的误解。

### 路径 A · 合成（诉求已经谈透）

**不访谈。** 不许把已经谈定的事重问一遍，也不许为了凑齐格式去编需求。
材料只有两样：已经发生的对话，和代码现状。**材料里没有的东西，规格里不许出现。**

1. **先对一遍现状。** 还不了解这块代码现在长什么样就不要动笔。
   通篇用项目既有的领域词汇（术语表怎么定的就怎么用），这块地方已经定过的决定
   （决策记录、已冻结的契约）尊重它们，不要另起一套叫法——
   另起一套叫法等于把一个已经消解过的歧义重新引进来。
2. **先划验证接缝。** 写下打算在哪些接缝上测这个特性。**优先用已经存在的接缝；用能用的最高的那一条；
   非开新接缝不可，就开在能开最高的点上。**接缝越少越好，理想状态是全库一条。
   理由：每多一条接缝就多一处要另写一份测试的地方，而且它会诱使实现把逻辑摊到接缝上。
3. **唯一的一次确认。** 把划好的接缝给用户看，请他核对这套接缝是不是他预期的。
   合成路径上允许的是**确认**，不是**提问**——把已经谈定的形状亮出来核对，
   和用开放问题去挖需求，是两件不同的事。
4. **写正文，六块。**
   - **诉求**：这件事的问题是什么、解决之后是什么样，**都从用户的视角写**——
     用户怎么描述这个麻烦、怎么描述它变好了。不要写成系统的自述。
   - **用户故事**：一份**长的、编号的**清单，每条一个固定句式：
     作为<角色>，我想要<能力>，以便<收益>。要覆盖这个特性的各个侧面。
     **清单短是危险信号**：两三条通常意味着合成时在偷懒，
     剩下没写出来的侧面会在实现阶段变成惊喜。
   - **实现决定**：建哪些模块、改哪些模块、这些模块的接口怎么改、哪些技术澄清已经定了、
     哪些架构决定、数据形状怎么变、对外契约怎么变、具体怎么交互。
     **不写具体文件路径，不写代码片段**——它们比正文过期得快得多。
     唯一的例外：原型里某段东西比散文更精确地表达了一个决定（状态机、归约、模式、类型形状），
     那就把它缩到只剩决定本身，内联到对应的那一条决定里，并注明它来自原型。
   - **测试决定**：什么算好测试（只测外部行为，不测实现细节）、哪些模块要测、
     仓库里已有的同类测试长什么样（先找到先例再动手，不要自己发明一种写法）。
   - **不做**：这次明确不碰的。
   - **附注**：其余要交代的。
5. **落进项目既有的问题跟踪系统**，并标成可以直接开工的状态。
   **不要为了标状态再补一轮分诊**，也不要在已有体系旁边并排造第二份规格。
6. **过一道关**：诉求与用户故事同源（没有跑出诉求范围的故事）、实现决定里没有会过期的路径、
   测试决定能推出可判定的完成口径、正文里没有夹带「待定」。

**`why` 从哪来**：合成路径不新编理由。A4 的 `why` 只能从已经谈定的对话里取。
**取不出来就是访谈没谈透的信号**——退回起手方式的判断，改走访谈路径，
不要在合成正文里补一段听起来合理的理由，那是最容易混进正式文档的一种编造。

### 路径 B · 访谈（诉求还没谈透）

**第 0 步 · 规模检查（只在一种情况下做）**
一次请求捆了多个可以各自独立验证的能力时才做。识别信号：
需求点名了几个各有自己消费者或数据的能力；验收口径聚成了可以分开上线的几组；
或者砍掉其中一个不会逼你重写其它能力的规格。
命中就在写任何规格正文之前，先出一张**能力地图**：模块 id 加职责加依赖方向，加一条建造顺序。
模块 id 用短横线小写，定下就不改名；依赖箭头单向，两个模块互相需要就是同一个模块；
模块之间的契约放在提供方那侧。地图本身也要过一次评审——地图错了很贵，评审十行不贵。
没命中就直接跳到下一步，不要给单一能力的特性套一层层级。

**第 1 步 · 写规格**
1. **先把假设摆出来。** 动笔前列一份「我正在假设的」清单，放在正文最前面，请对方现在纠正。
   静默填补模糊需求是这里最贵的错误——规格存在的全部意义就是把误解提前暴露在代码之前。
2. **写六块内容**：建什么、为什么、谁受益（目标）；完整的可执行命令（带参数，不只是工具名）；
   项目结构（源码、测试、文档各住哪）；风格（一段真实代码胜过三段描述）；
   验证策略（用什么、测在哪、覆盖到什么程度、哪类关注点在哪一层测）；边界（见下）。
3. **三档边界**：永远做、**先问再做**、**永远不做**。
   「永远不做」这一档里要有一条：**这个文件本身不得为了让某次改动通过而被降低标准。**
4. **把模糊要求重写成成功口径。** 「让它快一点」不能进规格，
   要写成能判定的条件（首屏在某个网络条件下某个指标低于某个值、某次加载在多少毫秒内完成），
   然后把这几条念回去问对不对。重写出来的口径才是后面判 PASS/FAIL 的依据。
5. **规格要落进仓库。** 仓库已有规格体系就沿用它的产物格式和存放惯例，不要并排造第二份。
   这条技能拥有的是澄清、内容与评审关；怎么表示由既有体系决定。
6. **写完过一道关。** 六块齐了、对方确认了、成功口径可判、边界写死了，才算写完。

### 规格是活的
决定变了先改规格再动手；范围增减也反映在规格里；规格进版本库，和代码一起被评审；
下游改动回指它实现的是哪一节。

### 这一节之外的事

从规格拆出实现顺序和任务片、逐片实现、逐片验证，是别的阶段的事。这里只交冻结的那份契约。

## 产出

A4 冻结契约，四个字段都要在写代码之前定死。**合成路径不另出产物编号**，
它的六块正文按下面的落法装进这四个字段：

- `what`：合成路径先接诉求与用户故事清单——每条故事写清角色、能力、收益，
  合起来覆盖「建什么」；再接实现决定——建/改哪些模块、接口怎么变、数据形状怎么变。
  访谈路径的合格线不变：动词开头，第三方能原样复述，听完不需要问「具体指哪个」。
- `why`：为什么——业务理由，不是技术偏好。「因为这个结构更干净」不算 why，
  「因为每加一个渠道就要改三处核心逻辑」才算。**合成路径下它只能由已谈定的对话提供，写不出来就是路径选错了。**
- `done_definition`：什么证据算完成。**必须可判定：只凭它，第三方能给出 PASS／FAIL／UNVERIFIED 三个判定之一。**
  「功能可用」不可判定；「在 X 条件下 Y 指标不高于 Z，验证命令是 C」可判定。
  合成路径的测试决定要能直接推出这几条口径，推不出来说明测试决定写得不够具体。
- `boundaries`：什么不做、什么不许改。覆盖本次变更涉及的全部系统边界，
  并且明确包含「不许为了让检查变绿而削弱检查」这一条。合成路径上这一块原样来自诉求的排除项，
  缺失即视为诉求没谈透。

规模检查命中时，能力地图不占 A4 编号：它是写正文之前的一道关，产出后 A4 按模块分别写，
每个模块的 `done_definition` 各自可判定。

## 常见做错

- 先写代码再补规格：那是事后文档。规格的价值全在动手之前那一次澄清。
- `done_definition` 写成「写完了就算」：不可判定的判据等于没有判据，
  下游所有环节都只能靠「看起来对不对」来推进。
- `why` 写成技术偏好：三年后没人能从中判断当初的取舍在什么前提下成立。
- 隐式假设不写出来：规格里那些「我们假设」会在实现阶段变成惊喜，而那时改的成本已经翻了几倍。
- 多个可独立验证的能力塞进一份规格：下游每一片都不得不对着整份契约推理，
  而一份十行的能力地图是更便宜的选择。
- 一次请求捆了几个能力，还打算「在规划阶段再拆」：模块边界和依赖方向在写规格之前就要定，
  到规划阶段那份超大的产物已经存在了。
- **该合成的时候又访谈一轮**：把已经定下来的事重新问一遍，零信息增益，
  却把「谈透了」这个前提重新拉回未知。
- **该访谈的时候直接合成**：合成产出的规格和访谈产出的语气一模一样——都很正式，
  里面塞的却是编出来的决定。判据是 `why` 取不取得到，不是文档的语气。
- 用户故事只写了两三条：清单长度是覆盖率的下界。剩下的侧面没写，
  等于把它们交给实现阶段现场发明。
- 实现决定里写满文件路径和代码片段：正文和它引用的一切具体物都会漂移，
  而这些路径不会跟着代码一起被读到。
- 验证接缝留到规格写完再想：接缝决定的是要在哪里证明对，而它反过来约束模块形状。
  写完再定接缝，等于先画完了再找尺子。
