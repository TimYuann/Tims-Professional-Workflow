# 薄片增量

> 以薄的、可验证的片交付变更，每片结束于可运行状态。

- 阶段：P3　归属角色：`builder`　产物：A6

## 什么时候用

- 任何跨一个以上文件的改动。
- 按任务图接着做下一片时。
- 重构现有代码时。
- 手上有一个功能开关：需要先把未完成的增量合进去，但不能让它对使用者可见。
- 手痒想一次写一大片——这个技能存在的时刻就是那一刻。

不适用：单文件、单函数、范围已经最小到没有余地的改动。

## 开工前要拿到

- 任务图 A5：这一轮要落的片和它的验收口径。
- **拿不到 A5 就退回**：没有片就没有增量边界，「薄」会退化成「随便切一刀」。
- 若目标是让检查点来得及发现别人的破坏，先确认这一片可以独立落地（不依赖别人正在写的代码）。

## 方法

1. **跑一个增量循环。** 实现最小完整的一块 → 测 → 验证（测试过、构建过、必要时手工点一下）→ 提交 → 进下一片。**不通过这一片，不开始下一片。**
2. **先想最简。** 动手前问「能做成什么样的最简版本」。写完过一遍这几问：能不能更少几行、这些抽象挣到自己的复杂度了吗、有没有更直白的选择、我是不是在为假想的需求搭架子。
3. **锁住范围。** 只碰这一片要求的：不顺手清理相邻代码、不重构没改到的文件的导入、不删自己没完全看懂的注释、不加契约里没有的能力、不顺手升级语法。**看到了范围外值得改的地方：记下来，不要改。**
4. **一次只做一件逻辑上的事。** 一次提交里同时加新东西、重构旧东西、改配置，就是三件事。拆成三次提交。
5. **保持可构建。** 每个增量之后项目能构建、已有测试全绿。不许在两片之间留下一个跑不起来的状态。
6. **没完成的功能挂开关。** 增量要合并但功能还不该给使用者看时，现在就把开关加上并默认关掉。**「功能没做完就先合，开关以后再补」是错的**：没做完的代码在没开关的情况下就是对使用者可见的破坏。
7. **默认取安全值。** 新代码的默认行为取保守的一侧（缺省不触发、需要显式开启），不要让「参数没传」等于「全开」。
8. **可回滚。** 每个增量能单独撤：新增性的改动好撤，改既有代码的部分要小而聚焦，迁移要有对应的回退迁移。**不要在同一次提交里删掉什么又用新东西替上它**——拆成两次。
9. **不重复跑没变过的命令。** 成功跑过一次、代码此后没动，就不要重跑——重跑不产生新信息。在后续编辑之后再跑才有意义。
10. **切片的三种排法。** 纵向：一条条端到端通路（能建 → 能列 → 能改 → 能删），每片都交付一段完整可用功能。契约先行：先定接口契约，然后后端与前端各自对着契约做，最后合流验一次。风险优先：把最不确定的那块放第一片，它失败时你还什么都没铺。

## 产出

落到 A6：

- `change`：按增量序列写，每片一次提交，说清这片让什么行为变可用、范围严格停在哪。合格的判据是把 `known_gaps` 里的项对照回来，能指出「这个缺口是哪片故意留下的」。
- `runnable`：这一轮跑过的真实验证记录——每片的测试、构建、类型检查结论，加上最终那条端到端确实能观察到新行为的检查。全部是跑出来的，不是「应该」。
- `known_gaps`：每片明确留下的缺口：还没接的边界情况、还挂在开关后面的能力、还没删的旧形态、以及范围外记下来但没改的东西。这一栏按增量分条写。

- **`subject`**：**候选的对象身份**——开工时的基线 commit，交付时的结果 commit。`P5` 验证的对象必须与它逐字一致。这一栏空着，下游证明不了「验证过的就是上线的」。**每个产出 `A6` 的技能都要在交付时填上它**。

## 常见做错

- 「反正最后会测」：第一片里的缺陷会让后面四片全错——它们是按第一片那个错误的前提建起来的。测试跟着每片走。
- 「一次写完更快」：感觉上更快，直到某个地方坏了，你得在几百行改动里找出是哪一行。薄的片换来的定位能力就是这个。
- 「这个重构很小，一起改了吧」：重构和特性混在一起，两件事都变难审、难回滚、难从历史里读出来。
- 开关留到以后再加：该合并的未完成增量现在就暴露给了使用者。开关和增量同时来。
- 在没变的代码上重跑一遍以求安心：它不会告诉你任何新东西，只会在你心里种下一颗「上次是不是真的绿了」的怀疑。
